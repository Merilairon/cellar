### Conditions for the tag

1. **README Known limitations is incomplete.** It does not mention CR-m2d (two very fast browser Backs can leave the editor with unsaved edits) or O4 (`Alt+Left` / `Alt+Right` unverified against real browser history; the README keyboard table advertises them as the "move step one column" chord). It says "browser Back ... ask first" without the residual. Both are honestly stated in `v0.4.1-carryover.md` only. Add one sentence each to the README.
2. **Q11 owner try.** Either record one line from the owner's real phone / tablet try in this file, or ship with "not tested on real devices" in the release notes (the README already says this).
3. **"From scratch" is a reading, not literal.** The mouse and keyboard specs start from a grid recipe that already holds eight of the nine ingredient rows and one column step (`cookieStart(8)`); the phone spec starts with all nine rows. Rows 1 to 8 are never typed in the editor, and the sample used (Mocha Skillet Cookie) has no sections, split rows or bottom banner. This follows owner decision Q5 (grid recipes only; a grid needs a column step) and the UX spec F1, and the spec says so in its header, but the milestone sentence "recreate the sample grid from scratch" is met only in that reading. State it in the carryover or release notes.
4. Nits to record, not block: phone step-sheet text inputs measure 42 px tall (spec wording is about buttons, which are all 44 px; the e2e target-size test does not measure the collapsed sheet details); tasklist DoD checkboxes are still unticked and `RELEASE_PLAN.md` still says "pending gate" (update after the tag).

### Acceptance criterion: "recreate the sample grid from scratch using only the mouse and also only the keyboard"

- **Specs inspected for vacuity.** Mouse spec: a first test reads its own source and fails on `keyboard.press`, `.press(`, `keyboard.down`, `keyboard.up`; the scan is anchored by `sourceBody()` which throws if the marker is missing (the m10 fix, tested in `tests/unit/source-body.test.ts`, passes). The test then performs real `page.mouse` drags on the span handles, clicks, typed text via `fill`, Undo and Redo through buttons, saves, then compares the stored recipe via `project()` against `SAMPLE_SKILLET_COOKIES` including kinds, labels, details, spans, temperatures, minutes, banner order, split groups and `view_mode`. Keyboard spec: a first test bans `page.mouse`, `.click(`, `.dblclick(`, `.tap(`, `.hover(`, `.dragTo(`, `.fill(`, `.check(`, `.focus(`, `.selectOption(`; the body uses `Tab`/`Shift+Tab` through a `reach()` helper that only presses keys, plus chords from the spec, `Ctrl+S` to save, then the same comparison. Phone spec: taps and stepper buttons only, 375 x 667, `hasTouch`.
- **Run:** all three pass in the 206-test run (mouse 2.6 s, keyboard 2.3 s, phone 2.9 s). **My negative control failed the mouse spec as expected** (see commands).
- **Caveats (not vacuous, but weaker than the sentence):** the start state is not empty (condition 3); `project()` compares `raw_text` and names but not numeric quantity fields; the "mouse only" test types text with `fill()`, which is "typed text" in the spec's own allowance; Alt+Left/Right is not part of the recreation.
- Status: **PASS in the reading used by the spec (Q5/F1), with condition 3.**

## What was NOT run

- **Real phone or tablet, any touch hardware**; drag against sideways scroll on touch; on-screen keyboard over Save; iOS sheet scroll lock; Android back and iOS edge swipe through the history guard. Q11 try unrecorded.
- **Firefox, Safari / WebKit**; any width other than those in the specs; macOS or arm64 rendering. Baselines are Linux x86_64 only.
- **Any screen reader** (NVDA, JAWS, VoiceOver, TalkBack, Orca). axe results and structural checks are taken from the e2e run (they passed); what a user hears is unknown.
- **Raspberry Pi / arm64**; the Caddy compose profile; the headless compose profile and the sidecar Docker suite (`docker/browser/scripts/docker-tests.sh`, the sidecar is untouched in this diff); real-network TLS.
- A v0.3.x or older data volume (only a v0.4.0-era volume was upgraded).
- The double-Back race, the header-link guard by hand, a service-level race between the pre-check and the transaction, two truly simultaneous saves, large-body and chunked-body edge cases, `npm audit`.
- Browser (UI) display of `4 oz butter -> 115 g` and `x2 -> 8 oz (230 g)`: covered by the `display.test.ts` unit tests inside the 2408 passing tests; not re-checked in a browser by me.
- Performance: the C11 / perf-sanity figures (create 4 ms, save 4 ms at 1000 recipes, in memory, developer machine) and the 4000-row 0.66 s save are quoted, not re-measured. Not Pi-class.
- The checkpoint's deliberate guard-removed / compare-removed / validator-removed negative controls were not repeated (only the positive tests were run).
- Real family usability sessions. The `v0.4.1-usability-check.md` is an agent walkthrough and says so; F9 (phone chrome height) was never measured.
- Hydration negative control: quoted from T15, not repeated.
