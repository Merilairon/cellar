# v0.3.2 S0 spike: headless sidecar on x86 and arm64

Date: 2026-11-06. Host: x86_64, Docker 29.9.3, runc 1.5.2, kernel 7.3. Scratch code: `docker/browser/` (Dockerfile, `spike.mjs`, `run.sh`, `seccomp-userns.json`). Becomes T2 if kept.

## Go / no-go

- **x86_64 (amd64): GO.** Chromium's own sandbox works (no `--no-sandbox`), non-root, `cap_drop: ALL` plus one cap.
- **arm64: NOT VERIFIED. Open item, not a no-go.** This host has no QEMU/binfmt for arm64 (`alpine` arm64 fails with `exec format error`, `/proc/sys/fs/binfmt_misc` has no qemu entry). Registering binfmt needs a privileged container that changes host config, so it was not done. Needs a real arm64 host, or the owner's OK to run `tonistiigi/binfmt --install arm64`, or a CI job (QEMU). Until then the arm64 line is "unknown"; do not claim support.
- Manifests exist for arm64: `mcr.microsoft.com/playwright:v1.64.1-noble` and `node:24-bookworm-slim` both publish `linux/amd64` and `linux/arm64`. `package-lock.json` carries `@img/sharp-linux-arm64` and `@img/sharp-libvips-linux-arm64`. These show availability only, not that anything runs.

## Answers

1. **Image and render, per arch.** amd64: slim image (`node:24-bookworm-slim` + `playwright-core@1.64.1` + `install --with-deps --only-shell chromium`) builds in about 50 s. Chromium 156.0.8078.4 (headless shell) rendered a JS-only fixture (JSON-LD injected by script): `{"arch":"x64","uid":10001,"chromiumSandbox":true,"version":"156.0.8078.4","domLen":752,"jsRendered":true,"renderMs":734}`. arm64: not run (see above).
2. **Size and memory (amd64).** Image 1.24 GB on disk (content 1.24 GB; the full `playwright` image is 3.63 GB, so the slim build is the way). RSS summed over all processes (double counts shared pages, so an upper bound): idle after launch 354 MB, after one render 566 MB. Render of the tiny fixture 0.7 s wall. Fits `mem_limit 1g`. **Not measured**: a heavy real page (no outbound test target was set up); T18 must measure it, and arm64 numbers.
3. **Sandbox.** Works without `--no-sandbox` on amd64 with: user `pwuser` (uid 10001), `--cap-drop ALL --cap-add SYS_CHROOT`, `no-new-privileges`, read-only root, tmpfs `/tmp` (noexec), custom seccomp = Docker default profile plus `clone, clone3, unshare, setns` allowed (`seccomp-userns.json`). Findings that change the plan:
   - Docker default seccomp: "No usable sandbox" (blocks user namespaces).
   - Playwright's documented `seccomp_profile.json` (fetched from microsoft/playwright main): **runc 1.5.2 crashes at container start** (SIGSEGV in libpathrs, "container process is already dead"). That profile is too restrictive for this runc. T5 must not assume it; it needs re-testing on the target hosts' runc versions.
   - `cap_drop: ALL` alone fails: `Check failed: sys_chroot("/proc/self/fdinfo/") == 0`. The zygote needs `SYS_CHROOT` (a user-namespace root cannot exceed the container bounding set). **Decision for review: `cap_add: [SYS_CHROOT]`** is the one extra capability. It is not `SYS_ADMIN`.
   - Host sysctl `user.max_user_namespaces` must be non-zero (256146 here). Hosts with unprivileged userns disabled (some hardened distros) cannot run the sidecar; document it.
4. **Proxy (G1).** Chromium launched with `--proxy-server=http://127.0.0.1:<port> --proxy-bypass-list=<-loopback>` plus `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`, `--disable-features=WebRtcHideLocalIpsWithMdns,NetworkPrediction,PrefetchProxy`, `--disable-background-networking`, `serviceWorkers: 'block'`. A fixture page tried: WebSocket (went to the proxy as `CONNECT canary.invalid:9999`), RTCPeerConnection with a STUN URL, `fetch` to 127.0.0.2, `<link rel=preconnect>` to 127.0.0.3, `rel=prefetch` to 127.0.0.4, `rel=dns-prefetch`. Canary listeners (TCP on 127.0.0.2/3/4 port 9, UDP 3478) recorded **zero direct connections**; the proxy log saw only the page load and the WebSocket. **Decision: (a) filtering forward proxy in the sidecar.** Limit of the evidence: loopback canaries only, no packet capture on a real bridge; T9/T12 must re-check with an external canary host.
5. **Network layout (G2), tested with two plain containers.** `spike-link` (`--internal`) plus `spike-egress` (normal bridge): browser reaches the internet (yes), app on the internal network alone has no internet (DNS fails), app reaches browser by service alias (ping ok). **But the browser container on the egress bridge reaches a host service via the bridge gateway (`172.21.0.1:18080` returned the host's page).** So compose networks alone do NOT satisfy "no route to the host". The in-sidecar IP guard (G1) is mandatory, not optional, and must reject the gateway address; the `DOCKER-USER` snippet stays optional layer 2. Not tested: the app's SQLite volume (it is simply never mounted into `browser`) and LAN ranges beyond the gateway.
6. **sharp in the app image.** amd64, `cellar:local`: `sharp 0.35.5, libvips 8.18.7, x64, create PNG -> resize -> WebP re-encode ok (82 bytes)`. arm64: not run (no emulation). Still the v0.3.0 carryover; T18 or an arm64 host closes it.
7. **Profile off.** No compose change made in S0; `docker compose config --services` still lists only `app`. Re-verify after T5.

## Decisions to record

| Item | Decision |
| --- | --- |
| G1 | Filtering proxy inside the sidecar (a) |
| Sandbox | Chromium sandbox ON; user `pwuser`; `cap_drop: ALL` + `cap_add: [SYS_CHROOT]`; custom seccomp (Docker default + clone/clone3/unshare/setns); `no-new-privileges` |
| `--no-sandbox` | Not used, not needed on amd64 |
| Limits | `mem_limit 1g` fits (measured peak 566 MB, upper bound, light page) |
| Image | Slim build, 1.24 GB; pin base by digest in T2 |
