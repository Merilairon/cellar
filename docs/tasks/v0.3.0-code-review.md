# v0.3.0 Code Review (URL import, slice 3a)

Scope: `git diff main...release/v0.3.0` against `milestones/03-url-import.md` (3a: req 1-4, 6-9, 13, 14) and `docs/tasks/v0.3.0-tasklist.md`. Read-only review; nothing was executed or changed. The `RecipeForm.tsx` section-key hydration issue is excluded as agreed.

## Summary

The slice is solid. The SSRF layer is the strongest part: URL parsing goes through WHATWG canonicalization, DNS is resolved once per hop, every resolved address is checked, the socket is pinned to the validated IP, and redirects are re-validated manually. Wire and decoded bytes are both capped. Fetch options come only from `getEnv()`, the request schema is `.strict()`, and the local-fetch seam is refused outside dev/test. Ownership is enforced everywhere: jobs are owner-scoped (404 for others), photos use `canRead`, and the file path comes from the DB row and is checked against the uploads dir. Save is compare-and-set in one `immediate` transaction. Sanitization is applied at ingest and again at save. The cover pipeline is correct: magic bytes, pixel cap before decode, re-encode to WebP with metadata stripped, ULID file name, `wx` flag. Tests are broad and mostly assert real behavior.

No blockers. A few majors worth fixing before release, mostly resource-exhaustion and robustness. No security hole was found in SSRF, auth, CSRF, path handling or sanitization.

## Blockers

None.

## Major

### M1. No request-body size cap before JSON parsing (authenticated memory DoS) [FIXED: `readJson` takes a byte cap, 413 on oversize Content-Length or streamed body before parse; 1 MB import, 256 KB save]
`src/lib/recipes/http.ts` `readJson` (used by `src/app/api/import/route.ts:23` and `src/app/api/import/[id]/save/route.ts:15`).
Evidence: `await request.json()` buffers the entire body. The 500 KB `text` limit in `schemas.ts` is applied by zod only after full parse. A logged-in user can POST a multi-hundred-MB body. The rate limit counts the attempt but does not bound its size. Next route handlers have no default body limit.
Fix: in `readJson`, reject when `Content-Length` exceeds a cap (for example 1 MB for import, 256 KB for save) with 413. Also read the stream with a byte counter when the header is absent or chunked.

### M2. sharp decode is outside the concurrency limiter and the pixel cap is generous for the target hardware [FIXED: decode runs in a separate limiter (1 at a time, queue 4), cap 16 MP, `sharp.concurrency(1)` and `sharp.cache(false)`]
`src/lib/import/cover.ts:107-109` and `:16` (`MAX_COVER_PIXELS = 40_000_000`).
Evidence: `limitFetch` wraps only the network fetch. `reencodeCover` runs after it, unbounded. Each 40 MP decode is roughly 160 MB or more of RGBA. Several concurrent saves (the rate limit is per user, so many users or many jobs) can OOM a Raspberry Pi / small VPS, which the milestone names as a deployment target.
Fix: run `reencodeCover` inside the same limiter, or a separate limiter with max 1 or 2. Lower the cap to about 16-25 MP, and consider `sharp.concurrency(1)` and `sharp.cache(false)` on small hosts.

### M3. Import jobs are never cleaned up and can get stuck in `fetching` [FIXED minimally: stale `fetching` jobs (>5 min) are failed lazily on next import / GET by the same user; pruning of `draft_json` and raw HTML deferred, see carryover]
`src/lib/import/service.ts:90-91`, `src/lib/db/import-jobs.ts`.
Evidence: a job row is inserted and set to `fetching` before the pipeline runs. A crash or restart mid-fetch leaves it `fetching` forever. Every needs_review job keeps its full `draft_json`, with no TTL or pruning. `raw_html_path` files (KEEP_RAW_HTML) are never removed with their job. `src/instrumentation.ts` already runs an hourly session cleanup, so there is a natural place.
Fix: add an hourly prune (for example drop jobs not `saved` and older than 7 days, and unlink their `raw_html_path`), and mark stale `fetching` rows as `failed/fetch_failed` at boot. The `saved` jobs can be kept or pruned too, since they only reference the recipe.

### M4. Unbounded wait in the fetch concurrency queue [FIXED: queue cap 16 and 15 s wait timeout, 503 + Retry-After; job is marked failed]
`src/lib/import/limiter.ts:9`.
Evidence: callers beyond 4 wait in a FIFO queue with no timeout. The 10 s timeout only starts inside `safeFetch`, so the client request can hang for 10 s times the queue depth, and the request holds a Node handler the whole time. With the per-user limit at 20/h, a handful of users can queue many requests.
Fix: cap queue length (reject with `fetch_failed` or 503 and `Retry-After` when full) or put a total deadline around queue plus fetch.

## Minor

### m1. Relative cover URLs resolve against the entered URL, not the final URL after redirects
`src/lib/import/pipeline.ts` (`normalizeRecipe(node, { sourceUrl })`) and `src/lib/import/normalize.ts:125-131,210`.
Evidence: `page.finalUrl` is returned by `safeFetch` but unused. A short link or www/non-www redirect with a relative `image` resolves against the wrong origin or path, and then either 404s or fetches from an unintended host (still SSRF-guarded).
Fix: pass `finalUrl` as the base for relative resolution while keeping the entered, normalized URL as `source_url`.

### m2. Cover URL is force-upgraded from http to https
`src/lib/import/normalize.ts:131`.
Evidence: `abs.replace(/^http:\/\//i, 'https://')`. For http-only image hosts the cover fails every time (`cover_failed` warning). `normalizeSourceUrl` also stores `source_url` as `https://` (G12) even for http-only sites, so the shown source link can be dead.
Fix: try https first and fall back to the original scheme on connection failure (the guard applies per hop anyway). For `source_url`, consider keeping the scheme and only collapsing it in the duplicate-lookup key.

### m3. User cannot clear `source_url` during review
`src/lib/import/save.ts:81`: `tree.fields.sourceUrl ?? job.url`.
Evidence: clearing the field in the form yields null and silently falls back to the job URL. This is probably intended (attribution), but nothing tells the user.
Fix: either document it in the UI hint, or only fall back when the key is absent from the body.

### m4. `markImportJobSaved` CAS guards with `ne(status,'saved')` rather than `eq(status,'needs_review')` [FIXED]
`src/lib/db/import-jobs.ts:56`.
Evidence: correct today because `saveImport` pre-checks `needs_review`, but the CAS itself would also flip a `failed` or `fetching` job if called from elsewhere.
Fix: use `eq(importJob.status, 'needs_review')`.

### m5. Photo cache header outlives permission changes
`src/app/api/photos/[id]/route.ts:27`: `Cache-Control: private, max-age=3600`.
Evidence: after a recipe is made private or deleted, a previously authorised browser keeps the image for up to an hour. Low impact (private cache, same user).
Fix: `private, no-cache` with an ETag (photo id is immutable per file), or shorter max-age.

### m6. Corpus success rate excludes out-of-slice pages [FIXED: report prints both ratios]
`scripts/import-corpus.ts` (`rate = draftPassed / draftTotal`), `tests/unit/import-corpus.test.ts:15`.
Evidence: 44 fixtures: 34 expect a draft, 5 are `out_of_slice` (3 JS-only, 2 microdata), 5 are deliberate `no_recipe`. The gate measures 34/34 against the 34 drafts. The spec says 85% of the corpus (at least 30 pages) must yield a valid draft. By a stricter reading that is 34/39 = 87% of recipe pages, still passing. But the two microdata pages are in spec req 4 ("if time allows"), so excluding them is a scope decision that should be stated in the printed report and the release notes.
Fix: print both ratios in `npm run test:import` (in-slice and all recipe pages).

### m7. No test exercises reencode concurrency or the `sharp` failure mode on truncated or oversize inputs through `saveImport`
`src/lib/import/cover.test.ts` covers re-encode, EXIF stripping and SVG refusal. The decompression-bomb (`MAX_COVER_PIXELS`) path is not visibly covered end to end.
Fix: add a test with a small PNG whose header declares dimensions above the cap (hand-built IHDR) and assert `fetch_failed`.

### m8. `writeRawHtml` location derives from `dirname(uploadsDir)`
`src/lib/import/service.ts:42`.
Evidence: with `UPLOADS_DIR=/uploads` the raw dir becomes `/import-raw`. With `UPLOADS_DIR=./uploads` it lands in the project root.
Fix: add an explicit `RAW_HTML_DIR` env var (default `<dirname(DATABASE_PATH)>/import-raw`), validated in `env.ts`.

### m9. First resolved address only, no fallback
`src/lib/import/safe-fetch.ts:121` returns `addrs[0]`. Dual-stack hosts with a broken IPv6 route fail with `fetch_failed` even though an IPv4 address works. Security is unaffected (all records are checked).
Fix: try the next validated address on connect error (still bounded by the overall deadline).

## Nits

- `src/components/import/ReviewForm.tsx:79`: warnings use `key={w}`; a repeated warning code would duplicate keys. Use `${w}-${i}`.
- `src/lib/db/recipes.ts:338`: `findReadableRecipesBySourceUrl` is only referenced from `import-schema.test.ts`, and `findRecipeBySourceUrl` does the same job. Remove one, or make the test use the shipped function.
- `src/lib/import/safe-fetch.ts:223`: an `abort` listener is added per hop and never removed. Harmless (max 6, `once`), but `AbortSignal.any`-style cleanup would be tidier.
- `ImportDialog` cancel aborts the client request but the server keeps fetching and the attempt still counts against the rate limit. Worth a line in docs.
- `src/lib/import/save.ts:15`: the `SaveResult` union formatting looks like it escaped prettier (leading `{` on the continuation line).
- `src/lib/import/save.test.ts:190-205`: the comment in the rollback test talks about "break the FK" then does something different (spies `markImportJobSaved`). The test is valid, the comment is stale.

## Security checklist (verified by reading, not by running)

| Area | Result |
| --- | --- |
| SSRF: scheme, userinfo, port, URL length | OK. Non-default ports rejected unless the dev seam is on. |
| SSRF: IPv4 forms (decimal, octal, hex, short) | OK via WHATWG canonicalization, then `isBlockedIp`. |
| SSRF: IPv6 (mapped, NAT64, 6to4, Teredo, ULA, link-local, doc) | OK in `ip-guard.ts`. Fail-closed on unparsable literals. |
| SSRF: DNS rebinding, mixed A/AAAA | OK. Resolve once, reject if any record is blocked, pin the socket. |
| SSRF: redirects | OK. Re-validated each hop, max 5, wall-clock deadline across hops. |
| SSRF: size, decompression bomb, timeout | OK. Wire and decoded caps, 10 s deadline. |
| SSRF seam from request | OK. `.strict()` schema, options built only in `route-deps.ts`, production refuses the env flag. |
| Cover URL source | OK. Taken from the stored draft, not the save request. |
| Auth and ownership on `/api/import*` | OK. CSRF (403) then session (401), job scoped by `user_id` (404). |
| Auth on `/api/photos/:id` | OK. `canRead` on the recipe, 404 otherwise. Path from the DB row, escape check. |
| CSRF | OK on all mutating routes via `authenticate`. JSON content type required (415). |
| Rate limiting | OK on `/api/import` per user, counting failures. Save is not limited, but is one-shot per job and jobs are limited. |
| Upload handling | OK. Magic bytes, pixel cap, re-encode, metadata stripped, ULID name, mode 0600/0700. |
| Path handling | OK. `resolveUploadPath` rejects absolute and `..` escapes. |
| Sanitization | OK. Linear regexes, bounded input, entity decode once then re-strip, bidi and control chars removed. Rendered as React text only. `safeHttpUrl` guards links. |
| Transaction and race on save | OK. Recipe insert and job CAS in one `immediate` transaction. Double submit gives 409. Cover after commit, best effort, orphan file cleaned if the DB insert fails. |
| Error hygiene | OK. `ImportError` carries codes only. Logs omit page content. No `raw_html` in responses. |

## Tests that assert little

Nothing is vacuous. The thinnest files are small but purposeful (`duration.test.ts`, `limiter.test.ts`, `source-url.test.ts`, `ip-guard.test.ts`). `tests/unit/env-production.test.ts:22` uses `toBeTruthy()` on a parse-result function that is called; acceptable. The route tests mock `safeFetch`, `getEnv` and the db seam, so they check wiring and policy, not the network; the real transport is covered by `safe-fetch.test.ts` (real loopback socket, pinned IP, Host header). The corpus gate is only as strong as its `.expected.json` files (m6).

## Verdict

**APPROVE WITH CHANGES**

Please address M1 and M2 (cheap, directly protect a small self-hosted box) and M3/M4 before tagging. The minors can go to the carryover list. The SSRF, auth, CSRF, path and sanitization work needs no changes.
