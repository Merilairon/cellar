# v0.3.2 Headless sidecar threat model (T1)

Date: 2026-11-06. Author: security-architect. Inputs: `v0.3.2-tasklist.md` (G1-G17, Security note), `v0.3.2-spike.md` (S0 evidence, amd64 only). Status: reviewed for T3 start, pending security-appsec-engineer sign-off (tasklist T1 acceptance).

## 1. System overview

An optional `browser` container (Playwright `chromium` headless shell, Node HTTP server) renders one URL per job and returns the serialized DOM to `app`. Off by default (`HEADLESS_URL` unset, compose profile `headless`). It executes attacker-controlled JavaScript from whatever URL a logged-in user imports.

Assets, by value:

| Asset | Why it matters |
| --- | --- |
| Host network, LAN, cloud metadata (169.254.169.254) | SSRF target through the browser |
| `app` container, port 3000, `/data` volume (SQLite, photos, raw HTML) | Holds all user data and sessions |
| Other compose containers (Caddy, future services) | Lateral movement |
| Host kernel | Container escape via Chromium bug plus kernel bug |
| Operator bandwidth, CPU, RAM | Abuse, DoS on small hosts |
| Operator IP reputation | Browser traffic exits from the operator's address |

Attackers:

- A1: malicious or compromised web page (hostile HTML, JS, redirects, DNS answers, responses).
- A2: malicious authenticated user who chooses the URL (the app has self-registration disabled by default, but any member is an A2).
- A3: a compromised sidecar (after a Chromium exploit) attacking the app, the network or the host.
- A4: another container on a shared compose network calling `/render`.

## 2. Trust boundaries and network design

```
internet (hostile) <--80/443-- [headless-egress bridge] -- browser -- [headless-link, internal] -- app
                                                                         app also on default network (Caddy, published port)
```

| Boundary | From | To | Controls |
| --- | --- | --- | --- |
| B1 | Internet | Chromium | In-sidecar filtering proxy, route policy, Chromium sandbox, container hardening |
| B2 | Chromium | Sidecar server and host kernel | Chromium sandbox (userns + seccomp-bpf), non-root, caps dropped, seccomp, read-only rootfs, no volumes |
| B3 | App | Sidecar | `headless-link` internal network only, bearer token, JSON body cap |
| B4 | Sidecar | App (response) | Response is hostile: size cap, zod, content type, `finalUrl` re-check, same sanitize pipeline |
| B5 | User | App | Existing auth, rate limit, app-side pre-check (`parseUrl`, `pickAddress`) |

Networks: `headless-link` (`internal: true`, members `app` and `browser` only) and `headless-egress` (normal bridge, `browser` only). The `app` never joins `headless-egress`. `browser` has no volumes, no published ports, no Docker socket.

Fact from S0 (tested): a container on a normal bridge reaches host services via the bridge gateway. Compose networks therefore do not provide "no route to host/LAN". The in-sidecar proxy is the primary control for that, not a defense in depth item. Layer 2 (operator `DOCKER-USER` snippet) is optional and documented only.

## 3. STRIDE-lite

| Threat | Component | Risk | Scenario | Mitigation (layer) |
| --- | --- | --- | --- | --- |
| S | `/render` | Med | A4 calls the sidecar as an open fetch proxy | Internal network, optional-but-recommended bearer token (constant-time compare), no published port |
| S | DNS | High | A1 rebinding: public IP at check, private at connect | Proxy resolves once, checks every address, connects to pinned IP; Chromium never resolves (all traffic via proxy) |
| T | Sidecar response | High | A3 returns huge HTML, scripts, private `finalUrl`, bad JSON | App client caps, zod, `finalUrl` re-validation, existing sanitize/extract pipeline, no direct rendering |
| T | Proxy | High | Request smuggling, CR/LF in Host, absolute-URI forms, CONNECT to port 22 | Strict parser, ports 80/443 only, reject malformed, fail closed |
| R | Jobs | Low | Cannot tell which user triggered a render | `import_job` row records method; sidecar logs host only, never URL or HTML |
| I | Browser to LAN | Crit | Redirect, subresource, WebSocket, WebRTC, prefetch to 127.0.0.1, RFC1918, gateway, metadata | Proxy with shared `ip-guard`, scheme/port/type route policy, WebRTC and prefetch flags, `serviceWorkers: block`; canary listener tests (T9) |
| I | Cross-job state | Med | Cookies, storage, service worker leak between jobs | Fresh incognito context per job, closed in `finally`, no `storageState` |
| I | Error text | Low | Sidecar internals shown to users | App maps sidecar errors to codes, never forwards text |
| D | Sidecar | High | Infinite loop, memory bomb, 1000 subrequests, endless response, fork bomb | 30 s wall-clock kill with process-group SIGKILL (clamped, not configurable above 30 s), byte/request caps, concurrency 1 (503), mem/cpu/pids limits, app semaphore |
| D | Operator host | Med | Heavy render starves a Raspberry Pi | Profile off by default, documented RAM cost, not supported on Pi/HA targets |
| E | Chromium to container | High | Renderer exploit, then sandbox escape | Chromium sandbox ON (no `--no-sandbox`), non-root uid 10001, `cap_drop: ALL` + `SYS_CHROOT`, `no-new-privileges`, read-only rootfs, noexec tmpfs, pinned image |
| E | Container to host | High | Kernel bug reached through userns or syscalls | Custom seccomp limited to Docker default plus 4 syscalls; `mount`, `bpf`, `keyctl`, etc. stay denied; documented residual risk (section 6) |
| E | Sidecar to app | High | A3 uses `headless-link` to reach app:3000 | App is behind session auth and CSRF checks; sidecar holds no credentials; documented that the link network is trusted-ish and `app` does not trust sidecar input |

## 5. Sandbox proposal review (S0 Q-S0-1)

Proposal: non-root uid 10001, `cap_drop: ALL` + `cap_add: [SYS_CHROOT]`, custom seccomp (Docker default plus unconditional `clone`, `clone3`, `unshare`, `setns`), Chromium sandbox on, `no-new-privileges`, in-sidecar proxy IP guard mandatory.

**Verdict: APPROVE WITH CONDITIONS.**

Reasoning:

- Alternatives are worse. `--no-sandbox` removes the only barrier between a renderer exploit and the container; `seccomp=unconfined` or `SYS_ADMIN` are far broader than this. Playwright's stricter profile crashes runc 1.5.2 at start, so it is not usable today.
- `CAP_SYS_CHROOT` alone is narrow: it lets a process `chroot()` inside its own mount view. It does not grant mount, namespace-escape, network, ptrace or raw-socket power. Combined with a non-root user, `no-new-privileges` and a read-only rootfs, I accept it. Any escalation from it needs a separate kernel bug.
- The seccomp delta is the real cost. It re-enables unprivileged user namespace creation inside the container, which exposes extra kernel attack surface (netfilter, namespaced network stack) to a compromised renderer. Mitigations that remain in force: the Docker default still denies `mount`, `umount2`, `pivot_root`, `bpf`, `keyctl`, `add_key`, `ptrace` (kernel dependent), `perf_event_open`, kexec, module loading and the new mount API (`fsopen`, `fsmount`, `fsconfig`), because they need `CAP_SYS_ADMIN` that the container does not have. So a userns inside gives a renderer little beyond namespaced sockets. Accept the residual risk because the sidecar is optional, holds no secrets, has no volumes and sits behind the in-sidecar proxy.
- Two limits of the evidence: amd64 only, and the profile is allowed unconditionally (`clone3` cannot be argument-filtered by seccomp, and the flag-filtered `clone` rules are overridden by the blanket allow).

Conditions (all become acceptance checks in T2/T5/T11):

1. Ship the profile as a reviewed file `docker/browser/seccomp.json`, with a header comment/README naming the exact Docker default profile version it derives from and a script or documented diff showing the delta is exactly `clone, clone3, unshare, setns`. Re-diff when the base is updated.
2. Drop-in rule: no further syscalls are added without a new security review. T11 verifies `mount`, `bpf`, `keyctl`, `ptrace` and `open_by_handle_at` are still denied inside the container (test that they return EPERM).
3. `cap_add` is exactly `SYS_CHROOT`. Never `SYS_ADMIN`, `NET_ADMIN`, `NET_RAW`, `SYS_PTRACE`. T11 checks `docker inspect` for the full capability list.
4. `--no-sandbox` stays forbidden on every architecture. If arm64 or an older runc cannot run with the sandbox, that platform is declared unsupported (Q7), not run unsandboxed.
5. The sidecar must refuse to start (fail closed) if the Chromium sandbox is not active, and the self-check is part of `/healthz` readiness: launch must not pass `--no-sandbox` or `--disable-setuid-sandbox`, and a startup test asserts `chromiumSandbox: true` and non-root uid. A grep gate in CI forbids those flags in `docker/browser/`.
6. Hosts with `user.max_user_namespaces=0` (or unprivileged userns disabled) are unsupported. The sidecar fails to start with a clear log line; `docs/deployment.md` states it (Q-S0-3, accepted by owner).
7. The in-sidecar proxy IP guard is mandatory and cannot be disabled by config. It must reject the Docker bridge gateway and host addresses (covered by the shared block-list since they are RFC1918; T9 adds an explicit gateway case). Do not rely on the compose network layout for this: S0 proved the host is reachable from the egress bridge.
8. The image base and seccomp profile are pinned and re-tested on each target runc version before a release; the runc/Docker versions tested are recorded in `docs/deployment.md`. Playwright's own profile is re-tried when runc is fixed.
9. arm64 is verified by a CI job before arm64 is claimed. QEMU was the original plan, but QEMU user-mode cannot create user namespaces, so the job runs on a native GitHub arm64 runner (green, CI run 42354517591 on `release/v0.3.2`). Hardware (Raspberry Pi, HAOS) remains unverified.

## 6. Residual risks (stated, not mitigated)

1. Chromium zero-day plus kernel bug through the userns surface (section 5). Mitigation is pinning, documented image upgrade path, optional profile.
2. A malicious page can exfiltrate to the public internet or use the operator's IP for requests that pass the guard. Accepted: the sidecar holds nothing sensitive; rate limits and concurrency 1 bound the volume.
3. HTTP/3 or other non-proxied protocols: if a bypass of the proxy is found by the pen test (T12 P2), the network layer does not stop it because the egress bridge reaches the LAN. This is why the optional `DOCKER-USER` snippet is recommended for hosts with a sensitive LAN.
4. Loopback canary evidence only (S0); no external packet capture yet. T9 and T12 must re-run with an external canary host.
5. `HEADLESS_TOKEN` is optional; without it any container on `headless-link` can use `/render`. Only `app` and `browser` are on that network by design.
6. Resource exhaustion is bounded, not prevented: a 2 GB cap (raised from 1 GB) on a 1-2 GB VPS can still hurt the host without swap.
7. arm64 and a heavy real page memory number are unmeasured as of S0.

## 7. Operator hardening (documented in `docs/deployment.md`, T5)

- Optional `DOCKER-USER` chain rule dropping traffic from the `headless-egress` subnet to RFC1918, link-local, loopback and the host (snippet in the doc; pen test checks it, the app does not depend on it).
- Generate `HEADLESS_TOKEN` next to `SESSION_SECRET`.
- Keep the profile off on Raspberry Pi and Home Assistant targets and on hosts with unprivileged userns disabled.
- Upgrade path: bump the pinned Playwright tag and digest, rebuild, re-run T9.

## 8. AppSec review (security-appsec-engineer, 2026-11-06)

**Verdict: APPROVE WITH CONDITIONS.** T3 may start. Layering, boundaries and the sandbox verdict (section 5) hold. The gaps below are requirements on T2/T3/T4/T6/T9, not redesigns. The two most important: Chromium bypasses a proxy for loopback by default, and QUIC/UDP/WebRTC/DNS are not covered by an HTTP proxy at all.

| # | Gap | Required control | Task | Test |
| --- | --- | --- | --- | --- |
| R1 | Implicit loopback proxy bypass: Chromium sends `localhost`, `127.0.0.1`, `[::1]` direct, which would reach the sidecar's own `/render` (token-less recursion) and any local listener | Launch with `--proxy-bypass-list=<-loopback>` so loopback also goes through the proxy and is rejected by the guard; no `--remote-debugging-port` (pipe transport only) | T3, T4 | C12 |
| R2 | QUIC/UDP/WebRTC/DNS are not proxied, and the egress bridge allows UDP to the LAN | `--disable-quic`, `--disable-features=WebRtcHideLocalIpsWithMdns,AsyncDns,DnsOverHttps` plus `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`, `--host-resolver-rules="MAP * ~NOTFOUND"` (Chromium never resolves; proxy does it), `--disable-background-networking`, `--disable-component-update`, `--no-pings`. Launch args are asserted by a unit test (exact list). Residual: UDP cannot be tested hermetically for LAN targets, so T12 P2 must use an external UDP/QUIC canary and the `DOCKER-USER` snippet is recommended where the LAN is sensitive | T3, T4, T12 | C13, P2 |
| R3 | WebSocket: `context.route` does not see WebSocket traffic; `wss://` is an opaque CONNECT tunnel | Enforce at the proxy: refuse any plain-HTTP request with `Upgrade`/`Connection: upgrade`; CONNECT only to the validated pinned address on 443. | R4 | DNS rebinding: pinning must survive redirects, subresources and the connect-retry from T14 | Per-job `Map<host, validatedAddrs>` filled by one `lookup({all:true})`; every later connection to that host (any hop, any resource, any tunnel) uses only that set, retry only within it; cache discarded at job end. Compare via `timingSafeEqual` on equal-length digests of both sides. `Authorization: Bearer` only. Token never logged, never in error bodies, and removed from the environment passed to Chromium (explicit `env` on launch). `/healthz` is the only unauthenticated route and returns no version or config detail | T2, T5, T6 | C10 (extended), C17 |

Smaller requirements:

- Disable `--proxy-server` fallback: if the proxy listener is down, Chromium must fail, never go direct (`--proxy-server` set, no `direct://`, `--no-proxy-auto-detect`-equivalent); T9 kills the proxy mid-job and expects `failed` with zero direct connections.
- Sidecar logs host only (as designed); also never log headers or the token. Add a grep gate: no `console.log(req.headers`/`url` in `docker/browser/src/`.
- Rate limit for A2 stays in the app (existing import limiter + semaphore); T6 must apply it before the sidecar call, not after.
- Residual risk 3 is upgraded: QUIC/UDP/DNS bypass is a flag-level control (R2) and not network-enforced; document in `docs/deployment.md` that sensitive-LAN hosts should apply the `DOCKER-USER` snippet.

New test cases (added to T9, numbered after C11): C12 loopback and `localhost` via proxy bypass list (including `http://127.0.0.1:<sidecar port>/render`); C13 QUIC/UDP/WebRTC/DNS: launch-arg assertion plus an `RTCPeerConnection`/`fetch` to a UDP/HTTP3 canary with zero packets; C14 WebSocket and `wss` to a blocked address and `Upgrade` on plain HTTP refused; C15 rebinding across redirect hops and subresources with one resolver call per host asserted, and Docker-name (`app`, `browser`) resolution rejected; C16 userinfo URLs at every redirect hop and the 6th redirect aborted; C17 sidecar refuses to start without token, token absent from Chromium env and logs; C18 oversized DOM, gzip bomb, and app-side streaming abort on an endless sidecar response; C19 proxy parsing: CL+TE smuggling, duplicate CL, Host mismatch, origin-form, CR/LF in target, obs-fold; C20 CONNECT to port 22/80/0443, userinfo, tunnel and byte caps, socket error does not crash the proxy, proxy-down means fail-closed.
