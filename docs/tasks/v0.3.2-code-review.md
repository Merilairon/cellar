# v0.3.2 code review (slice 03c, headless sidecar)

Scope: `git diff v0.3.1..HEAD` on `release/v0.3.2` (114 files, about 12k added lines, 27 commits)
against `v0.3.2-tasklist.md`, `v0.3.2-threat-model.md`, `v0.3.2-security-checkpoint.md` and
`v0.3.2-pentest.md`. Read-only review; no code was changed.

Evidence base: I read in full `headless-client.ts`, the `pipeline.ts`, `safe-fetch.ts`,
`service.ts`, `import-jobs.ts` and `env.ts` diffs, migration `0004` and its test, the sidecar
`server.ts`, `config.ts`, `render.ts`, `supervisor.ts`, `policy.ts`, `sandbox.ts`, `browser.ts`,
`ip-guard.ts` and the first third of `proxy.ts`, `docker-compose.yml`, the Dockerfile, `run.sh`,
the CI workflow, the import dialog and review form diffs, and the new docs. I read the pipeline,
client, prune and compose tests. I did NOT run any suite, Docker, Chromium or CI, and I did not
review `proxy.ts` past the header parsing, the rest of `proxy.test.ts`/`proxy-abuse.test.ts`, the
seccomp JSON, or the mapper fixtures. Conclusions about those parts rest on the threat-model and
pentest documents, which I did not independently re-verify.

## Summary

This is careful, defensive work. The app side treats the sidecar as an untrusted peer: wire cap
while streaming, content-type and content-encoding checks, zod envelope, fixed error mapping,
`finalUrl` re-validated against the SSRF policy, token and HTML never logged, a single in-process
render slot with no queue. The sidecar fails closed (no token, no sandbox, root uid and a bad
`BIND_ADDR` all refuse to start), strips the token from Chromium's environment, forces Chromium
through a per-job pinning proxy with `<-loopback>`, and the seccomp profile is the Docker default
plus one proven delta. The pipeline refactor into a shared `processHtml` keeps static and headless
from diverging, and the trigger table is tested case by case. Migration `0004` is the standard
table rebuild, tested on a populated v0.3.1-shaped database. Prune confines unlink targets to
`<dir>/<26 chars>.html` and has good traversal tests. The docs are unusually honest about what was
not run (arm64, CI runner, real pages).

The weak spots are configuration coherence (the app accepts a state the sidecar cannot serve),
one retention claim that is false for a supported upgrade path, tests that pass without exercising
what their name says, and a few doc sentences that say more than the code does. No security or
data-loss blocker found in the parts I read.

Fix status: see [Fix status](#fix-status) at the end.

Counts: 0 blockers, 3 major, 8 minor, 6 nits.

## Blockers

## Major

### M1. `HEADLESS_URL` without `HEADLESS_TOKEN` is accepted by the app but can never work
`src/lib/env.ts:103-110`, `src/lib/import/headless-client.ts:213`, `docker-compose.yml` (browser
`HEADLESS_TOKEN: ${HEADLESS_TOKEN:-}`).

Scenario: operator copies `HEADLESS_URL=http://browser:3001` from the README, forgets or blanks the
token. `parseEnv` passes (each field is validated alone). Compose starts `browser`, which exits with
`HEADLESS_TOKEN is required`. The app sees `isHeadlessEnabled` true, so every JS-only or 403 import
runs the static fetch, then tries the sidecar, then fails with `headless_unavailable`, with only a
generic log line. The operator is told nothing at startup. The reverse case (token set to a value
the sidecar rejects, see m2) fails the same silent way.

Fix: add a cross-field refine on the schema: `HEADLESS_URL` set requires `HEADLESS_TOKEN`
(unless the operator-only escape hatch is mirrored). That makes the "fail at startup" contract
symmetrical with the sidecar. Add the case to `env.test.ts` (currently only the 32-char floor is
covered, not presence).

### M2. Pruning silently orphans raw HTML for anyone with a custom `UPLOADS_DIR`
`src/lib/env.ts:98,123` (`RAW_HTML_DIR` default), `src/lib/db/import-jobs.ts:88-95,155`,
`docs/deployment.md`, `README.md` (retention bullets).

v0.3.0/v0.3.1 wrote raw HTML to `dirname(UPLOADS_DIR)/import-raw`. The new default is
`dirname(DATABASE_PATH)/import-raw`. The two differ whenever `UPLOADS_DIR` is not a sibling of the
DB file (the `.env.example` itself suggests `./data/uploads`, and `UPLOADS_DIR` is a documented
override). After upgrade: old files live in the old directory, `confinedRawHtmlPath` refuses them
(wrong dirname), and `pruneImportJobs` deletes the row anyway. The file is now unreferenced and
never deleted, while the docs say raw HTML is "pruned with its job". For a feature whose point is
bounded retention of fetched pages (privacy), this is a false claim on a supported config.

Fix: default `RAW_HTML_DIR` to `join(dirname(UPLOADS_DIR), 'import-raw')` when `UPLOADS_DIR` is
set (the v0.3.0 behaviour), or keep the new default and, in prune, treat a stored path that is
valid-by-name but outside the dir as "log and leave the row" instead of deleting the row. Document
the move either way. Add a test with `UPLOADS_DIR` and `DATABASE_PATH` in different parents.

### M3. Tests named for a property they do not exercise (CAS, 401/429, wire contract)
Three independent cases; I group them because the failure mode is the same: a green check that
would stay green if the code were wrong.

1. `src/lib/db/import-prune.test.ts:153` "skips a row changed since it was selected (CAS)". The test
   updates the row to `saved` with `updatedAt: FRESH` before calling `prune()`. The initial SELECT
   (`updated_at < cutoff`) already excludes it, so the compare-and-set in `import-jobs.ts:142-152`
   is never reached. Deleting the CAS entirely keeps this test green. Needed: change the row
   between the SELECT and the write (call the inner step with a stale row snapshot, or make the
   selection injectable), or drop the claim from the doc comment ("so a job saved concurrently is
   skipped").
2. `src/lib/import/pipeline.test.ts` "static 403 (and 429, 401) + headless ok": the loop runs three
   times with the identical `new ImportError('blocked')`. Nothing distinguishes 401, 403 and 429;
   the mapping lives in `safe-fetch`, so this test cannot catch a regression in it, yet the name and
   the README ("403/429") suggest coverage.
3. App client and real sidecar are never run together. `headless-client.test.ts` talks to a
   hand-written fake; the e2e stub (`tests/e2e/stub-sidecar.mjs`) does not check the token, the
   content-type or the body shape, and returns 500 for unknown URLs where the real server returns
   502/503 with other codes. The CI `headless` job curls the real server but never through
   `renderPage`. A drift between `server.ts` (envelope, status codes, `Content-Type`) and
   `okSchema`/`errSchema` would pass every suite.
   Fix: one test (vitest with `BROWSER_DOCKER_TESTS`-style opt-in, or a CI step) that starts
   `createSidecar` from `docker/browser/src/server.ts` with a stub `Renderer` and runs the real
   `renderPage` against it, including a wrong token and a 413.

## Minor

### m1. Static `no_recipe` after an empty Recipe node: docs say headless runs, code says no
`README.md:75`, `src/lib/import/pipeline.ts:134-139`. The README says headless runs "when the static
step ends in `no_recipe`, 403 or 429". The code runs it only when there is no Recipe node at all;
a node that normalizes to nothing returns `no_recipe` without a render (and a test pins that).
Also `blocked` includes 401. Reword to "no Recipe data at all in the static page, or 401/403/429".

### m2. Token charset rule differs between app and sidecar
`src/lib/env.ts:107-110` (length only) vs `docker/browser/src/config.ts:41`
(`^[A-Za-z0-9+/_=-]{32,}$`). A 40-character token containing `!`, `.` or a space is accepted by the
app and makes the sidecar exit at start. Commit `1d224a0` aligned length only. Use the same regex
in `env.ts` (comment says "same as the sidecar"; make it true).

### m3. Client timeout below 30 s leaves an orphan render holding the sidecar slot
`src/lib/env.ts:111` (`HEADLESS_TIMEOUT_MS` min 1), `docker/browser/src/server.ts:158-170`.
The sidecar never watches `req`/`res` close, so when the app aborts (say `HEADLESS_TIMEOUT_MS=5000`)
the render runs to the 30 s kill with `active` held. Every import in that window gets 503, which the
client maps to `headless_unavailable`. Either enforce a floor above the sidecar's budget (or document
"keep at 35000") or cancel the job on `res.on('close')`.

### m4. Cold browser (re)launch is outside the sidecar's 30 s budget
`docker/browser/src/supervisor.ts:103-108`. `ensureBrowser()` runs before the deadline timer starts,
and after every kill the next job pays a launch. Worst case is 30 s + hard-kill wait (up to 2.5 s) +
launch against a 35 s client cap, and a launch that hangs holds `active` forever with no timer.
Start the deadline before `ensureBrowser` or bound the launch separately.

### m5. One user's render makes every other user's headless attempt look like "not available"
`src/lib/import/headless-client.ts:152-153`, `pipeline.ts:156-160`. The slot is process-wide with no
queue by design (G12), but a `LimiterBusyError` becomes `headless_unavailable`, rendered to the user
as "headless is not available, paste instead", and consumes one of their 20 hourly imports. Consider a
distinct busy outcome (retry hint) or a short bounded wait; at minimum give the dialog text for the
busy case ("try again in a moment") rather than implying a setup problem.

### m6. POST and GET disagree about `headless` for a failed headless job
`pipeline.ts:156-160` returns `headless: null` for a sidecar `blocked`/`timeout`/`too_large`/
`private_address`, so the dialog omits "we tried a browser". `service.ts:116-122` derives `used` from
`job.method === 'headless'`, which is true for the same persisted failure. Same job, two answers,
depending on the endpoint. Decide one rule (a render was attempted means `used`) and apply it in
both places.

### m7. Unrelated behavior changes ride in the slice
`src/lib/import/safe-fetch.ts` (multi-address connect fallback, reworked abort/listener handling in
the hot SSRF path) and `src/app/api/photos/[id]/route.ts` (`Cache-Control` change, commit `db5de1b`,
"m5" of an earlier review). Each is defensible and tested, but they touch security-sensitive code
unrelated to headless and are easy to miss in a 114-file diff. Not asking for a revert; the release
notes and the security checkpoint should list them, and the safe-fetch change deserves its own line
in the threat model (all candidate addresses are validated before the first connect, which is the
property that makes the fallback safe).

### m8. Migration `0004`: the PRAGMA lines are no-ops and safety depends on a fact nobody asserts
`drizzle/0004_import_headless_error.sql:1,24`. Drizzle's migrator runs the file inside a
transaction, where `PRAGMA foreign_keys` is ignored. The rebuild is safe only because no table has
an FK that points at `import_job` (a `DROP TABLE` with enforcement on does an implicit delete and
would cascade). Today that is true and the test checks `foreign_key_check`. Add a one-line comment in
the SQL (or a test asserting no `REFERENCES import_job` in `sqlite_master`) so the next person who
copies this pattern for a parent table does not lose child rows.

## Nits

- n1. `docker/browser/src/policy.ts:59,99,121`: `redirectsExceeded` is set but never read by
  `render.ts`; the cap works only because the page is closed and the navigation then fails as a
  generic `failed`. Read the flag and return a deliberate code.
- n2. `docker/browser/src/ip-guard.ts` is a byte-identical copy of the app's. A drift test exists,
  which is good; a shared source with a build copy step would remove the failure class.
- n3. `playwright-core` is exact `1.64.1` in the sidecar and `^1.64.1` in the app. The unit tests in
  `npm run test:browser` resolve `playwright-core` from the app's tree, not the sidecar lockfile, so
  they cannot detect a skew. The deployment doc asks for equality; add a one-line check.
- n4. App sends the raw entered URL (up to `MAX_IMPORT_URL` 2048) but the sidecar rejects over 2000
  characters (400, shown as `headless_unavailable`) and a body over 2048 bytes (413, shown as
  `too_large`, wrong for a long non-ASCII URL). Align the limits or send the normalized href.
- n5. Docs: `README.md:82` and `docs/deployment.md` tell people "if you already set a
  `HEADLESS_TOKEN`, it must be 32+" and "it was 16 before". `HEADLESS_TOKEN` does not exist in
  v0.3.1 (`git show v0.3.1:src/lib/env.ts`). It was only 16 in an unreleased commit. Remove the
  upgrade warning. Also idle memory is "about 106 MiB" in the README and carryover but "about 108 MB"
  in `deployment.md`.
- n6. CI: `dorny/paths-filter@v3` and the other actions are pinned by tag, not SHA, in a repo whose
  sidecar is otherwise pinned by digest; `HEADLESS_URL` accepts any `http://` host, so a typo'd
  public host would send the bearer token in clear text (operator config, documented as internal
  only, but a one-line warning in the env table would help).

## What I could not check, and what the docs claim

- `docs/tasks/v0.3.2-carryover.md` is accurate about not having run the `arm64` job, the runner
  sysctl step, the 1 GiB abuse run, real pages and a compose volume upgrade. I agree with every row
  of its "not verified" table; the README's "arm64: not verified" matches. I found no place where a
  doc claims arm64 or CI-runner results.
- "39/39 locally (16 + 10 + 13)": the static count of `test(` in `syscalls.docker.test.ts` is 5, with
  the rest generated by a loop over `CALLS` (two cases each). Plausible, not independently counted.
- The deployment doc's claim that compose `seccomp=./docker/browser/seccomp.json` resolves relative
  to the project directory depends on the Compose version; the carryover records Compose 5.7.0 only.
  `compose.test.ts` is a line-regex over the YAML, so it checks the spelling, not that Compose
  actually loads the profile. A `docker compose config` or a live `docker inspect` assertion in the
  `headless` CI job would close this.

## Good things worth keeping

- `headless-client.ts`: cap-while-streaming, `destroy` on every early exit, deadline raced against
  the run with abort propagated, and the `finalUrl` check running before status mapping.
- `processHtml` as the single path for static and headless, with `noRecipeNode` as an explicit
  signal instead of string matching on the error.
- Sidecar `loadConfig`: the 30 s ceiling is clamped in code, `BIND_ADDR` must be an IP literal,
  token compare hashes both sides, `browserEnv` removes the token from Chromium's environment.
- The CI grep gate that bans sandbox-weakening flags across the whole directory (built from parts so
  the gate does not trip on itself), and the honest "emulated, not hardware" wording for arm64.
- `confinedRawHtmlPath` plus its traversal tests.
