## 1. Photos (requirement 6)

### 1.1 Cover on `RecipeCard` and in lists

- The card gains a media area **above** the text, full card width, fixed `aspect-ratio: 4 / 3`, `object-fit: cover`, `border-radius` matching the card's top corners, `loading="lazy"`, `decoding="async"`. `src="/api/photos/{cover_photo_id}?size=thumb"`. Plain `<img>` (G13). The `<img>` carries `width`/`height` from the thumb (so the browser reserves space before CSS loads); CSS ratio wins, so there is no layout shift and no crop surprise.
- **No cover**: the same 4:3 box shows the placeholder (a plate-and-fork line icon, `--rg-muted` on `--rg-empty`, `aria-hidden`, no text). The box is always rendered, so a list mixing covered and uncovered recipes has even card heights. This is the designed placeholder T8 requires.
- Alt text `""` (F4); the whole card is still one link whose accessible name is the title (unchanged).
- Failure (404, 401, network): `onError` swaps in the placeholder. No broken-image icon.
- Rating line on the card sits under the title (section 3.4).

### 1.2 Recipe page: hero and gallery

- **Hero** under the title block: shows the cover with the full file (`/api/photos/{id}`). Phone: full width, `aspect-ratio: 16 / 9`, `object-fit: cover`. 768: full width of the container, `16 / 9`, `max-height: 360px`. 1280: sits **right of** the title, meta and rating at 320 x 240 (4:3), so the grid stays near the top of the page.
- **Gallery strip** (only when the recipe has 2 or more photos): thumbnails 72 x 54 px (phone, 44 px high tap box minimum is met by padding to 44) in a wrapping row under the hero. Each thumbnail is a `<button aria-pressed>` that swaps the hero to that photo. No lightbox, no swipe (out of scope). The cover is the initial hero. Focus ring `--rg-focus`.
- **No photos, reader**: nothing is rendered (no empty hero block).
- **No photos, owner or admin**: a dashed-border prompt, 4:3 at phone and 1280, text "No photo yet" and an **Add a photo** button (section 1.3).

### 1.3 Where upload and management live

Owner or admin only (`recipe.can_edit`). Readers see photos and no controls.

- **Entry**: an **Edit photos** button in the recipe action row (after Edit) and the **Add a photo** button in the empty prompt. Both toggle the **photo manager**, an inline panel under the hero/gallery (`aria-expanded` / `aria-controls`, focus stays on the toggle; not a dialog, so the page behind stays usable). Hidden while the grid editor is open (the editor replaces the read view).
- **Manager contents**: a heading "Photos ({n} of 10)"; a responsive grid of the photos (2 columns at 375, 3 at 768, 5 at 1280), each tile 4:3 with the image, a text badge **Cover** on the cover (icon + word, not colour alone), and two buttons under the tile: **Make cover** (omitted on the cover; replaced by the badge) and **Delete**; at the top the **Add photos** control.

```
375                                    1280
+----------------------------+        +----------------------------------------------------------+
| Photos (3 of 10)  [Done]   |        | Photos (3 of 10)                       [Add photos] [Done]|
| [Add photos]               |        | +------+ +------+ +------+                                |
| +--------+  +--------+     |        | |img   | |img   | |img   |                                |
| |img     |  |img     |     |        | |COVER | |      | |      |                                |
| |[Cover] |  |        |     |        | +------+ +------+ +------+                                |
| +--------+  +--------+     |        | [Delete] [Make cover][Delete] [Make cover][Delete]        |
| [Delete]    [Make cover]   |        +----------------------------------------------------------+
|             [Delete]       |
+----------------------------+
```

- **Add photos**: a label styled as `btn` around `<input type="file" accept="image/jpeg,image/png,image/webp" multiple>`. **No `capture` attribute**: on a phone the browser offers camera or library. The input is visually hidden but keyboard focusable; the label shows the focus ring (`:focus-within`). Enter or Space opens the picker.
- **Client pre-check** (speed only; the server is authoritative): MIME type or extension in the list and size <= 10 MiB; otherwise that file is listed as an error without a request. A renamed SVG passes the pre-check, is rejected by the server, and is shown with the server's message.
- **Upload sequence**: files go one at a time (the server decodes one image at a time anyway). Progress list under the control, one row per file: file name (text), a native `<progress>` with the percentage as text ("Uploading 2 of 3: 45 %"), then "Added" or the error. Uploads use a request that reports progress (T8 chooses `XMLHttpRequest` or fetch streams). Inputs and the Add button stay enabled for other actions; a second pick while uploading appends to the queue.
- **Success**: the tile appears, the first photo of a recipe becomes the cover and says so ("Added. It is now the cover."), the hero updates. Polite status "Photo added." once per file, or "3 photos added." once when a batch ends.
- **Error rows** (text plus an "x" icon and the word "Problem"; stable codes from T4; if a code name differs the key follows the code):

| Cause | Message (en) | Retry control |
| --- | --- | --- |
| Pre-check or 413 | "{name} is larger than 10 MB." | none |
| Pre-check, 415 or `unsupported_type` | "{name} is not a supported image. Use JPEG, PNG or WebP." | none |
| `invalid_image`, 422 | "{name} could not be read as an image." | none |
| `too_many_pixels` | "{name} has too many pixels. Resize it and try again." | none |
| `photo_limit` | "This recipe already has 10 photos. Delete one to add another." | none |
| 503 / 429 | "The server is busy. Try again in a moment." | **Try again** button (uses `Retry-After` for the wait text) |
| 401 / 403 / 404 | "You can no longer edit this recipe." | none |
| Network / 5xx | "Could not upload {name}. Check your connection." | **Try again** |

  Errors stay in the list until dismissed (**Dismiss** button per row, or all cleared when the manager closes). The list region is the single polite status for the manager; a row's error is also announced once when it appears (`role="status"`, not `alert`).
- **Limit reached (10)**: **Add photos** becomes `aria-disabled="true"` (stays focusable) with `aria-describedby` text "This recipe has 10 photos, the most it can have. Delete one to add another." Pressing it announces that text.
- **Set cover**: **Make cover** applies immediately (one request, optimistic badge swap, rollback with an error row on failure). Announce "{Photo n of m} is now the cover." The hero updates.
- **Delete**: **Delete** replaces the tile's buttons with an inline confirm: "Delete this photo? This cannot be undone." **[Delete] [Keep]**; focus goes to **Keep**; Escape = Keep. On Delete the tile is removed, focus moves to the next tile's first button (previous when last, **Add photos** when none), announce "Photo deleted." If the deleted photo was the cover, the next one is promoted (server rule G11) and the badge moves; announce adds "{Photo n} is now the cover." If it was the last photo, the owner prompt returns.
- **Done** closes the manager and returns focus to the toggle.

### 1.4 Keyboard model (photos)

Tab order: Edit photos toggle (action row) -> inside the open manager: Add photos, per-tile **Make cover** then **Delete** in DOM order, Done. Gallery thumbnails (readers and owners) are buttons in the tab order after the hero. No roving tabindex (at most 10 tiles x 2 buttons = 20 stops, bounded). Enter/Space activates; Escape cancels an inline delete confirm.

### 1.5 Missing or forbidden image

Image 404/401/403 or load error: the `<img>` is replaced by the placeholder box. On the recipe page hero the placeholder carries visible text "Photo unavailable" and a **Reload** is not offered (the next page load retries). A photo deleted by someone else while the page is open behaves the same. A reader never sees a message that distinguishes "forbidden" from "missing" (authorization uses 404).

### 1.6 Layout shift and performance

Every image box has a reserved ratio (card 4:3, hero 16:9 or 4:3, tile 4:3, thumb 4:3). Below-the-fold images `loading="lazy"`. The hero is the only image allowed `fetchpriority="high"`. No `next/image` (G13).

### 1.7 Import review cover preview [STRETCH, cut line 1]

In the import review a 4:3 preview shows the cover that `import_cover` will save, with the caption "Cover from the page". When none was found: dashed placeholder and text "No cover image found." No controls (the owner can replace it on the recipe page afterwards). `alt=""`, the caption carries the meaning.

### 1.8 Reduced motion and dark mode

No transitions on swapping hero or badge (an instant swap). Progress bar has no animation beyond value change. Tokens in section 9.

### 1.9 Alt text policy (F4)

Card: `alt=""`. Hero: `Photo of {title}`. Gallery thumbnail and manager tile: `Photo {n} of {total}` plus, on the cover, the visible word "Cover" inside the tile (read by screen readers as text). Placeholder icons are `aria-hidden`. There is no alt editing in 4c.

## 2. Notes (requirement 7)

### 2.1 Placement and anatomy

A **Notes** section (`h2`) sits **after the recipe grid / list and before the page footer**, so cooking first, notes second. It is inside the same region at every width (max readable line length: the section is capped at `max-w-prose` = about 65ch even at 1280, left aligned).

```
375                                 1280
+-----------------------------+     +------------------------------------------+
| Notes (3)                   |     | Notes (3)                                |
| +-------------------------+ |     | +--------------------------------------+ |
| | Marie        [Shared]   | |     | | Marie  Nov 3  [Shared]               | |
| | 3 Nov                   | |     | | Less sugar next time, it was sweet.  | |
| | Less sugar next time.   | |     | +--------------------------------------+ |
| +-------------------------+ |     | | You  Nov 5  [Only you]    Edit Delete| |
| | You        [Only you]   | |     | | Use the small tin.                   | |
| | 5 Nov                   | |     | +--------------------------------------+ |
| | Use the small tin.      | |     | Add a note                               |
| | [Edit] [Delete]         | |     | [textarea                       ]        |
| +-------------------------+ |     | 0 / 4000      Who can see this note:     |
| Add a note                  |     | (o) Only me  ( ) Everyone with access    |
| [textarea              ]    |     |                          [Add note]      |
| 0 / 4000                    |     +------------------------------------------+
| Who can see this note:      |
| (o) Only me                 |
| ( ) Everyone with access    |
| [Add note]                  |
+-----------------------------+
```

- **Item** (`<li>` in a `<ul aria-label="Notes">`): header row with author, date, and a marker; body below; action buttons for the author.
- **Marker, never colour alone**: private = lock icon + the word "Only you" in a **dashed**-border chip (`--rg-banner` fill); shared = people icon + the word "Shared" in a **solid**-border chip. For another user's shared note the header reads "{Name}" + "Shared"; for your own shared note "You" + "Shared". A reader never sees another user's private note (API rule), so "Only you" always means the viewer.
- **Order**: oldest first by `created_at, id` (the API order). The add form is **below** the list, so a new note appears above it. Heading count "Notes (3)" counts what the viewer can see.
- **Body**: `white-space: pre-wrap`, `overflow-wrap: anywhere`, plain text node. No auto-linking, no markdown, markup shown literally. No clamp; long notes just wrap (the cap is 4000 characters).
- **Dates** via `useFormatter` (`dateStyle: 'medium'`), as the card does.

### 2.2 Add

- `<textarea>` with a visible label "Add a note" (`<label>`), `rows=3`, auto-grow to at most 10 rows, `maxLength` not set (the counter and error handle the cap so a paste is never silently truncated).
- **Counter** under the field: "{n} / 4000", visible text. It is not live. At 3800, 3950 and 4000 characters a single polite announcement ("200 characters left" / "50 characters left" / "Limit reached") fires once per threshold.
- **Visibility** control: a `fieldset` with legend "Who can see this note" and two native radios: **Only me** (default, helper "Nobody else can see or search this note.") and **Everyone who can see this recipe** (helper "Shown with your name. Found by search."). Default is private (safer).
- **Add note** (`btnPrimary`): `aria-disabled` + `aria-describedby` reason when the text is empty/whitespace ("Write something first") or over 4000 ("{n} characters too many"). Pressing a disabled button announces the reason.
- **Success**: the note appears at the end of the list; textarea cleared; focus stays in the textarea (the user may add another); polite "Note added." **Errors** (inline, `FieldError` pattern, `aria-invalid` on the textarea): `note_limit` "You have 200 notes on this recipe, the most allowed."; 422 empty "Write something before saving."; 422 too long; 401/403/404 "You can no longer add notes to this recipe."; network "Could not save the note. Your text is still here. Try again." The typed text is never cleared on failure. No `localStorage` draft.
- **Who may add**: any signed-in reader, including on a read-only `users` recipe and on the viewer's own recipe (Q3). No role-based hiding.

### 2.3 Edit and delete

- **Edit** (author only): the item's body becomes a textarea prefilled with the text, plus the same visibility radios and **Save** / **Cancel**. Focus goes to the textarea with the caret at the end. Escape = Cancel. Save returns focus to that note's **Edit** button; Cancel the same. Changing shared -> private shows helper "Others will no longer see or find this note." Changing private -> shared shows "Others will see this note with your name."
- **Delete**: author, and the **recipe owner/admin on other users' shared notes** (Q3; they never get Edit and never see private notes). **Delete** swaps the item's buttons for an inline confirm "Delete this note? This cannot be undone." **[Delete] [Keep]**, focus on **Keep**, Escape = Keep. After deletion focus goes to the next item's first button, else the previous, else the add textarea; polite "Note deleted."
- A note belonging to a deleted account is gone (Q14 cascade); nothing to design.

### 2.4 Empty state

"No notes yet. Notes you mark **Only me** stay private." Shown in place of the list; the add form is still shown. For a reader on a read-only recipe the same text (they can add notes).

### 2.5 Keyboard path (notes)

Tab: add textarea -> radios (arrow keys inside the group; one tab stop) -> Add note; list items: Edit, Delete per own note in DOM order. Enter in the textarea inserts a newline (never submits); **Ctrl/Cmd+Enter** submits (hint in the helper text under the counter: "Ctrl+Enter to add"). Escape cancels edit or confirm.

## 3. Ratings (requirement 8)

### 3.1 The star control as an accessible radio group

- Markup: `role="radiogroup"` on a wrapper with `aria-labelledby` pointing at the text "Your rating". Inside, **five native `<input type="radio" name="rating-{recipeId}">`**, each visually hidden but focusable, each inside a `<label>` that draws the star. Radio semantics give the right behaviour for free: one tab stop, **Left/Up arrow = previous, Right/Down arrow = next, and the arrow selects** (this is the platform behaviour), Tab leaves the group.
- Each radio's accessible name is `"{n} of 5 stars"` (`aria-label`, key `rating.star`), so a screen reader says "3 of 5 stars, radio button, 3 of 5". The group name is "Your rating".
- **Visible text** next to the stars, always: "Your rating: 3 of 5" or "Not rated yet". Stars are not the only carrier of the value.
- **Shape not colour**: filled star = solid glyph with `--md-star`; empty star = outline only in `--rg-muted`. Contrast: filled glyph >= 3:1 against the surface, outline >= 3:1.
- **Targets**: each star's label is 44 x 44 px at every width (visual glyph 28 px); five stars = 220 px, which fits 343. Focus ring (3 px `--rg-focus`, offset 2 px) is drawn on the 44 px label of the focused star (`:has(input:focus-visible)`).
- **Pointer preview**: hover (fine pointer only) fills stars up to the hovered one; touch has no preview.
- **Clear**: native radios cannot be unset, so a text button **Clear my rating** appears after the stars **only when the viewer has a rating** (omitted otherwise, not disabled). Clicking the selected star again does nothing.
- **Saving**: each selection sends `PUT .../rating` after a 400 ms debounce (arrow-key sweeping 1 -> 4 sends once, for 4), optimistic: stars and text update at once; on failure the previous value is restored and the polite status says "Could not save your rating." Success is announced once, coalesced: "Your rating is 4 of 5 stars." / "Your rating was cleared."
- **Who**: any reader (including the owner on their own recipe, Q3). Not rendered for the unauthenticated case (the page requires sign-in).
- **Keyboard path**: Tab into the group (lands on the checked star, or the first when none), arrows change and save, Tab to **Clear my rating**, Enter/Space activates. Home/End are not special.

### 3.2 Average and count on the recipe page

`RatingSummary` is one text string with a decorative star row: **"4.3 from 5 ratings"**, "4.0 from 1 rating", or **"No ratings yet"**. The five-star row beside it is `aria-hidden` and fills fractionally (visual only). Average is shown to one decimal (G8) and is read-only for everybody; the viewer's own control (3.1) sits under it with the label "Your rating". The summary is a single text node (`aria-label` is not needed). The average and count update after the viewer saves (the response carries the new aggregate).

### 3.3 Read-only for non-raters

Every signed-in reader can rate, so there is no "cannot rate" state in 4c; the only read-only rendering is the average itself (cards, summary, and any future guest view). Individual raters are never shown.

### 3.4 Average on cards

Under the title: a small star glyph (decorative) + "4.3" + "(5)" with an `aria-label` equal to the full text "Average rating 4.3 of 5 from 5 ratings". Not rated: muted text "Not rated yet" (keeps the card rows aligned). No stars row on cards (space). Position: between the title and the tag chips; on the 4:3 media area nothing is overlaid.

### 3.5 `min_rating` filter on `/recipes`

- Placed in the same filter area as `TagFilter`, as its own labelled group (`role="group"`, label "Minimum rating"): single-select **chips** (`aria-pressed`, same chip style as tag chips): **Any**, **2+**, **3+**, **4+**, **5+**. Visible text "4+ stars"; accessible name "4 stars or more". "Any" is pressed when `min_rating` is absent. `min_rating=1` from a pasted URL is valid: no chip is pressed, and the active-filter chip (below) shows "1+ stars".
- Phone: chips wrap onto a second row under the tag chips; 44 px targets. 768 and 1280: same row as the tag filter when it fits, otherwise wrapping.
- **Active filter chip**: when `min_rating` is set a removable chip "4+ stars  x" appears with the other active filters (button, "Remove minimum rating filter"), focus goes to the filter group's **Any** chip after removal.
- Behaviour: pressing a chip updates the URL (`?min_rating=4`), combines with `q`, `tag`, `author`; shareable. Helper text under the group while active: "Recipes nobody has rated are hidden." (key `rating.filter.unratedHidden`).
- **Empty results** (uses the existing `search.noResults*` pattern): title "No matches" + "No recipes with an average of {n} stars or more match. Lower the minimum rating or clear the filters." + the existing **Clear filters** button.
- Ranking with `q` is not affected (G9); results ordering is unchanged.

## 6. Cook mode (requirement 9; G14, G15) [CUT 2]

### 6.1 Entry and exit

- **Cook** button (`btn`, icon + text) in the recipe action row, **visible to every reader**, placed before Edit. `aria-haspopup="dialog"`. The chunk is dynamically imported on click; the button shows `aria-busy` and keeps focus until the overlay mounts. Hidden while the grid editor is open.
- **Overlay**: a native modal `<dialog>` through `SheetDialog` with a full-screen variant (`inset: 0; width: 100dvw; height: 100dvh; max-height: none; border-radius: 0`). It is not a route (Q9). It renders over the same loaded recipe object, the page's current scale factor and unit mode **frozen at open** (the page behind is inert, so they cannot change while cooking).
- **Close**: the **Close** button (X icon + visible text "Close", 48 px), **Escape**, and **browser Back / Android back gesture** all close it, and focus returns to the **Cook** button. Back: opening pushes one history entry (`pushState` with a marker, no URL change, same idea as `useLeaveGuard`); `popstate` closes the overlay; Close/Escape call `history.back()` when the marker entry is still on top, so there is exactly one close path and no stale entry. No unsaved data exists, so no confirm.
- **Focus**: on open, focus goes to the overlay heading (`h2` "Cooking: {title}", `tabindex=-1`), then Tab reaches Close first. Focus is trapped by the modal dialog.

### 6.2 Overlay chrome (sticky top bar)

```
375
+----------------------------------+
| [X Close]   Cooking: Brownies    |   row 1: 48 px, title truncates to 1 line (full text in title attr / heading)
| 3 of 9 ingredients - 1 of 4 steps|   row 2: progress, plain text (not live)
| Scaled 2x - US units             |   row 3 only when scale != 1 or units != default
| (i) Screen stays on while cooking|   row 4: wake lock status line (one line, wraps to two)
+----------------------------------+
```

- Only row 1 is `position: sticky; top: 0` (solid `--rg-surface`, bottom border). Rows 2 to 4 scroll away so a phone in landscape keeps its height.
- **Progress** is optional in G15; the spec includes it as text "3 of 9 ingredients, 1 of 4 steps" computed from the checkbox state. It is not a live region (the checkbox itself announces its state).
- **Scale line**: "Scaled {n}x" when the factor is not 1, "US units" or "Metric units" when the unit mode is not the default, so it is obvious why quantities differ from the recipe page. Step times and temperatures do not change (existing rule).

### 6.3 Wake Lock status line (G14, Q10)

One line, `--rg-muted` text with a small icon, `role="status"` (polite), updated at transitions only:

| State | Text (en) |
| --- | --- |
| Lock acquired | "Screen stays on while you cook." |
| Re-acquiring after the tab was hidden | (no text change; silent) |
| API missing or insecure context (plain HTTP LAN) | "Your screen may turn off. Keeping it on needs a secure (HTTPS) connection or a browser that supports it." |
| Request rejected (battery saver, denied) | "Could not keep the screen on. It may turn off." |

Everything else works in all states. The hook never throws. On exit the lock is released and the line is gone with the overlay. This clause is tested only with a stub; real behaviour is the owner's device list (Q10 accepted: Caddy profile gives HTTPS).

### 6.4 Layouts at 375 / 768 / 1280 and the grid in cook mode

Text scale: base 1.25rem (20 px) at phone, 1.375rem at tablet, 1.5rem at desktop (`--ck-scale`; tokens in section 9). Rows have a minimum height of 64 px (phone) / 72 px (larger). The sticky ingredient column and `ScrollRegion` (sideways scroll, arrow cue) are kept. Columns:

| | Ingredient column (sticky) | Step column min width | Checkbox zone |

| 375 (phone) | 184 px (read view: 138) | 156 px | 48 px |
| 768 | 260 px | 168 px | 48 px |
| 1280 | 380 px | 192 px | 48 px |

```
375 (visible width 343; sticky col 184, so 159 px of steps shows; the rest scrolls)
+--------------------------------+
| [X Close]  Cooking: Brownies   |

| (i) Screen stays on ...        |

```

Ingredient cell: the **whole cell is the toggle** (a `<label>` wrapping the native checkbox and the ingredient text). A visible box 28 px at the left, 48 px hit zone by padding, text wraps beside it. Checked: box shows a check mark, the text is struck through (`text-decoration: line-through`) and uses `--rg-muted`, cell fill `--rg-banner`. Toggling never changes cell size (same box, same font weight, strike only), so there is no layout shift. The accessible name is the ingredient text ("2 tbsp butter"), the state is the checkbox's own.

**Step cell: checkbox and expansion coexisting at 375 px.** The cell has two non-overlapping zones; there is never a control inside a control:

```
156 px wide cell, rowSpan 1 (min 64 px high)
+----+-----------------------+
|    |                       |
| [] | Melt                  |   left strip  = checkbox zone, 48 px wide, full cell height
|    | 5 min                 |   right area  = expand button (label + params), >= 108 px
+----+-----------------------+   a 1px --rg-line divider between the zones
```

- Left strip: native `<input type="checkbox">` with `aria-label` "Mark {label} done" (key `cook.step.check`), 28 px box centred, whole strip is the hit area (a `<label>` for the strip). Tap or Space toggles.
- Right area: the existing `.rg-stepbtn` (label + params + sr-only "Uses x to y"), same expand behaviour as the read view. Tap or Enter/Space expands; it never toggles the checkbox.
- The cell-level click (the whole-`td` target of the read grid) is **not** used in cook mode (F3). A tap outside both zones (padding) does nothing.
- **Checked step**: box checked, label struck through and muted; expansion still works (you can read a done step). The checked state does not collapse an open panel.
- **Tall cells** (rowSpan > 1): the strip stays full height, the check box is centred vertically in it.
- If a label is long it wraps to at most 3 lines (`line-clamp` not used; the cell grows). Min width keeps at least 108 px for the text at 375.
- Banners (top/bottom): one row, text centred, the checkbox strip at the left like a step; their detail is already inline text, so there is nothing to expand. Checkbox is still offered (a "Rest 30 min" banner is a thing to tick).
- Tab order inside a row: ingredient checkbox, then for each step cell in column order: checkbox, then expand button. That is 2 stops per step cell (G15 asks that two controls not fight; they are separate stops and separate hit zones). The `ScrollRegion` itself is one stop before the table, as today.

### 6.5 Step expansion in cook mode

Same data, same text. Phone (< 640): the step opens in a **bottom sheet inside the overlay** (`SheetDialog`, existing read-view behaviour; text at the cook scale; close button 48 px; Escape closes only the sheet; focus returns to the step's expand button). 640+: the inline panel under that section's table (`rg-panel`, as in the read view), `aria-expanded` / `aria-controls` on the expand button. One step expanded at a time. Back button closes the overlay (and the sheet with it); the sheet does not add a history entry.

### 6.6 List recipes in cook mode

A recipe in list view mode renders cook mode as two lists per section: **Ingredients** (each `<li>` is a full-width label with the checkbox) and **Steps** (numbered; checkbox in a left strip, step text beside it, no expansion needed because the detail is already inline). Same text scale, same chrome, same keys. The Cook button is shown for list recipes too.

### 6.7 State

Checkbox state is component state only (Q8): not persisted, not in the URL, cleared on close and on reload. Keys are **section index + row index** and **section index + step index** within the loaded recipe object (G6), never ingredient or step ids. If the page replaced the recipe data while cook mode is open (it cannot: the page is inert), state is dropped. Opening again starts all unchecked; there is no "restore" prompt.

### 6.8 Keyboard path (cook mode)

Tab / Shift+Tab walk the stops in 6.4; Space toggles a focused checkbox; Enter/Space on an expand button opens the step; Escape closes the open step first, then the overlay on the second press; Close button and Escape return focus to **Cook**. Arrow keys scroll the `ScrollRegion` only when it has focus (existing). No roving tabindex: the stop count is bounded by the recipe (about 9 ingredients + 4 steps x 2), which is acceptable for a cooking surface; if the 4b walkthrough pattern is wanted later it is a follow-up.

### 6.9 Contrast, motion, zoom

- Text uses `--rg-ink` on `--rg-surface` (>= 7:1); muted/struck text `--rg-muted` (>= 4.5:1 on `--rg-surface`, `--rg-banner` and `--rg-step` in both themes; axe confirms in T13).
- Checkbox box: 2 px border `--rg-ink`; checked fill `--rg-accent` with a white (light) / `--rg-surface` (dark) check mark; both >= 3:1 (WCAG 1.4.11).
- Reduced motion: no transitions on checking, the sheet appears without slide, scroll cue is static.
- Browser zoom 200 % and large OS text: all sizes are rem, so cook mode grows further; the top bar wraps, the table scrolls sideways, nothing clips; no page-level horizontal overflow (the dialog does not scroll sideways, only the region).
- "Page is scaled" (recipe scale 2x): quantities are shown at 2x as on the page; the scale line (6.2) says so.
