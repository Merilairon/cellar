# v1.0 carryover

## Open owner decisions from the security review

Source: [v1.0-security-review.md](v1.0-security-review.md). None of these changes code; each needs a written owner decision.

- **M1: a member can make the admin JSON export impossible (awaiting owner).** A member can create or restore enough large recipes (for example 52 recipes of 4000 ingredients) that the manifest passes the 32 MiB export cap, so the admin `GET /api/export?all=1` answers `413 export_too_large`, as does the member's own export. The volume copy (the documented primary backup) is unaffected. The cap is deliberate: every export must be restorable. Reviewer recommendation: **accept in writing** and state in the README backup section that the JSON backup has a 32 MiB manifest ceiling and the volume copy has none; the alternative is to raise `MAX_MANIFEST_BYTES` after measuring memory on the smallest supported host (the restore now stays near 580 MiB for a 32 MiB manifest, see the resolution in the review), or add a per-user row quota at recipe write time.
- **Q4: the rate limiters trust `X-Forwarded-For` (awaiting owner).** With `TRUSTED_PROXIES` set and the app port reachable, rotating the header defeats the per-IP login and the `/r/*` limiters; nothing else depends on the client address. Reviewer recommendation: **accept**. The README and `docs/deployment.md` already say never to publish the app port; an optional startup warning for the mode trap was suggested by the architect.
- **Q7: the admin export contains everyone's private recipes (awaiting owner).** Admin-only, logged as `export.started scope=all`, no password hash, token, session or invite inside. The admin can already read any recipe by id and holds the volume. Reviewer recommendation: **accept**; keep the log line and keep the backup page saying the file holds everyone's private recipes. Re-entering the password for `?all=1` is a post-1.0 idea.
- **Q16: share tokens are stored in plaintext (awaiting owner).** In `recipe.share_token`; never in lists, exports, logs or responses to non-owners. A database leak already exposes every private recipe, so hashing the token buys nothing the owner would keep. Reviewer recommendation: **accept**.

## Code review residuals (v1.0)

Source: [v1.0-code-review.md](v1.0-code-review.md). Recorded, not fixed.

- **m2:** `resolveUploadPath` costs 3 synchronous syscalls (`realpath(base)`, `lstat`, `realpath(file)`) per photo request; optional fix is caching `realpath(base)` per process.
- **m3:** `generateMetadata` and the page both read the DB on the edit, import, register and reset pages (only the recipe page uses `cache()`); cost only, no leak.
- **m5:** a credentialed `source_url` fails whole-file restore validation (`backup_invalid`) of an older own export; fix would be to accept and strip userinfo in restore, or mention it in the release notes.
- **n1:** `log.ts` adds an `error` listener to stdout and stderr at import; stacked listeners could trigger MaxListenersExceededWarning if many bundles load the module (guard with a `globalThis` flag).
- **n2:** `npm test` prints every `log()` line; mock `@/lib/log` or set `LOG_LEVEL=error` in the vitest setup.
- **n4:** `DELETE /share-link` works while `PUBLIC_LINKS_ENABLED=false`; already in the README upgrade table and the release notes.

## Gate findings (T18, tree c0b56b7)

Source: [v1.0-reality-check.md](v1.0-reality-check.md). Verdict NEEDS WORK until the owner decisions above are recorded in writing.

- **Dependency audit (owner decision, new):** `npm audit --omit=dev --audit-level=high` reports 2 high findings: picomatch ReDoS (GHSA-fc5q-39xc-vjpf, affects all versions up to 4.0.7, the newest published) reached through `next-intl`, then `@parcel/watcher`. No fixed version exists, so `npm audit fix` changes nothing. The path is a file-watcher dependency and is not reachable with untrusted input at runtime. Recommendation: **accept** until picomatch publishes a fix; the scheduled CI audit job stays red until then, which is the intended signal. Re-check at each release.
- **Known flakes (unexplained, not regressions):** `backup-a11y` keyboard test (page lands on `/` instead of `/backup`), `backup.spec` "discard" ECONNRESET, `import-headless`, `import-mapping-a11y` keyboard, `share-a11y` document-title. The diagnosis could reproduce only the first, on both v0.5.1 and HEAD, so it predates slice C. Two full pinned-image runs at the gate were 415 passed, 0 failed.
- **Restore re-encodes photos:** a restored photo can differ in bytes (same dimensions, samples within 4 of 255). Stated in `docs/deployment.md` only.
- **`x-powered-by: Next.js` is still sent** (review I1, not done).
- **Share links are not restored, by design.**
