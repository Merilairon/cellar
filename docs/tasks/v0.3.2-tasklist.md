**Out of scope for 3c (do not build)**
- Making headless the default, or any install path that requires it. `HEADLESS_URL` unset is a first-class supported configuration and must keep working unchanged.
- A Home Assistant add-on or any packaging that bundles the browser (v1.1, RELEASE_PLAN).
- Site-specific scraping rules, login/cookie handling, CAPTCHA solving, stealth plugins, proxy rotation. The sidecar renders one public page; if the site still blocks it, the user pastes.
- Screenshots, PDFs, scrolling/clicking automation beyond "load, wait for network idle, read the DOM". No user-supplied scripts or selectors.
- Persisting rendered HTML beyond the existing `KEEP_RAW_HTML` rule.
- Cover image fetching through the browser: covers keep using `safeFetch` in the app at save time (unchanged).
- Cover preview, tags persistence, search, unit conversion, grid editor (04a to 04c). Any AI/LLM call.
- Backup/restore, retention for `KEEP_RAW_HTML` backups (v1.0). T16 only adds the minimal pruning rule, see its scope.
- Microdata/RDFa extraction of any kind: moved to 04a by owner decision Q10 (third carry avoided). Fixtures `microdata-only-basic` and `microdata-only-howtostep` stay `out_of_slice`.
- Supporting hosts with `user.max_user_namespaces=0`: unsupported by owner decision (the Chromium sandbox needs unprivileged user namespaces); documented, not worked around.

**Hard rules**
- Optional everywhere: with `HEADLESS_URL` unset there is no sidecar request, no new code path that can fail an import, and the UI offers paste with a clear message. A test pins this (T6, T13).
- The browser never runs inside the app container and the app never gets a Playwright dependency.
- The sidecar is untrusted: the app treats its response as hostile input (size cap, content-type, timeout, same sanitize/extract/normalize pipeline). A compromised sidecar must not be able to reach the database, the volume or the LAN (T1, T5).
- No request from the sidecar may ever leave toward a blocked address: enforced at the network layer (T5) **and** in the sidecar (T3) **and** pre-checked in the app (T6). Three independent layers; the pen test (T12) attacks each.
- Hard limits: 30 s per job (kill, not abort), 5 MB response cap, 1 concurrent render by default, memory/CPU/pids limits in compose.
- Fail closed: any interception error, unresolvable host, or ambiguity aborts the request, never allows it.
- No hard-coded UI strings; every new code has an `import.errors.*` or warning message (T8). Warnings stay codes, never free text from the sidecar.
- Conventional Commit after each numbered task, no co-author trailers (owner's global CLAUDE.md). No background processes or server start commands in task commands; compose/browser commands in tasks are run by the developer or CI, not backgrounded by the agent.

| # | Gap | Affects | Proposed minimal resolution |
| --- | --- | --- | --- |
| G1 | Spec says "request interception with IP checks and DNS pinning" but Playwright `page.route` cannot connect to a chosen IP; it can only continue, fulfil or abort a request, and Chromium does its own DNS. Interception alone leaves a TOCTOU window (check resolves host to a public IP, Chromium re-resolves to a private one). | S0, T3 | Spike decides between (a) **filtering forward proxy inside the sidecar** (recommended): Chromium launched with `--proxy-server=http://127.0.0.1:<port>`, `--proxy-bypass-list=<-loopback>` removed so nothing bypasses, the proxy handles `CONNECT` and plain HTTP, resolves once, checks every address with the shared `ip-guard`, connects to the pinned IP (TLS passes through end to end, so no MITM and no CA). Plus `context.route('**/*')` for scheme/port/method/resource-type policy and `serviceWorkers: 'block'`. (b) route-only with `--host-resolver-rules` per request, rejected as fragile. Document the choice in `v0.3.2-spike.md`. |
| G2 | "Isolated network ... no route to the host, LAN, or app database" versus "the browser must reach the public internet". Docker `internal: true` blocks all egress; a normal bridge reaches the host's LAN. | T1, T5 | Two networks: `headless-link` (`internal: true`, only `app` and `browser`) for the app-to-sidecar HTTP call, and `headless-egress` (normal bridge, only `browser`) for internet. ## Security note (sidecar threat model summary; full text in T1)

The sidecar executes **attacker-controlled JavaScript** from any URL a logged-in user imports, on a host that holds other things (app, SQLite volume, possibly a LAN). Assets: the host network and LAN, the cloud metadata address, the app container and its `/data` volume, other containers on the compose networks, the operator's bandwidth and CPU. Trust boundaries: internet to sidecar (hostile), sidecar to app (hostile response), app to sidecar (authenticated by network plus token).

Required controls, with the task that delivers each: no route to host/LAN/DB (T5, T1); filtering proxy with shared IP guard and pinned IPs (T3); scheme/port/resource policy (T3); no downloads, `file://`, extensions, service workers (T3, T4); fresh context per job and 30 s hard kill with process-group SIGKILL (T4); non-root, read-only rootfs, dropped capabilities, `no-new-privileges`, seccomp (T2, T5; Chromium's own sandbox needs either a user namespace or Playwright's documented seccomp profile, **never** `--no-sandbox` without an explicit documented reason, Q7); memory/CPU/pids limits (T5); response caps and hostile-response handling in the app (T6); pre-check in the app (T6); bearer token (T2, T6); no secrets in the sidecar environment (no `SESSION_SECRET`, no DB path). Residual risks to state: Chromium zero-days (mitigate by pinning and documenting upgrade of the image tag), exfiltration to the public internet by a malicious page (accepted; the page is public content and the sidecar holds nothing sensitive), resource exhaustion (bounded by limits and concurrency 1).
