# v0.5.1 Security Checkpoint (T13)

Scope: slice B of v1.0 on `release/v0.5.1` (HEAD `43741ee`): `src/lib/backup/*` (schema, parse, migrate, export, toTree, zip, unzip, restore, staging, prune), `src/app/api/export/route.ts`, `src/app/api/import/backup/**` (stage, delete, apply, shared), `src/lib/security/export-limits.ts`, `src/proxy.ts` (matcher now excludes `/api/import/backup`), `src/lib/env.ts`, `Caddyfile`, `src/components/backup/*`. Reviewed against the Security note, G13 to G17, R6, R7, R8, R12 in `v1.0-tasklist.md`. Method: code read in full, negative controls in a throwaway git worktree with its own `npm ci`, and a live probe against a production build (`next build` plus `next start` on port 3777, temp SQLite, temp uploads and restore dirs, `TRUSTED_PROXIES=127.0.0.1`, one admin and two members). Server stopped and worktree removed afterwards. Playwright not run (pinned image).

## Verdict: PASS (conditions M1 to M4 closed)

No Critical or High finding. No other-user data exposure, no auth or CSRF bypass, no file write outside the restore and uploads dirs, no unbounded memory. Four Medium findings, all about missing limits or tests, not exploitable holes: three controls whose removal fails no test (M1 to M3) and the missing per-user restore limiter (M4). Conditions for the tag: fix M1 to M3 (test-only, smallest fixes below) and either add the restore limiter or record M4 as an accepted residual with the owner's sign-off.

### Reproductions and smallest fixes (Medium)

**M1.** Mutation: delete `if (produced > size) return fail('size_mismatch');` in `inflateRange`. All 87 tests in `unzip.test.ts` and `restore-route.test.ts` still pass, because the later `data.length !== info.size` check turns the same bomb into the same reason after the whole output was inflated. The existing "lying small declared size" test only asserts the reason. The ratio check uses the DECLARED size, so an entry that declares 100 bytes and carries 1 MiB of deflated zeros (about 1 GiB of output) passes the ratio check and relies on this limit alone. Fix: in the test, spy on the inflater output (or run with `--max-old-space-size`) and assert that the produced bytes never exceed `size + chunkSize`, for example by passing a 50 MiB bomb and asserting `process.memoryUsage().arrayBuffers` growth under 32 MiB, or export a counter from `inflateRange`.

**M2.** Mutation: `Number(declared) > max` replaced by `false`. The test "413 on the declared Content-Length, before any file exists" still passes (the streaming cap returns the same 413 and removes the file). Fix: in that test, make the request body a stream whose `pull` throws or records, and assert it was never read and that `open` of the stage path was never called (spy on `node:fs/promises.open`).

**M3.** Mutation: budget test `attempted++ >= MAX_RESTORE_PHOTOS` replaced by `false`: 71 tests pass. Fix: a restore test with `MAX_RESTORE_PHOTOS + 1` photo references (one tiny valid webp copied; the `decode` seam stubbed) expecting `photos_restored === 2000` and `photos_failed === 1`.

**M4.** Reproduction: a signed-in member can POST `/api/import/backup` in a loop. Each call streams up to 256 MiB to disk, parses and deletes it: disk I/O and CPU with no limit (only one upload in flight per user and one stage per user, so disk at rest is bounded to about 512 MiB per member). Each apply can decode and store 2000 photos; repeating it grows `UPLOADS_DIR` with no quota (same as photo upload, v0.4.2 Q13 accepted). `beginApply` is process-global, so one member re-applying a big backup keeps every other user (admin included) at 409 for the duration. Smallest fix: `restoreLimiter()` in `export-limits.ts` style (`RATE_LIMIT_RESTORE_MAX` 10 per hour, per user) hit after authentication and before `beginUpload`, refunded on 4xx validation failures; optionally refuse a new upload when `statfs(RESTORE_DIR).bavail` is below `2 * RESTORE_BODY_MAX`.

**L1.** Fix: set `X-Content-Type-Options: nosniff` inside `noStore()` (`src/lib/recipes/http.ts`) or in `fail()` plus a tiny `jsonNoStore` helper used for the 201, 200 and 204 responses.

## Check results

### 1. Redaction (R8) against the serializer

`export.ts` names every output field. Greps over `export.ts`, `restore.ts`, `schema.ts` for `passwordHash`, `share_token`/`shareToken`, session, invite, password_reset, import_job: no reference. Columns that reach an export: recipe (title, description, servings, servings_label, prep and cook minutes, source_url, source_name, visibility, view_mode, created_at, updated_at; `owner_email` in `all` only), section, ingredient, step, photo (position, is_cover, width, height, file, thumb), note (body, shared, author display name, `author_email` in `all`, `mine` in own scope, stamps), rating (stars, `user_email` in `all`, stamps), tags, and for admin `all` a `users` list of email, display_name, role, unit_pref, locale. Never selected: user.id, password_hash, deactivated_at, created_at; session; invite; password_reset; import_job; recipe.id, owner_id, share_token, copied_from_id. Live: `?all=1` as admin, grep for `argon2|password|share_token|session|"id"` returned 0, users keys are exactly the five above. Notes and ratings predicates are in the SQL (own scope: `shared = 1 OR user_id = me`, rating `user_id = me`).

### 2. Export authorization

Member (and admin without `all`): `recipe.owner_id = actor.id` only, not `readableBy` (a `users`-visible recipe of someone else is not exported). `all=1` for a member: 403 at the route (`route.ts:50`) and again in `buildBackup`; for an admin the stored role of an ACTIVE user is re-read inside the transaction (`export.ts:199`), so a stale session claim cannot widen the export. No id parameter exists (no IDOR surface). Query is `strictObject` with `z.literal('1')`; repeated or unknown parameters are 400. Live: member plain 200, member `all=1` 403, admin `all=1` 200, `all=2`, `all=1&all=1`, `x=1` 400.

### 3. Zip reader bounds (`unzip.ts`)

File based, range reads only (`readRange` throws on a short read). Entry count cap 60 000 and `total * 46 <= cdSize`; central directory at most 8 MiB and `cdOffset + cdSize === eocdPos` (so offsets are inside the file); end record must run exactly to the end of the file (comment length checked); disk fields, ZIP64 markers and locator refused; per-entry `localOffset + 30 + nameLen + compressedSize <= cdOffset` (JS numbers, no 32-bit overflow); encrypted and strong-encryption flags, methods other than 0 and 8 refused; name bytes checked as ASCII against `backup.json` or `photos/<ULID>.webp` before any decode; duplicates, overlapping entries (sorted offset check) refused; size caps 16 MiB manifest, 20 MiB photo, 2 GiB declared total; ratio cap 200 and `compressedSize > cap + 1 MiB` for deflate; local header must match the central record (name, method, and CRC and sizes unless bit 3); inflate has a hard output limit (cut at `size`, M1 above); CRC-32 verified; entries are read one at a time. Whole-file reads: none for zip; the JSON kind is `readFile` after a `stat` size check at 16 MiB. Live: traversal zip and 8 MiB-of-zeros bomb zip both 422 `backup_zip_invalid`, no file left. The ratio check is on the declared size, so the output limit is the only defence against a lying entry (see M1).

### 4. JSON parsing

`parseBackupJson`: BOM strip, text depth scan (cap 32) before parsing, reviver that throws on `__proto__`, `constructor`, `prototype` at any depth, then an iterative walk for forbidden own keys and depth. `migrateBackup` runs `checkCaps` (reads `.length` only) before the structural walk and before zod; every schema object is `strictObject` (9 sites); zod issues are sliced to 20 and the document superRefine mints at most 50 issues, the route returns at most 10. Strings and arrays are capped per field. Version: `version` must be the literal 1; a version 2 file answers `backup_version_unsupported` with the number only (attacker text is never echoed). Live: `__proto__` at top level and `constructor.prototype` both 422 `forbidden_key`; v2 422 with `found: 2`; garbage JSON 422 `syntax`.

### 5. Staging

Ids and paths are ULIDs minted server side (`ulid()`), path is `RESTORE_DIR/<ULID>.<json|zip>`; the id in the URL is only a Map key after `STAGE_ID_RE`; no user input reaches a path. Owner binding: `getStage(id, ownerId)` returns undefined for a foreign id (uniform 404 with the expired and unknown cases). Live: other member's and the admin's apply and delete of a member's stage all 404 and the stage survived; `..%2F..%2Fetc` 404. TTL one hour enforced at read and by prune; orphan prune of unregistered files older than the TTL (I1). `beginUpload` one per user, `applyRunning` per user and process-wide `beginApply` give 409; live 4 concurrent applies: one 200, three 409. Files are `0o600` via `open(path, 'wx', 0o600)`; directory 0o700 on creation (I2). Cleanup: `keep` flag plus `finally { removeFile }` on every stage failure (413, 408, 415 never create a file, 422, 403, 500); apply always `discardStage` in `finally`. A new stage replaces the user's previous one after the new one validated.

### 6. Body cap while streaming

Order live: CSRF 403, session 401, 415, 409, declared length 413, streamed 413, stall 408, then validation. Live (cap 2 MiB): 3 MiB json and zip by Content-Length 413, chunked 413 (no Content-Length), lying short Content-Length the server closed the connection; 408 after 30.1 s with a 4-byte body and a 1 MB declared length; 150 MB unauthenticated and 150 MB wrong-type bodies answered in 2 and 3 ms (not read); 150 MB member zip streamed at default cap, RSS flat (306.8 to 309.3 MB), 422, no file left; 47 MB valid zip staged, RSS 243 to 323 MB peak, file mode 0600. The 30 s limit is idle, not total: a sender trickling a byte every 29 s keeps its one per-user slot (and a Node default `requestTimeout` of 300 s probably ends it; not measured).

### 7. Apply

`owner_id` in a member restore is always `actor.id` (`ownerOf`); `owner_email` is not allowed in own scope by the schema and is ignored outside `all` by `plan`. Note author: own scope `mine === true` gives the actor, others' notes are skipped; `all` scope maps emails to EXISTING ACTIVE users only, unknown authors are skipped. Ratings: own scope the actor, `all` mapped, unknown skipped. `users[].role` is never read, no user is created, no role granted; `users` is not in own scope. `share_token` is not in the schema (strict), `insertRecipeTree` assigns `null`. `visibility` is restored from the file: a member file with `users` makes the member's own restored recipe visible to every signed-in user. Assessment: acceptable. The recipe is owned by the restorer and the member can already set the same value in the editor; it reproduces what the exported recipe had. UX note: the preview does not say that visibility comes back. `validateRecipeGrid` runs per recipe (`gridFailure`); removing it fails 2 tests. Per-recipe `BEGIN IMMEDIATE` transaction; the first failing recipe stops the run, earlier ones stay, `failed_at` returned. Photo files are written after the recipe commits and removed on a failed insert; titles are renamed with a bounded suffix loop. L4 is the admin reroute.

### 8. Images

Every photo goes through `processImage` with `allowed: jpeg, png, webp` (magic bytes, header pixel cap 16 Mpx, one decode, rotate, WebP re-encode, metadata dropped) under `limitDecode` (shared limiter, 3 retries). Stored names are fresh ULIDs written with `wx`; the archive name never reaches a path. Budget 2000 per apply (M3). Reported peak 280 MiB RSS on a 200 MiB zip is consistent with the 150 MB and 47 MB runs above (entries are read one at a time, 20 MiB cap each). The 16 MiB manifest path (string plus parsed tree plus zod clone) was not measured and could be several hundred MiB on a Pi (residual).

### 9. Response headers

`Cache-Control: private, no-store` on every response of the three routes and on export (live). Export: `Content-Type` application/json or application/zip, `Content-Disposition` `attachment; filename="cellar-backup-YYYY-MM-DD.<ext>"` built from the server clock only, `nosniff` present (export is behind the proxy). Stage, apply, delete: JSON content type; `nosniff` only on error bodies via `fail()` (L1); no CSP, X-Frame-Options or Referrer-Policy (JSON only, low value).

### 10. Proxy exclusion and CSRF

The proxy gave other `/api/*` routes: the cookie-presence 401 gate, the security header set and (for `/r/*` only) a limiter. There is no CSRF and no body-type logic in the proxy; CSRF lives in `authenticate`. For the three routes `authenticate` runs first: CSRF 403 before 401, then session validation (real DB check, stronger than the cookie gate). Live, all with the response `Cache-Control` only: no Origin 403 (even without a session), `Origin: http://evil.test` 403, `Sec-Fetch-Site: cross-site` 403, no cookie with a good Origin 401 for POST stage, apply, DELETE. The 401 is a plain API 401 with an empty body, not a 307 to `/login` (the proxy would have returned `{"error":"unauthenticated"}` JSON, which `/api/export` still does). Gained by exclusion: none; lost: headers (L1) and the proxy's JSON 401 body. Cross-site forms cannot set `application/zip` or `application/json`, so 415 is a second layer behind CSRF.

### 11. Export limiter, one in flight, logging

Per user limiter (default 10 per hour): live 10 times 200, then 429 with `Retry-After`; one export in flight per user (409), lease freed by the stream close hook, 6 h stale bound. `console.*` in the backup code logs only `e.message` of caught errors (zip reason words, sqlite constraint text, error codes), recipe index `k`, never titles, notes, emails, file names or tokens. `src/lib/log.ts` does not exist yet: T14 must move these 9 call sites (`restore.ts:339,372,381`, `zip.ts:215`, `staging.ts:54`, `export/route.ts:98,99`, `import/backup/route.ts:131`, `apply/route.ts:78`) to the logger and keep the no-contents rule (G18 redaction test).

### 12. UI

`src/components/backup/*`: no `dangerouslySetInnerHTML` or `innerHTML` (grep). File name, conflict titles, unknown owner emails, the server `message` and `errors` strings are React text children (`PreviewTable.tsx` list items, `RestoreView.tsx`); the export link is a fixed relative `href` built from two booleans; `errors` entries are filtered to strings and sliced to 5. A hostile title such as `<img src=x onerror=alert(1)>` is escaped by React.

## Residuals

- M4 if accepted: no restore limiter, no disk cap, one global apply lock, no quota on photo growth (v0.4.2 Q13).
- Admin export and `all` restore carry other users' private data by design (Q7); a restore of an `all` file with unknown owners lands them on the admin (L4).
- Total upload time is bounded only by the 30 s idle rule plus Node's own `requestTimeout` (not measured); a trickling sender holds one per-user slot.
- Symlinks in `UPLOADS_DIR` are not followed on write (`wx`), and the export reads names that only ever match `photos/<ULID>.webp`; `resolveUploadPath` is lexical, so a symlink planted by someone who can already write the uploads volume would be read by the zip export. Out of scope for this threat model.
- Hostile 16 MiB manifest peak memory (parse plus zod) not measured; 1 GB host behaviour not tested.
- Not tested: Playwright, a real Caddy (the 260 MB cap vs the 256 MiB default, L2), browsers, requests behind a real reverse proxy.
