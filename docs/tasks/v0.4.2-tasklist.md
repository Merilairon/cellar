## Specification Summary

**Source**: [milestones/04-search-edit.md](../../milestones/04-search-edit.md) (slice 4c only, requirements 6 to 9), [data-model.md](../data-model.md) (photo, note, rating, recipe_fts and §5 API table), [RELEASE_PLAN.md](../RELEASE_PLAN.md) (cut line), [TASK_ASSIGNMENTS.md](../TASK_ASSIGNMENTS.md) (v0.4.x table, 04c rows, Gate, Per-slice workflow), [v0.4.1-tasklist.md](v0.4.1-tasklist.md) (format), [v0.4.1-carryover.md](v0.4.1-carryover.md) (items assigned to this slice), [user-journeys.md](../user-journeys.md) (Journey 2 step 6 and "Screen sleeping: use Wake Lock API where available (cook mode)"; Journey 3 step 5 "Uploads a photo, adds tags").

**Objective (quoted, milestone 04)**: "Make the recipe collection usable day to day: search and tags, unit conversion and scaling, a visual grid editor, and photos/notes/ratings." Slice rule: "**4c (v0.4.2)** photos, notes, ratings, cook mode (6-9)."

**Requirements 6 to 9 (quoted, in full)**
- "6. **Photos:** upload (jpeg/png/webp, <= 10 MB), re-encode and resize (e.g. 1600 px + 400 px thumbnail), cover selection, delete; served from `/data/uploads` with authorization."
- "7. **Notes:** private and shared notes per recipe; list under the recipe."
- "8. **Ratings:** one 1-5 star rating per user; average shown on cards and recipe page; filter by min rating."
- "9. **Cook mode:** optional full-screen larger-text grid, checkboxes on ingredients/steps (local state), Wake Lock where supported."

**Requirement 1 clauses that land here (quoted)**: "FTS5 index over title, description, ingredient names, tags, shared notes and the user's own notes; ... `GET /api/recipes?q=&tag=&min_rating=&author=`; results respect visibility." (4a shipped everything except notes and `min_rating`.)

**Acceptance (quoted, 04c subset)**: "Uploaded oversized or non-image files are rejected." Carried from 4a/4b and still binding: "a private recipe is not found by another user" (extends to **private notes**: another user's private note text must never find, rank or reveal a recipe).

**Target pace**: 2 weekends maximum (Release Plan: "Re-split any slice that cannot finish in two weekends"). This slice is **larger than 4a/4b in surface** (one migration, three data domains, an upload pipeline, search changes, four UIs, a performance baseline). The honest estimate and the pre-agreed split are in Sizing.

**Technical stack**: TypeScript strict, Next.js 16.4.5 App Router (**AGENTS.md: this version differs from training data; the guides read for this list are in T0**), Drizzle + better-sqlite3, zod 4, next-intl, Tailwind, Vitest, Playwright 1.64.1 (pinned image for visuals), axe harness, **sharp 0.35.5 (already a runtime dependency; no new dependency is planned)**. **One migration, `0007`** (first schema change since `0006`).

**Existing code this slice builds on (verified by reading `src`)**
- **`photo` table already exists** (migration `0003_import_photo`, `src/lib/db/schema.ts:259`): `id`, `recipe_id` (FK, `ON DELETE CASCADE`), `file_path`, `width`, `height`, `position` (default 0), `is_cover` (CHECK 0/1), `created_at`; index `photo_recipe_id_idx`; **unique partial index `photo_one_cover_uq` (one cover per recipe)**. There is **no thumbnail column**. `note`, `rating` tables **do not exist** (milestone says "tables to add: ... `note`, `rating`"; only the data-model sketch exists).
- `src/lib/db/photos.ts`: `insertCoverPhoto` (immediate transaction: clears `is_cover`, inserts the new cover at position 0, so a re-import replaces the cover but keeps the old row), `getPhoto`, `getCoverPhoto`, `listPhotoPathsByRecipe`. No list, set-cover or delete helper.
- `src/lib/import/cover.ts`: the image pipeline for imported covers. `sniffImage` (magic bytes; jpeg/png/webp/gif, SVG refused), `reencodeCover` (sharp `limitInputPixels` = `MAX_COVER_PIXELS` 16 000 000, `failOn: 'error'`, `.rotate()` then metadata dropped, WebP, longest edge `MAX_COVER_EDGE` 1600), `sharp.concurrency(1)`, `sharp.cache(false)`, ULID file name, `limitDecode` concurrency limiter (`src/lib/import/limiter.ts`). **It accepts gif and has no thumbnail output**; its header says "Open item (04c): `POST /api/recipes/:id/copy` does not copy the cover file." `src/lib/import/uploads.ts`: `resolveUploadPath` (no escape out of the uploads dir), `removeUploadFiles` (best effort).
- `src/app/api/photos/[id]/route.ts`: `GET` only. `authenticate`, `getPhoto`, `getRecipeRow`, `canRead` (else 404), path from the DB row through `resolveUploadPath`, `Content-Type: image/webp`, `Cache-Control: private, no-cache`, `X-Content-Type-Options: nosniff`. **No POST, no DELETE, no thumbnail, no ETag.** There is no `src/app/api/recipes/[id]/photos`, `.../rating` or `.../notes` route.
- UI: `grep -il cover` over `src` finds **no component that shows a cover or a photo**: `RecipeCard`, `RecipeView`, `types.ts` have no photo field. Journey 2 already states "search results are a list of recipe cards with tags and no cover photos (photos are shown from v0.4.2)". The import review has no cover preview (C13).
- `src/lib/db/search.ts`: `searchRecipes` joins `recipe_fts` (`bm25(recipe_fts, 0, 10, 2, 4, 6, 1)`: the sixth weight, **notes = 1, is already reserved**), enforces `readableBy` (own plus `visibility = users`, no admin reach) in the same statement, caps at 100 with `q`; `buildMatchQuery` quotes every token and appends `*` so FTS syntax typed by a user is inert. `min_rating` is rejected today with 400 `invalid_query` (`data-model.md` §5). The list without `q` is ordered `updated_at desc, id desc`, so **any write that bumps `recipe.updated_at` re-orders the list and trips `base_updated_at` in the grid editor**.
- `data-model.md` §recipe_fts: `notes` "reserved, always `''` until 04c adds triggers on the `note` table (Q2). Private notes cannot live in a shared row; 04c decides between a per-user second index and a join check". Triggers `recipe_fts_*` rebuild one row per recipe (migration `0005`/`0006`, `withDeferredFts` in `src/lib/db/recipes.ts`).
- `src/lib/recipes/http.ts`: `authenticate` (CSRF 403 first, then session 401), `readJson` (**415 unless `application/json`**, `readCapped` streaming cap), `IMPORT_BODY_MAX`/`GRID_BODY_MAX` 1 MiB, `failure()`, `noStore`. `src/lib/recipes/access.ts`: `canRead` (admin, owner, or `visibility = users`), `canWrite` (owner or admin). `src/lib/recipes/service.ts`: `copyRecipeFor`, `deleteRecipeFor` with `opts.uploadsDir` (removes photo files after the row delete).
- `src/lib/db/users.ts` `deleteUserGuarded`: `reassign` or `delete` (deletes recipes; photo rows cascade, **photo files on disk are not removed**: the C2 family of gaps) and deletes the user.
- `src/proxy.ts`: `matcher` covers every route except `_next/static`, `_next/image`, `favicon.ico`, so **`/api/*` request bodies pass through the proxy**. `next.config.ts` has no `experimental` block unless `BASE_URL` is set. `src/lib/security/headers.ts` already has `img-src 'self' data: blob:`.
- `UPLOADS_DIR` (`src/lib/env.ts`, default `<dir of DATABASE_PATH>/uploads`, `/data/uploads` in Docker). No `navigator.wakeLock` use anywhere in `src`.
- Reusable UI: `RecipeGrid` (`detailMode: 'inline' | 'sheet'`, per-cell button, sr-only range text), `ScrollRegion`, `SheetDialog`, `StepDetail`, `RecipeView` (scale and unit state), `RecipeCard`, `RecipeList`, `TagInput`, `tests/e2e/helpers.ts`, `scripts/update-visual-baselines.sh`, `scripts/perf-sanity.ts` (in-memory, developer machine).

**Findings that change the plan (read before T1)**
1. **No new table is needed for photos, but a migration still is**: `note` and `rating` are new, `photo` needs a thumbnail path, and notes need an FTS structure. `0007` is required (the milestone and the data-model both say so; T2).
2. **Upload bodies go through `proxy.ts`.** The Next 16.4.5 `proxyClientMaxBodySize` guide (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/proxyClientMaxBodySize.md`, flagged **experimental**) says the proxy clones and buffers request bodies and the default limit is **10 MB**, "the body will only be buffered up to the limit". A 10 MB image in a multipart envelope is over that limit. T0 spikes this with a real 10 MB upload before the API is built (G3).
3. **Writes by notes, ratings and photos must not touch `recipe.updated_at`.** Otherwise a rating re-orders the newest-first list and causes false 409 conflicts for someone with the grid editor open (G5).
4. **Ids change on every save** (v0.4.1 carryover, `data-model.md` §1 note): photos, notes and ratings reference `recipe_id` only. No column, URL or cook-mode checkbox key may use an ingredient or step id (G6).
5. **The 16 MP pixel cap would reject some modern phone photos** (a 48 MP or 50 MP sensor) if reused as is. That is an owner decision (Q5) and is measured in the performance baseline.

**Hard rules**
- **Never cut sandboxing, backup/restore** (Release Plan cut line; not in this slice, restated). **Never cut** upload validation, the authorization matrices, the private-note visibility tests, or the security checkpoint.
- **Pure first**: the image pipeline function, note/search match building and the rating aggregate maths are tested before any UI (mirrors the 4a units rule and 4b reducer rule). T2 to T7 are green before T8 starts.
- **Authorization**: CSRF first (403), session (401), `canRead` else **404** (a recipe the actor cannot read is indistinguishable from a missing one), then the operation rule: photos write = `canWrite` (owner or admin); notes and ratings = any reader (`canRead`) for their own rows (Q3). The check is repeated **inside** the write transaction (existing `writeGuard`/`readGuard` pattern).
- **Upload = untrusted input**: never trust `Content-Type`, file name or extension; magic bytes then sharp decode; pixel cap before decode; size cap enforced **while streaming**, before buffering all of it (413); re-encode always (no original is stored, so EXIF/GPS and polyglot payloads are dropped); stored name is a fresh ULID; one decode at a time (existing `limitDecode`), a busy server answers 503/429, never queues unboundedly (Q15).
- **Private notes never leak**: a private note's body, its existence and its effect on search ranking are visible only to its author. Admin gets **no** reach (matches `readableBy`). A negative-control test must fail when the visibility predicate is removed.
- **Images are served only through the authenticated route** (`/api/photos/:id`, thumbnail variant); never from `public/`; `X-Content-Type-Options: nosniff`; responses `Cache-Control: private, no-cache` plus an `ETag`, so a revoked/deleted photo is not served stale from a shared cache.
- All user text (note body, tags) rendered as React text; no `dangerouslySetInnerHTML`. Note body is plain text, capped (Q16).
- All strings in `messages/en.json`; one message per new error code; no hard-coded labels. Targets >= 36 px (44 px `pointer: coarse`), aria-labels, nothing by colour alone (stars carry text "3 of 5").
- No `recipe.updated_at` change from photo, note or rating writes (G5). No key on ingredient or step ids (G6).
- Conventional Commit after each numbered task, **no co-author trailers** (owner's global CLAUDE.md). No background processes or server start commands in task commands; dev server, Playwright and docker runs are done by the developer or CI.

## Security note (new write paths: uploads, notes, ratings; changed read path: search)

Assets: other users' private notes (a new kind of per-user secret in a shared index), recipe privacy (photos are files), the single-threaded small server (image decode is CPU and memory heavy), disk space, stored text rendered later (stored XSS through note bodies), file system (path traversal through names), image parsers (malformed or hostile files, decompression bombs, polyglots, EXIF/GPS leakage). Attacker: a signed-in member uploading a hostile file or probing others' private data, a read-only member trying to write, an unauthenticated caller, a CSRF page, anyone with a leaked photo id.

Required controls (T12 checks each): CSRF and session before reading the body; `canWrite` for photo write, in-transaction re-check; streamed size cap before buffering (413) and a content-length pre-check; magic-byte sniff then sharp decode with `limitInputPixels` and `failOn: 'error'`; always re-encode (drops metadata, SVG and other types are never stored or served); generated file names, `resolveUploadPath` on every read and delete; serve `image/webp` with `nosniff` and `Content-Disposition` unset or `inline` with a fixed name; no SVG anywhere; photo ids from the DB, never client file paths; per-recipe photo cap; a concurrency limit on decode (`limitDecode`), 503 when saturated; note bodies stored as data and rendered as React text, length-capped; search `MATCH` only through `buildMatchQuery` (operators inert) including the new note branch; **private-note visibility predicate (`n.shared = 1 OR n.user_id = :me`) is in the same SQL statement as the match**; rating: integer 1 to 5 validated server-side, one row per (recipe, user), no mass assignment (`user_id` always the session user); `Cache-Control: private, no-store` on JSON, `private, no-cache` + `ETag` on images; error bodies carry codes only.

Residuals to decide in the checkpoint: no per-user disk quota (Q13); upload is unthrottled apart from decode concurrency (Q15); `users`-visible recipe photos are readable by every signed-in member by design; an admin can read and delete any photo (`canRead`/`canWrite` parity) but gets no reach into others' private notes through search or API (Q3); file orphans after a crash between file write and row insert.
