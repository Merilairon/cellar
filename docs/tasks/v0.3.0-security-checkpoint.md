# v0.3.0 security checkpoint (end of weekend 1)

Scope: `src/lib/import/{safe-fetch,ip-guard,extract-jsonld,sanitize,normalize,pipeline,paste,uploads,source-url}.ts`, `src/lib/env.ts`.
Method: manual review plus throwaway PoCs (kept outside the repo, nothing edited). Existing suite: 47 files, 655 tests, all passing.
Not in scope yet (not written): `cover.ts`, API routes, `import_job` persistence, `KEEP_RAW_HTML` writer. Nothing calls `safeFetch` or `getEnv().IMPORT_ALLOW_LOCAL_FETCH` yet, so the wiring is unreviewed.

## Verdict: PASS WITH FIXES

The SSRF core is sound; no bypass found. Three robustness bugs in the extract/normalize path (F1 to F3) and one env hardening item (F4) should be fixed before T6 exposes the pipeline to a route.

## What was verified and holds

- DNS pinning: one resolve per hop, every returned record checked (mixed answers rejected), socket `lookup` overridden to the validated IP, `Host` and TLS `servername` keep the hostname, `agent: false`. PoC: pinned fetch to `fake.example` connected to 127.0.0.1 with `Host: fake.example:<port>`; no second resolution.
- Redirects: manual, max 5, every hop re-parsed (scheme, userinfo, port) and re-resolved/re-checked. Location to `169.254.169.254` is rejected in production mode (only the allowLocal seam lets it through, as designed).
- URL tricks: WHATWG parser canonicalizes decimal/octal/hex/short IPv4; IPv6 zone ids, userinfo, non-http schemes, URLs over 2048 chars rejected. Non-default ports rejected when `allowLocal` is false (PoC: `invalid_url`), including on redirects.
- IPv6: `::1`, `::`, `::ffff:a.b.c.d`, IPv4-compatible, NAT64 `64:ff9b::/96`, 6to4, Teredo, ULA, link-local, site-local, multicast, documentation all blocked; unparsable input fails closed.
- Hostnames: `localhost`, `*.localhost`, `*.internal`, `*.local`, trailing dot handled; other names are caught by the resolved-IP check (docker service names resolve to private IPs).
- Size/time: single 10 s deadline over DNS, connect, headers and body (PoC: slow-drip body aborted at 2 s); 5 MB cap on wire bytes and on decoded bytes (PoC: 200 MB gzip bomb stopped with `too_large` in 11 ms); Content-Length pre-check; unknown content-encoding rejected; content-type allowlist; response destroyed on every early exit.
- Errors: `ImportError.message` is fixed per code; causes (which may hold IPs) go only to `deps.log`. No IP or body text reaches the result object.
- Sanitizer: plain-text output; scripts/styles/comments/CDATA stripped; entities decoded once then tags stripped again (`&lt;img ...&gt;` yields empty); control/bidi/zero-width characters removed; regexes linear (PoCs finished instantly); input pre-capped.
- JSON-LD extractor: no DOM parse of the page, scan is linear, script count, node count and depth capped, JSON.parse only (no eval); `__proto__` keys never merged.
- Production seam: `IMPORT_ALLOW_LOCAL_FETCH` refused when `NODE_ENV=production` (tests in `tests/unit/env-production.test.ts`), booleans parsed literally (`yes` throws), Dockerfile sets `NODE_ENV=production`, compose does not set the seam.
- `uploads.ts`: `resolveUploadPath` rejects absolute and `..` escapes; removal failures are swallowed and log only the message.

## Findings

### F1 (Medium) Stack overflow on deeply nested Recipe fields escapes as an unhandled RangeError
**Status: FIXED. `textOf` depth cap (3); `runImport` wraps extract/normalize in try/catch (failed `no_recipe`, logged) for URL and paste. Tests: normalize 200k-nest, pipeline deep page/paste, `pipeline-throw.test.ts`.**

Evidence: `normalize.ts` `textOf()` recurses through `name`/`text` with no depth limit; `runImport` catches only the fetch. PoC page (about 2.6 MB, within the 5 MB cap): `"name":{"name":{"name": ... "x"}}` nested 200k deep gave `RangeError: Maximum call stack size exceeded` thrown out of `runImport` (41 ms). V8 `JSON.parse` accepts the nesting; the extractor's depth cap only applies to finding the Recipe node, not to its contents.
Impact: any authenticated user can make an import request throw a non-`ImportError`. Depending on the route, the `import_job` row may be left in `running` or the request 500s. No process crash.
Fix: add a depth parameter to `textOf` (max 3, return `''` beyond). Also wrap the extract and normalize section of `runImport` in try/catch returning `failed(..., 'no_recipe')` (or add a `parse_failed` code) with `deps.log`. Add a regression test with the 200k-nest payload.

### F2 (Medium) `toLowerCase()` index drift hides JSON-LD on pages containing certain characters
**Status: FIXED. Scan uses case-insensitive regexes on the original string, no lowercased copy. Tests: `İ` before lower- and upper-case script.**

Evidence: `ldJsonScripts` finds offsets in `html.toLowerCase()` and slices the original `html` with them. Characters whose lowercase form has a different length (for example `İ` U+0130 becomes 2 code units) shift every later offset. PoC: `'İ'.repeat(5) + '<script type="application/ld+json">{...Recipe...}</script>'` returned `no_jsonld`, found 0. Turkish and other recipe sites with `İ` before the script will import as `no_recipe`. Attackers can also use it to desync the open-tag slice from the body slice, but they only affect their own page.
Impact: correctness and a silent import-failure class; low direct security impact.
Fix: do not compute offsets on a lowercased copy. Use a sticky/global case-insensitive regex (`/<script(?=[\s>/])/gi` with `lastIndex`) on the original string, and the same for `</script`. Keep the linear scan. Add a test with `İ` before the script.

### F3 (Low to Medium) Work done before truncation: about 0.7 s event-loop block per request
**Status: FIXED. Ingredients sliced to MAX+1 before sanitizing; tag parts capped at 40. Tests: 100k ingredients/keywords. The optional 1 MB JSON-LD body cap was not added.**

Evidence: `normalize.ts` sanitizes every ingredient line before `slice(0, MAX_INGREDIENTS)` (`lines` is built from the full array), and `collectTags` iterates all keywords before the 10-tag break. PoC with 900k one-character ingredients (about 5 MB): 714 ms; 900k keywords: 684 ms. Pasted input is capped at 500k chars, but the fetch path allows 5 MB. The 10 s deadline does not cover post-fetch CPU.
Impact: a few concurrent imports (20/h per user limit, but multiple users) stall the single Node event loop for seconds. Not a crash.
Fix: `arr(...).slice(0, MAX_INGREDIENTS + 1)` before the `flatMap`/sanitize (keep the `+1` so `ingredients_truncated` still fires); cap `parts` in `collectTags` (stop at `MAX_TAGS * 4`). Consider capping JSON-LD script body at 1 MB before `JSON.parse`.

### F4 (Low) Production-seam rejection is fail-open on `NODE_ENV` and not wired to startup
**Status: FIXED. Seam accepted only when `NODE_ENV` is `development` or `test`; `getEnv()` called in `instrumentation.ts` at boot. Tests: staging/prod/empty rejected. Route-level check recorded in T6 acceptance.**

Evidence: `env.ts` computes `isProd` once at module load from `process.env.NODE_ENV === 'production'`; `parseEnv(source)` ignores `source.NODE_ENV`. Any other value (unset, `staging`, typo) accepts `IMPORT_ALLOW_LOCAL_FETCH=true`, which disables the whole SSRF guard. `getEnv()` is lazy and has no callers yet, so a bad config would only surface on first use.
Impact: a misconfigured non-`production` deployment with the flag set has no SSRF protection. The Docker image sets `NODE_ENV=production`, so the default deployment is safe.
Fix: invert the rule: accept the seam only when `NODE_ENV` is `development` or `test`; reject it otherwise. Call `getEnv()` at boot (Next `instrumentation.ts`) so startup fails. In T6, read `allowLocal` only from `getEnv()` and never from request data; add a route test asserting a request cannot set it.

### F5 (Low) A few non-public ranges are not blocked
**Status: FIXED. Added SIIT `::ffff:0:a.b.c.d`, `64:ff9b:1::/48`, `192.88.99/24`, `192.0.2/24`, `198.51.100/24`, `203.0.113/24`; vectors in `ip-guard.test.ts` (plus public neighbours stay allowed).**

Evidence (`isBlockedIp`): `::ffff:0:7f00:1` (SIIT IPv4-translated, `::ffff:0:0:0/96`), `64:ff9b:1::/48` (local-use NAT64) and `192.88.99.0/24` return false. All three only matter on networks with SIIT/NAT64 gateways; the main NAT64 prefix and 6to4 are covered.
Fix: add `x[0..3]==0 && x[4]==0xffff && x[5]==0 -> v4(12)`, block `64:ff9b:1::/48`, and block `192.88.99.0/24`, `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` for completeness. Add vectors to `ip-guard.test.ts`.

### F6 (Low) Resolver answer leaks internal DNS existence
**Status: DECIDED, no code change. `private_address` stays as is: invite-only app, small enumeration risk accepted; code still never echoes IPs. Revisit if registration opens up.**

Evidence: a hostname resolving to a private address returns `private_address`, versus `fetch_failed` for NXDOMAIN. A user can enumerate which internal names exist.
Fix: map `private_address` to the same user-facing message as `fetch_failed` (keep the distinct code in `import_job.error_code` for the admin/log only), or accept the risk for a small invite-only app.

### F7 (Low) Sanitizer leftovers (text-only context, so not exploitable today)
**Status: NOT FIXED here (no code per decision). Recorded as acceptance checks in T10 and T11 (no `dangerouslySetInnerHTML` on imported text). The `BAD_CHARS` additions remain optional.**

Evidence (PoC): unterminated `<img src=x onerror=alert(1)` survives as literal text; Unicode tag characters U+E0000 to U+E007F (invisible, usable for hidden prompt text) and U+061C, U+00AD are not in `BAD_CHARS`; U+200C/U+200D (ZWNJ/ZWJ) are stripped, which breaks emoji sequences and Persian/Indic text.
Impact: none while every consumer renders through React text nodes. It becomes XSS if any later feature uses `dangerouslySetInnerHTML`, markdown rendering or an email/export template with this data.
Fix: add `\u{E0000}-\u{E007F}` and `؜­` to `BAD_CHARS` (with the `u` flag); keep ZWJ/ZWNJ (only strip the bidi controls). Add a lint/grep rule banning `dangerouslySetInnerHTML` on import-sourced fields; document "plain text only" as a requirement for T6 to T12.

### F8 (Info) Items for T6 and later tasks
**Status: NOT FIXED here (no code). Recorded as acceptance checks in T6 (no raw_html in API, concurrency limit, log causes), T8 (cover via safeFetch image accept) and T10/T11.**

- `ImportResult.raw_html` is returned in every success and `no_recipe` result. The API layer must never serialize it to the client and must write it to disk only when `KEEP_RAW_HTML` is true (file mode 0600, outside `uploads`, name from job id).
- `deps.log(msg, e.cause)`: make sure the logger does not forward causes to any user-visible channel.
- `sanitizeUrl` accepts any http(s) host for `cover_image_url`; that is fine only because T8 must fetch it through `safeFetch` with `accept: 'image'`. Review `cover.ts` for: magic-byte check, no SVG, pixel cap before decode, no `sharp` on the raw URL.
- `resolveUploadPath` does not resolve symlinks; acceptable while only the app writes the uploads dir. Keep `GET /api/photos/:id` keyed by DB id, never by a client path.
- `safeFetch` has no global concurrency limit; rely on the per-user rate limit plus a small in-process semaphore (for example 4 concurrent fetches).
- Picks `addrs[0]` only; on dual-stack hosts without IPv6 egress this yields `fetch_failed`. Optionally try the next validated address (still pinned, still within the deadline).
