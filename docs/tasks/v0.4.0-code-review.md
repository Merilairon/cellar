Scope: `git diff v0.3.2..88774ae` on `release/v0.4.0` (134 files, about 9.6k added lines, 12 commits)
against `v0.4.0-tasklist.md`, `v0.4.0-security-checkpoint.md` and `v0.4.0-carryover.md`. Read-only

Evidence base. Read in full: migrations `0005` and `0006`, `search.ts`, `readable.ts`, `fts.ts`,
`tags.ts`, the `recipes.ts`, `service.ts`, `schemas.ts`, `save.ts`, `pipeline.ts`,

NOT done: I did not run `npm test`, lint, typecheck, Playwright, the mapper/import corpus, Docker or

`RecipeMeta`, `IngredientTextarea`, `RecipeForm`. I did not re-measure the performance numbers in the
checkpoint.

## Summary

The core is careful. Visibility is one shared predicate (`readableBy`) inside the same statement as
`MATCH`; the FTS query is built from `[\p{L}\p{N}\p{M}]+` tokens that are quoted by code, so there is
no injection path (I tried lone combining marks, superscripts and ligatures: no FTS error). The
migration path from a v0.3.2 database works: backfill produced the right rows, no marker row is left
behind, cascade delete removes the FTS row. The defer marker rolls back with the transaction. Tag
normalization is shared by client, schema, import and data layer. The units module is pure and
mostly well bounded. The busy-hint flow is small and consistent in both directions of an app/sidecar
version mismatch.

The weak spots are: a client race in the header search that can eat typed characters, a design choice
in `completeMeasures` that stores friendly-rounded derived values (up to 20 percent off, unmarked,
and compounding under scaling), a shared node budget in the microdata extractor that silently drops
steps on large pages, a future-dated migration timestamp, and some carryover wording that is stale.
No security or data-loss blocker.

Verdict: **PASS WITH CONDITIONS.** Fix M1 and M2 (or get an explicit owner decision to keep M2 as is
and document it), fix m4 (one line) before tagging. Everything else can ride.

Counts: 0 blockers, 2 major, 12 minor, 9 nits.

## Major

### M1. Header search can overwrite characters the user typed while a navigation is in flight
`src/components/search/SearchBox.tsx:178-184` (render-phase sync of `value` to the URL),
`:193-195` (`latest` reset every render), `:198-211` (debounce 250 ms then `router.replace`).

Scenario (read, not reproduced): the user types `ab`; 250 ms later `router.replace('/recipes?q=ab')`
starts; the server render takes, say, 300 ms (force-dynamic page, FTS, Pi-class box). During that
time the user types `c`, so `value` is `abc`. When the navigation commits, `urlQ` becomes `ab`, which
differs from `seenUrlQ`, so the render-phase branch runs `setValue('ab')` and the `c` is lost; the
effect at `:193` then also resets `latest.current.value` to `ab`, so the pending debounce for `abc`
applies `ab` again. The slower the server, the likelier this is, and it is exactly the slow-typing
case on the target hardware.

Why it matters: it silently changes what the user is typing and which results they see.

Suggestion: only follow the URL when the change did not come from this component. Keep a ref with
the last `q` this component pushed (`lastPushed`); in the sync branch skip when `urlQ === lastPushed`
or when the input is focused with a newer `value`. Add a component test with fake timers: type, fire
the debounce, type again, then change the mocked `useSearchParams` to the first value and assert the
input still shows the second.

### M2. Derived alternate measures are stored rounded to the friendly grid: up to 20 percent off, not marked approximate, and then scaled from the wrong base
`src/lib/units/complete.ts:288-289` (rounds with `roundMeasure` before storing), `display.ts:380-383`
(on-the-fly derive passes `round = true` and reports `approx`), `round.ts:205` (5 g step from 10 g).

Evidence (ran `completeMeasures` and `measureParts`): 1 tbsp sugar (12.5 g) is stored as `15 g`
(+20 percent); 3 tbsp sugar (37.5 g) as `40 g`; 3 tbsp butter (42.6 g) as `45 g`; 2 tbsp honey (42.6 g)
as `40 g`. For the same ingredient, the on-the-fly path used for pre-v0.4.0 recipes returns
`approx: true` (shown with "about"), the stored path returns `approx: false`. So new recipes show
`15 g` as if the author wrote it, old recipes show `about 15 g`. At 2x the stored side becomes 30 g
(true: 25 g) because `scaleIngredient` scales the stored, already rounded value.

Why it matters: this is a baking app, and the error is baked into the database where it cannot be
told from an entered value (C7 accepts "unmarked", but the carryover and the data model do not say
that the stored value is rounded and can be 20 percent off at small amounts).

Suggestion, in order of preference: (a) store the derived side with enough precision (round to 3
significant digits or to 0.1 g / 0.01 of a unit) and keep friendly rounding for display only, which
also removes the inconsistency with the on-the-fly path; or (b) keep the grid but use a finer step
below 100 g (1 g, which keeps tbsp-sized amounts within 4 percent); or (c) if the owner wants it as
is, say so in `data-model.md` §4 and C7 with the 20 percent figure. Add a table test that checks the
relative error of `completeMeasures` for the density rows from 1 tsp to 4 cups.

## Minor

### m1. Microdata extractor: the node budget is shared between the scope search and the build, so a large page silently loses steps
`src/lib/import/extract-microdata.ts:31-36` (one `Budget`), `:266-284` (`find` scans the whole
document for up to 20 scopes before `buildRecipe` runs).

Ran it: a Recipe scope followed by 5 000 `<li>` gives name, ingredients and steps; followed by 20 000
`<li>` gives name and ingredients only, no `recipeInstructions`, and no `microdata_node_cap` note
(the note test at `:281` does not fire because the counter stops at the first refusal). The user gets
a draft with no steps and no explanation. Real pages with large comment sections can approach this.
Fix: give `find` and `buildRecipe` separate budgets (or stop `find` after the first scope when the
page has JSON-less microdata), and emit the cap note when any `take()` returns false.

### m2. `itemtype` and `itemprop` are split on a literal space only
`extract-microdata.ts:51` and `:66`. HTML allows any ASCII whitespace. Ran it:
`itemtype="http://schema.org/Thing\nhttp://schema.org/Recipe"` is not recognised (returns null);
`itemprop="name\n"` is ignored (name lost). Use `split(/\s+/)`. The `tok.trim()` at `:52` shows the
intent. Pretty-printed templates do produce multi-line attributes.

### m3. Stale derived side on API edits is not documented
`src/lib/recipes/service.ts` `toTree` calls `completeMeasures` only when exactly one side is empty
(`complete.ts:278`). The natural API pattern is GET, change `metric_qty` from 100 to 200, PUT: the
stored derived US side comes back in the GET and stays, so the ingredient now says 200 g and 3/4 cup.
The UI path is safe (an edited ingredient line is re-parsed and drops stored sides, `form-model.ts`
`buildIngredients`). Carryover C7 mentions only density-table drift. Add one sentence to C7 and to the
API section of `data-model.md`: "when you change a quantity, clear the other side". Not worth code now
(the same marker that fixes M2 would let the server re-derive).

### m4. Migration `0006` has a hand-typed, future-dated `when`
`drizzle/meta/_journal.json:50`: `1794140000000` is 2026-11-08T12:13:20Z, a round number, a day after
today (2026-11-07) and after the real time of `0005`. drizzle's migrator applies a migration only if
its `when` is greater than the newest applied one. The next migration generated by drizzle-kit before
that instant gets a smaller `when` and is skipped without error on every database that already ran
`0006`. Harmless after tomorrow, but a trap for v0.4.1 if work starts early, and it will look like
"the migration did not run". Set it to a value above `0005`'s (`1794054275021`) and below now, for
example the real commit time; databases that already applied `0006` keep working because the check is
against the stored maximum.

### m5. `GET /api/recipes` limits count UTF-16 units, the rest of the feature counts code points
`src/app/api/recipes/route.ts:12-13`: `q.max(100)` and `tag.max(MAX_TAG_LEN)`. A valid 30-emoji tag
(60 units, 30 code points) is a 400 `invalid_query` when used as `?tag=`. The checkpoint and
`data-model.md` say "100 characters" / code points; `search.ts:24` and `/api/tags` use code points.
Use `.refine((s) => [...s].length <= N)`.

### m6. `author` accepts lowercase ULIDs that can never match
`route.ts:14-17`: the regex has `/i`, ids are stored uppercase, `eq(recipe.ownerId, ...)` is
case-sensitive, so `?author=01j...` returns an empty list with 200 instead of 400. Drop `/i` or
uppercase the value.

### m7. Review form puts the raw draft tags into the form state
`src/lib/recipes/form-model.ts:226` (`tags: d.tags`) while `FormState.tags` is documented as
normalized and `formFromRecipe` normalizes (`:188`). Draft tags are only `sanitizeText`ed
(`normalize.ts:157`), so the chip shows `Dessert`, and a tag the server will refuse (control or
format character) shows up and makes the first save a 422 the user has to decode. Use
`normalizeTagList(d.tags)` here; `save.ts:85` already does the equivalent for the key-absent case.

### m8. Density matcher false positives
`src/lib/units/density.ts:57,114-127`. Ran `findDensity`: `powdered milk` matches `milk` (the exclude
list has `powder`, not `powdered`; `100 g powdered milk` derives 0.41 cup, real value is about 0.75
cup), `date sugar` matches granulated sugar via the bare `['sugar']` phrase, `lemon juice and water`
matches `water`, `semolina flour` / `whole wheat flour` use the 125 g all-purpose figure (about 30
percent off for semolina). Only `powdered milk` is a clear bug (add `powdered`, `dried`, `instant`,
`evaporated` already there); for the rest, either accept and list in C8 or make the head-noun rule
stricter (reject names containing `and`/`or`, require the phrase to be the whole name for bare
`sugar`).

### m9. `ScaleControls` behaviour gaps
`src/components/recipe/ScaleControls.tsx`:
- `:38`, `:62`: after picking 2x and then Custom, the factor snaps back to the last `customFactor`
  (1 at first) with an empty box, so amounts change when the user only opened the field.
- `:56-60`: invalid custom text keeps the previous valid factor on screen while the error shows.
- `:90-98`: flipping units at factor 1 announces "Showing amounts at 1x: serves N", which says
  nothing about units; the live region never mentions metric or US.
- `:18`: `1,000` parses as 1 (only the first comma is replaced). Cannot matter with the 100 cap.
- `messages/en.json` `scale.invalid` states only the upper bound; `MIN_FACTOR` is 1/100.

### m10. Header search on a non-list page replaces the history entry
`SearchBox.tsx:204`. On a recipe page, typing two characters navigates (replace) to `/recipes?q=..`,
so Back does not return to the recipe. Consider `push` when `!onList` (and a longer debounce there),
`replace` only while refining on the list.

### m11. A microdata stub suppresses the headless fallback
`extract-recipe.ts` + `pipeline.ts` `noRecipeNode`. A page with an `itemscope` Recipe shell and the
real content rendered by script now returns a node (so no render is attempted) and ends as
`no_recipe` where v0.3.2 would have tried the browser. Narrow, but it is a behaviour change of the
trigger table; either note it in the carryover or treat a node with no ingredients and no steps as
"no node" for the trigger.

### m12. Dead code: `listRecipesForUser` and `RecipeListItem`
`src/lib/db/recipes.ts:220-244`. After the `searchRecipes` switch the only caller is
`src/lib/db/recipes.test.ts:175,178`. It is a second implementation of the list/visibility query,
and the test asserts visibility on the copy that production does not use. Delete it and point those
assertions at `searchRecipes(db, id)` (which `search.test.ts` already covers for the same behaviour).

- n1. `src/lib/db/schema.ts:285-286` define `MAX_TAGS_PER_RECIPE` and `MAX_TAG_LENGTH`, unused;

- n3. `DELETE FROM recipe_fts WHERE recipe_id = ?` (every trigger, `fts.ts:29`) scans the table because

- n4. `recipes.ts:259-261` repeats the marker SQL by hand in `deleteRecipe` instead of using the
  helper, without `try/finally` (safe only because the caller owns the transaction). Put an
  `withFtsDeferred(conn, id, fn)` variant that skips the reindex next to `withDeferredFts`.
- n5. No `drizzle/meta/0006_snapshot.json`. Fine (table is not in `schema.ts`), but a one-line comment
  in `0006` saying "no snapshot on purpose" would save the next person a search.
- n6. `TagInput.tsx:60-61, 67-87`: between keystrokes the previous prefix's suggestions stay visible
  until the new fetch lands (`shown` is computed from the old list, `open` stays true). Clear
  `suggestions` when `text` changes, or key them to the prefix they answer.
- n7. `docs/data-model.md:355` says the FTS covers "ingredient names and notes"; README says notes are
  not searchable. Say "ingredient notes (the text after the comma), recipe notes are reserved".
- n8. `ResultsStatus.tsx:398` prints the raw `q` from the URL in the empty state with no length bound
  (React escapes it, so only layout). Truncate to 100 characters like the search does.
- n9. The `role="status"` summary and the `role="alert"` error in `ScaleControls` fire together on
  invalid input; one live region is enough.

## What I checked and found sound

- `readableBy` in the same statement as `MATCH` (`search.ts:70,93`); tag filter is an `exists` joined to
  the already filtered recipe; tag counts and autocomplete join `recipe` with the same predicate; admin
  has no extra reach, as documented.
- `buildMatchQuery`: NFC, 100 code points, 8 tokens of 2 or more, quoted, prefix star added by code;
  an empty token list returns `[]`, never the table.
- Trigger design: static SQL, `AFTER UPDATE OF` column lists, `WHEN NOT EXISTS (marker)` on exactly the
  five child triggers, `recipe_fts_recipe_au` and `_ai` correctly not deferred. `withDeferredFts`
  clears the marker in `finally`; callers are inside `BEGIN IMMEDIATE`, so a crash or a 21st tag rolls
  everything back (a stale marker can only exist if someone calls the helper outside a transaction;
  the doc comment says not to).
- `setRecipeTags`: removals before inserts so a swap of 20 does not trip the limit; orphan cleanup in
  the same transaction; `onConflictDoNothing` plus re-select is safe under the immediate transaction.
- `normalizeTagName`: normalizes, lowercases, re-normalizes and measures last; rejects Cc, Cf (except
  ZWNJ/ZWJ), Cs, Co, Cn; the SQL CHECK is the backstop.
- Units: `convertAcross` checks dimension and density row; `deriveAlternate` returns `null` for counts,
  unknown units and same-system input; `scaleMeasure` clamps invalid factors to 1, never rounds a
  positive value to 0, flags approx above 2 percent or a fractional count; `completeMeasures` is
  idempotent (second call sees both sides and returns the input) and does not touch `displayPrimary`
  or `raw_text` (the raw text is composed before completion in `toTree`).
- Microdata: htmlparser2 only, literal `includes` pre-check, depth/node/item/text caps, `script`,
  `style`, `template`, `noscript` skipped, no regex over the document; deep nesting of 39 000 `<div>`
  took 137 ms (hostile input stays bounded). Output is plain data fed to the existing normalizer and
  sanitizers.
- Mapper change: `resolveStepHeadings` is shared by `groupSteps` and `normalize.ts`, so the "known
  headings" set and the grouping cannot disagree.
- `saveImport`: client `tags` win and are validated strictly (422), draft keywords are normalized
  leniently only when the key is absent, everything stays in the one immediate transaction with
  `markImportJobSaved`.
- `TagInput`: combobox roles and `aria-activedescendant` are consistent, IME composition guarded,
  `mousedown` keeps focus, requests are aborted and a stale result is dropped, chips are React text,
  44 px targets. `TagFilter`: server-rendered links, `aria-current`, no client state.
