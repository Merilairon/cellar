**Objective (quoted, milestone 05)**: "Finish the MVP: per-recipe visibility with public read-only links, a print-friendly grid view, JSON backup/restore, and release hardening."

**Technical context (quoted)**: "Fields `recipe.visibility` (`private|users`) and `recipe.share_token` (independent public link) exist from M2; copy and visibility endpoints too."

**Requirements 1 to 9 (quoted, in full)**
1. "**Visibility enforcement:** central `canView(user, recipe)` / `canEdit(user, recipe)` helpers used by every query and route (recipes, photos, notes, search, export). Tests for every combination (owner, other member, admin, anonymous)."
2. **Findings that change the plan (read before T2)**
1. **The helper names and the actor model change.** The spec names `canView`/`canEdit`; the code has `canRead`/`canWrite` without an anonymous actor. T2 renames (spec vocabulary wins, rule R3), adds `actor: null` (anonymous) and a share-token context, rewrites `access.test.ts` as the full 4 × 2 (× link on/off × env) matrix, and migrates all 13 call sites in the same task, as the spec's first instruction orders. `readableBy` stays the SQL form and a new test proves the two agree on every combination (finding 2).
2. **Two sources of truth for "may see" already exist** (`canRead` for single rows, `readableBy` for lists). The spec says "central helpers used by every query". Rewriting every list query to a per-row helper is not possible in SQL; the rule is instead: `readableBy` is the SQL projection of `canView` for a signed-in actor without a token, and a table-driven test enumerates (owner/other/admin) × (private/users) through both and asserts equality. Admin's by-id read reach on private recipes (`canRead` true, `readableBy` false) is an existing inconsistency: Q7 decides whether export follows the by-id rule (admin may back up everything) and T2 documents the asymmetry rather than silently changing list behavior.
3. **`Referrer-Policy: no-referrer` and the rate limit for `/r/:token` can only live in `proxy.ts`.** Pages cannot set response headers or a 429 status; `proxy.ts` already stamps every response and is the one place that sees `/r/*` before rendering. The proxy runs on Node (guide verified) but the repo's own lint rule bars `node:*` there, and the client-IP code needs `node:net`. T0 spikes this; Q4 decides the policy (recommendation: allow `node:net` for `proxy.ts` only, keep DB and argon2 out, and reuse `resolveClient` + `getRateLimiter`).
4. **`setRecipeVisibility` bumps `recipe.updated_at`.** The binding rule for this slice is "no change to `recipe.updated_at` from sharing actions unless the spec requires it" (the spec does not). New share-link writes never touch it. Whether the existing visibility write stops bumping is Q3; the recommendation (stop) also gives a clean definition of "imported, unedited" for the copyright warning: `source_url` set **and** `updated_at === created_at` (content writes are the only things that move `updated_at`; imports and copies create both stamps equal).
5. **The spec lists what the public page shows, and photos are not on the list.** Requirement 3: "read-only grid/list view (unit toggle and scaling allowed), source attribution, no private/shared notes, ratings, or editing controls". The photo route is authenticated; showing a cover on `/r/:token` needs a new token-scoped image route (`/r/:token/cover`) with its own scoping tests. Q2: recommendation is **no photos on the public page in v1.0** (smallest surface, no new image endpoint), alternative a cover-only token route.
6. **A dependency-free zip is feasible.** Node 24 has `zlib.crc32`; WebP photos are already compressed, so the export zip can use **stored** entries (no deflate) written by a ~150-line writer with tests (local headers, central directory, data descriptors not needed when sizes are known). Restore must read zips the app wrote (stored entries) and tolerate deflated ones via `zlib.inflateRawSync` for hand-repacked archives. Q6 records the alternative (`yazl`/`archiver`); the Cut line forbids cutting backup/restore, so the decision cannot be "later".
7. **"Admin: option for all" and "never other users' private data" collide** unless the admin full export is explicitly defined as the whole-instance backup (it contains private recipes and private notes by design, exactly like the volume backup). Q7 fixes the two export shapes; the member export is strict.
8. **A "fresh instance B" needs a fourth e2e server** with its own `DATABASE_PATH` and `UPLOADS_DIR` (same production build, port `3103`). The unit-level round trip (two in-memory databases) is required too; the docker two-container restore is a gate step, not automated.
9. **No migration and no new dependency** are the expected baseline facts for v1.0: `ls drizzle` ends at `0007_note_rating_thumb.sql` before and after; `git diff v0.4.2 -- package.json package-lock.json` empty (unless Q6 picks a library).
10. **The 2-weekend cap forces a split.** Permission refactor + sharing + public page + print is one honest slice; export/restore (a format, a writer, a reader of untrusted archives, a two-step UI, a second instance test) is another; hardening + security review + accessibility pass + docs + checklist is the third. Q1.

## One rule per topic (every other sentence in this file follows these)

- **R1 Device try (v0.4.2 Q1) timing**: still owner-pending, due before the **v1.0** tag, not blocking. Extended with: open a public link on a phone, print the sample recipe from a phone and a desktop browser, restore a backup from a phone browser. If not done by the v1.0 gate, the reality check says "NOT TESTED" again. Tracked as Q15 here.
- **R2 Question ids**: ids in this file are v1.0 ids and unique. A v0.4.2 id is written "v0.4.2 Qn" (for example "v0.4.2 Q1", the device try; "v0.4.2 Q15", upload throttling). A bare Qn means this file.
- **R3 Permission vocabulary**: after T2 the only names are `canView(actor, recipe, ctx?)` and `canEdit(actor, recipe)`; `canRead`/`canWrite` are deleted (no aliases survive). `readableBy` is the SQL twin for signed-in list queries and is tested to agree with `canView`. Anonymous is `actor === null` and can only ever satisfy `canView` through a matching, enabled share token.
- **R4 Uniform public 404**: `/r/:token` returns the same 404 page, status and headers for a malformed token, an unknown token, a revoked token, a token of a deleted recipe, and `PUBLIC_LINKS_ENABLED=false`. Token format is checked first (fixed length and alphabet), the DB lookup is by exact value, and the stored value is compared with `crypto.timingSafeEqual`. No other branch exists between request and 404.
- **R5 Sharing never moves `updated_at`**: share-link create, rotate and revoke never touch `recipe.updated_at`; visibility follows Q3 (default: stops bumping). The grid editor's `base_updated_at` and the newest-first list order are therefore unaffected by sharing.
- **R6 Ids**: a public link resolves a token to a **recipe id**; exports reference **positions** (`section.position`, `ingredient.position`, `step.position`, `row_start`/`row_end`) and never child ids; restore assigns fresh ids. Photos in a backup are referenced by relative path inside the archive, never by id.
- **R7 Backup `version`**: integer, `1` for this format. `migrateBackup(doc)` in `src/lib/backup/migrate.ts` is a `switch` on `version` that returns a v1 document or a typed failure; version `> 1` or not an integer fails with `backup_version_unsupported` carrying the found version; the UI shows "This backup was made by a newer Cellar. Upgrade this instance first." (string in `messages/en.json`).
- **R8 Never exported**: `user.password_hash`, `session`, `invite`, `password_reset`, `recipe.share_token`, `import_job` and raw HTML, any env value, and (in a member export) any other user's private note or individual rating. A test greps the serialized output for these.
- **R9 Visual baselines**: generated only by `scripts/update-visual-baselines.sh` on a committed tree, every PNG reviewed, listed with a reason.
- **R10 Strings**: every new UI string lives in `messages/en.json` (new namespaces `share`, `publicPage`, `print`, `backup`); `tests/unit/i18n-keys.test.ts` stays green; user-controlled text is rendered as React text.
- **R11 Public page = read-only components**: `/r/:token` renders `RecipeGrid`/`RecipeList`, `RecipeMeta` (source) and the scale/unit controls through a new `PublicRecipeView`; it never renders `RecipeView` (which carries Cook, Convert, editor, `router.refresh`, per-user storage) and never calls an authenticated API.
- **R12 Restore is untrusted input**: the archive and JSON are validated with strict zod schemas (unknown keys rejected, `__proto__`/`constructor` keys rejected, counts and string lengths capped), zip entry names are matched against `^photos/[0-9A-HJKMNP-TV-Z]{26}\.webp$` only (no slashes, no `..`, no absolute paths), image bytes go through `processImage` again (re-encode) or are refused, and nothing is written before the whole document validates.

**Out of scope for v1.0 (do not build)**
- PDF export, Schema.org/JSON-LD export, shopping list, meal planner, OIDC, bookmarklet, more languages, AI mapping (Release Plan Post-1.0 Backlog).
- Photos on the public page beyond Q2's default (none). Public comments, public ratings, public search or listing of shared recipes, "explore" pages, per-link expiry dates or passwords, link analytics or view counters, per-user share permissions, sharing with a named user, email sending.
- Restore into an **existing** recipe (merge/overwrite): only skip or rename (spec). Scheduled or automatic backups, remote/object storage, encryption of backups, incremental backups, backups of `import_job`.
- Print: custom page size settings, headers/footers, per-section page breaks beyond what the one-page landscape needs, PDF generation server-side.
- Logging: no log shipping, no log files, no log levels configurable per module beyond `LOG_LEVEL`; no metrics endpoint.
- Cover preview in the import review (v0.4.2 carryover item 5): deferred post-1.0 (Q14). `note_fts` rowid migration, pixel cap, thumbnail size (v0.4.2 section 1): deferred (Q14). Any new migration.
- Locales other than `en`.

**Hard rules**
- **Never cut backup/restore** (Release Plan cut line) and never cut the authorization matrix, the uniform-404 and constant-time tests, the redaction test (R8), the security review (T15) or the restore validation (R12).
- **Permission helpers first**: T2 is merged (code review done) before T3 starts. No new route is written against `canRead`/`canWrite`.

## Security note (new surfaces: anonymous read path, share tokens, export, restore, logs)

Assets: private recipes and private notes (other users'), share tokens (bearer secrets; possession = read), the instance's whole content (admin export), the file system (`UPLOADS_DIR`, restore staging dir), the single-threaded server (zip/JSON parsing, image re-encode on restore), search-engine exposure of copyrighted content (`noindex`), referrer leakage of tokens to linked source sites (`no-referrer`), logs as a secondary store of secrets. Attacker: anyone on the internet with or without a token (enumeration, timing, revoked-link reuse), a signed-in member probing others' private data through export or restore (IDOR on staged restore ids, owner spoofing in a backup file), a member uploading a hostile archive (zip bomb, traversal names, polyglot images, deep JSON, prototype-pollution keys), a CSRF page hitting share-link or restore endpoints, a reverse proxy misconfiguration exposing the app port.

Required controls (T8, T13 and T15 check each): token = 128 random bits from `crypto.randomBytes`, format gate then exact lookup then `timingSafeEqual` (R4); uniform 404 incl. headers and body for every failure branch; `Referrer-Policy: no-referrer` and `noindex` on `/r/*`; rate limit keyed by trusted client IP, 429 with `Retry-After`; `PUBLIC_LINKS_ENABLED` enforced server-side in `canView`, not only in the UI; share-link endpoints `canEdit` + CSRF + `no-store`; the token never in list responses, logs, error bodies or `referer`; revoke = NULL in one statement, effective on the next request (no cache: pages are `force-dynamic`, `no-store`); export: `canView` applied per recipe through the same helper (a member export is `owner_id = me`, never `readableBy`, so `users`-visible recipes of others are **not** exported by a member; Q7), R8 redaction test, `all=1` admin-only and logged; restore: body cap enforced while streaming, written to disk not memory, strict zod (`.strict()`, key denylist, max 5000 recipes / 200 sections / 400 ingredients per section / 400 steps / 200 notes per recipe / 10 photos per recipe per the existing limits, string lengths per `recipeInputSchema`), zip central directory parsed with bounds checks (entry count cap 60 000, uncompressed size cap per entry 20 MiB, total cap `RESTORE_BODY_MAX` × 1, no entry outside `photos/<ulid>.webp` or `backup.json`), every image re-encoded by `processImage`, staged-file ids are ULIDs owned by the uploader (404 otherwise), one restore in flight per process (409), `owner_id`/`user_id` never taken from the file in a member restore; logs: redaction test (G18); CSRF on every new mutating route (`authenticate`); `Cache-Control: private, no-store` on every new JSON response; no `dangerouslySetInnerHTML`; the Traefik example must not publish the app port.

Residuals to decide in the checkpoints: DB index lookup timing on the token (accepted: the comparison after lookup is constant-time and the token space is 2^128; Q16); unknown-client public route unthrottled when `TRUSTED_PROXIES` is empty (Q4); admin export contains others' private data by design (Q7); plaintext token at rest (Q16); restore trusts `processImage` as the image gate (same as uploads).
