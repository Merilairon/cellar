Scope: the new read paths in commits `abfa399..8ae0b31` on `release/v0.4.0`: migration `0005_search_tags.sql` (tables, FTS5 table, all triggers), `src/lib/db/search.ts`, `tags.ts`, `readable.ts`, `src/app/api/recipes/route.ts` (GET q, tag, author), `src/app/api/tags/route.ts`, tag persistence in `src/lib/import/save.ts`, `src/lib/recipes/tag-name.ts` and `schemas.ts`, and the unit derivation code under `src/lib/units/`. Timings are from this machine (in-memory SQLite, better-sqlite3).

## Verdict: PASS WITH CONDITIONS

No Critical finding and no visibility leak found. One High availability defect (F1: quadratic FTS trigger cost, a signed-in member could block the server for 12 to 23 seconds per request) and one Medium input defect (F2: invisible and bidi characters in tag names) were found and fixed in this checkpoint, with regression tests. One Low information-disclosure finding (F3: bm25 ranking depends on corpus statistics that include private recipes) contradicts the tasklist's residual-risk statement and is ticketed as carryover for an owner decision. T9 to T11 (UI) may start.

## F1 detail (High, fixed)

Reproduction (before the fix, 20 sections x N ingredients, valid per the 200/section limit, body under the 1 MB cap):

| Ingredients | Create | Update (PUT) |
| --- | --- | --- |
| 1000 | 0.93 s | 1.5 s |
| 2000 | 3.1 s | 5.6 s |
| 4000 | 11.8 s | 22.6 s |

Cause: migration 0005 fires `recipe_fts_ingredient_ai/ad` per ingredient row; each rebuilds the whole FTS row (aggregate over all ingredients, delete, insert) and the `DELETE FROM recipe_fts WHERE recipe_id = ?` scans the unindexed column. Replace and cascade delete fire it for every row again. better-sqlite3 is synchronous, so one request blocks every user for the duration.

Fix (migration `0006_fts_defer.sql`, `src/lib/db/fts.ts`, `src/lib/db/recipes.ts`):
- New table `recipe_fts_defer(recipe_id)`. The five ingredient/`recipe_tag` triggers get `WHEN NOT EXISTS (marker for this recipe)`. Without a marker they behave exactly as in 0005 (tested by a direct insert/delete of an ingredient).
- `withDeferredFts(conn, recipeId, fn)` sets the marker, runs the writes, clears the marker and reindexes once. Used by `insertRecipeTree` (create and import), `replaceRecipe` and `copyRecipe`. `deleteRecipe` sets the marker around the cascade (the recipe delete trigger removes the FTS row).
- Everything runs inside the caller's `BEGIN IMMEDIATE` transaction, so a failure (for example the 21st tag) rolls the marker back with the rest; tested.
- A new migration rather than an edit of 0005, so databases that already applied 0005 get the fix.

After: 4000 ingredients at 2000 recipes in the table: create 0.75 s, update 0.72 s, delete 11 ms (was 11.8 s, 22.6 s, 1.6 s). Regression test `search-security.test.ts` (4000 ingredients, create + update + copy + delete in under 8 s, index content exact, marker table empty). Remaining cost is the row inserts themselves, linear.

## F2 detail (Medium, fixed)

Before: `normalizeTagName('a​b')`, `'a‮b'` (RTL override), `'a⁠b'`, `'a­b'`, `'a\u{E0041}b'` and a lone surrogate were all accepted. Effects: two visually identical tags that never merge (autocomplete and filter chips duplicate), bidi spoofing of neighbouring text in chips. Not an injection (React renders text, SQL is parameterized), hence Medium.
After: rejects Cc, Cf, Cs, Co, Cn; ZWNJ and ZWJ stay (Persian, Indic scripts, emoji sequences); a leading BOM is trimmed as whitespace. Tests in `tag-name.test.ts`.

## F3 detail (Low, open)

`bm25()` IDF uses the document count and per-term document frequency of the whole `recipe_fts` table. Proof, user B owns two readable recipes, user A adds 30 private recipes:

```
A private docs with "frobnicate":  base [D1 D2 tied]  after [D2:-3.4876 D1:-3.3512]
A private docs with "blorptastic": base [D1 D2 tied]  after [D1:-4.7419 D2:-3.4876]
```

The order of B's two own results flips depending on which term occurs in A's private recipes. Only order is returned (no score), the attacker must craft probe recipes, and learns term presence/frequency but not owner or text. Severity Low for a household instance. The tasklist statement "ordering is computed only over readable rows" should be corrected. Fix options for the owner (C1): rank by corpus-independent weights (title hit > tags > ingredients > description, computed from the per-column match, newest first) instead of bm25; or accept and document.
