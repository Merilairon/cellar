# v0.4.1 Security Checkpoint (T14)

Scope: `git diff main..HEAD -- src/` on `release/v0.4.1` (HEAD `0ecaad6`): `PUT /api/recipes/:id/grid` (`src/app/api/recipes/[id]/grid/route.ts`), `updateGridFor` and `sectionsToTree` (`src/lib/recipes/service.ts`), `replaceGrid` (`src/lib/db/recipes.ts`), `gridInputSchema` (`schemas.ts`), the helpers in `http.ts`, and the client: `src/components/recipe/grid-editor/*` (save flow, leave guard), `src/lib/grid/editor/*`, `RecipeView.tsx`. Reviewed against the Security note and T14 in `v0.4.1-tasklist.md`, and the T3 early look (commit `6d769f1`). Review from a security-appsec-engineer perspective, code read plus unit/db tests only. Timings are from this machine (in-memory SQLite). No server, build or Playwright was run (port 3100 belongs to another agent).

## Verdict: PASS

No Critical, High or Medium finding. Two Low findings from the early look (L1 same-millisecond stamp, L2 body cap) are resolved in this checkpoint with tests. The three negative controls fail the expected tests. Residuals are listed below and need no owner action beyond what Q12 already accepted.

## Findings

| ID | Severity | Title | Status |
| --- | --- | --- | --- |
| L1 | Low | `replaceRecipe` (recipe form PUT) and `setRecipeVisibility` stamped `updated_at` with `nowIso()` and no strictly-later guarantee. A form PUT or visibility change in the same millisecond as the previous stamp left the value unchanged, so an editor holding that stamp as `base_updated_at` would pass the compare and overwrite the change (lost update). Real-world window is one millisecond, but it is the optimistic lock | Fixed: shared `stampAfter(prev)` (`src/lib/db/recipes.ts:69`) used by `replaceRecipe` (:176), `replaceGrid` (:218), `setRecipeVisibility` (:303). Test `grid.test.ts` "same millisecond still conflicts (L1)" freezes the clock; fails on the old code (verified in a scratch worktree), passes now |
| L2 | Low | The grid route used the default 1 MB cap; `SAVE_BODY_MAX` (256 KB) is used only by `/api/import/:id/save`, not by the grid route | Decided, not lowered. Measured: a 20 sections x 200 ingredients payload with short fields is 474,709 bytes and replaces in 657 ms; a 256 KB cap would reject legitimate schema-ceiling payloads. Cost is bounded by the row limits (4000 ingredients, 2000 steps), not by bytes; the cap only bounds memory and parse work. Now explicit: `GRID_BODY_MAX` (1 MiB, `http.ts`) passed in the route. Test `routes.test.ts` pins that the 475 KB payload is 200 (it used to accept 200 or 413) and asserts it is above 256 KB and below the cap; the existing oversize test pins 413 above 1 MB |
| I1 | Info | `GET /api/recipes/:id` (and its 4xx) carry no `Cache-Control`. The grid route and the list/tags errors are `private, no-store`; this older route returns the full recipe. The editor's "Load the latest" and the page use it | Open, ticket as carryover (one line: wrap with `noStore`). Not exploitable on its own (session cookie, private browser cache), parity with v0.4.0 F5 |
| I2 | Info | C7 duty is client-side: a non-primary side (`us_qty` / `metric_qty`) that is sent is stored as sent, so an authenticated writer can store inconsistent metric and US values for their own recipe | Accepted: documented in `updateGridFor`, tested (`grid.test.ts` "documented client duty"); affects only recipes the caller may already write; values are range-checked numbers, rendered as text |
| I3 | Info | NUL (`\u0000`) in names, titles and notes is accepted and stored as data (probe: 200, FTS rebuild fine) | Accepted: bound parameters, React text rendering; no consumer treats the value as a C string |
| I4 | Info | A header-link navigation while dirty is not guarded (documented gap, O6) | Accepted, already in the tasklist and `useLeaveGuard.ts` header |

## Negative controls (recorded once; run in a scratch git worktree, discarded afterwards; the working tree was never edited for them)

Files run: `src/lib/recipes/grid.test.ts`, `src/lib/db/recipes.test.ts`, `src/lib/recipes/routes.test.ts` (69 tests, all green on the real code).

1. Remove `enforce(opts.guard, row)` from `replaceGrid`: **2 fail**, both in `recipes.test.ts`: "replaceGrid > runs the guard on the stored row inside the transaction and writes nothing when it refuses" and "the guard wins over the conflict check". The service and route 403/404 tests still pass because `updateGridFor` also checks `canRead`/`canWrite` before the transaction (defense in depth); the in-transaction guard is therefore proved only at the db layer, and a service-level race (owner changes between the pre-check and the transaction) has no test, see "Not tested".
2. Remove the `base_updated_at` compare (`throw new GridConflictError`): **7 fail** in 3 files: `recipes.test.ts` "throws GridConflictError with the stored stamp and writes nothing on a stale base"; `grid.test.ts` "two saves with the same base: first 200, second 409", "a recipe-form PUT or a visibility change between load and save conflicts (G13)", "a tag-only change on the recipe form also conflicts"; `routes.test.ts` "409 on a stale base...", "a recipe-form PUT between load and save causes 409", "every response carries Cache-Control (table)".
3. Remove `validateRecipeGrid` from `updateGridFor`: **5 fail**: `grid.test.ts` "no_rows / row_out_of_range / span_required_for_grid / split_group_cross_section is reachable with the validator path and writes nothing" and `routes.test.ts` "422 with validator paths; an uncovered row is 200; unknown keys 422".

L1 regression: the new "same millisecond" test fails on the pre-fix `recipes.ts` (scratch worktree) and passes on the fix.
