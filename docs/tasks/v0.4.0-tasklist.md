## Specification Summary

**Source**: [milestones/04-search-edit.md](../../milestones/04-search-edit.md) (slice 4a only, requirements 1-4), [data-model.md](../data-model.md) (tag / recipe_tag, recipe_fts, §4 Unit Conversion & Scaling, user.unit_pref, §5 API), [RELEASE_PLAN.md](../RELEASE_PLAN.md), [TASK_ASSIGNMENTS.md](../TASK_ASSIGNMENTS.md) (v0.4.x table 04a rows, Gate, Per-slice workflow), [v0.3.2-tasklist.md](v0.3.2-tasklist.md) (format and conventions), [v0.3.2-carryover.md](v0.3.2-carryover.md) (items 11, 12, section 8), [v0.3.1-carryover.md](v0.3.1-carryover.md), [v0.3.1-code-review.md](v0.3.1-code-review.md) (m4, m5, m6, n1 to n5), [v0.3.2-code-review.md](v0.3.2-code-review.md).

**Objective (quoted, milestone 04)**: "Make the recipe collection usable day to day: search and tags, unit conversion and scaling, a visual grid editor, and photos/notes/ratings." Slice rule: "**4a (v0.4.0)** search, tags, units, scaling (requirements 1-4)."

**Requirement 1 (quoted)**: "Search: FTS5 index over title, description, ingredient names, tags, shared notes and the user's own notes; triggers keep it in sync; prefix matching; `GET /api/recipes?q=&tag=&min_rating=&author=`; results respect visibility. Search bar in header with debounce."

**Requirement 2 (quoted)**: "Tags: add/remove on recipe form with autocomplete; tag filter chips on `/recipes`; tags created from imports (keywords/category)."

**Requirement 3 (quoted)**: "Units: `src/lib/units/` with unit table, within-dimension conversion, small density table (flour, sugar, butter, milk, water, oil, honey, cocoa...), friendly rounding. Populate missing alternate measure at save/import time when determinable; `unit_pref` selects the primary display; per-recipe quick toggle."

**Requirement 4 (quoted)**: "Scaling: servings control (1/2x, 1x, 2x, custom) on the recipe page; recompute quantities client-side; times and temperatures are unchanged; show ≈ for rounded counts."

**Data-model §4 (quoted)**: "Canonical units: weight `g`, volume `mL`; US: `oz`, `lb`, `cup`, `tbsp`, `tsp`, `fl oz`; plus counts. **Within a dimension** convert exactly (4 oz -> 113 g; imported metric value wins if present). **Across dimensions** (cup <-> g) only via `density` table (flour, sugar, butter, ...); else keep the original and show no alternate. Scaling multiplies both measures by `factor = target_servings / servings`; rounding to friendly fractions for US and to 5 g / 1 mL steps for metric. Display uses the user's `unit_pref` as primary and the other in parentheses." Also §1: "Unit conversion, when it arrives, must convert both bounds" (ranges).

**Acceptance (quoted, 04a subset)**:
- "Searching 'espresso' finds the sample recipe by ingredient; a private recipe is not found by another user."
- "4 oz butter displays `115 g` when metric is preferred; scaling x2 shows `8 oz (230 g)` or the equivalent per preference."
- "Unit-conversion tests cover >= 30 cases including fractions and rounding."
- Instructions: "Implement units and scaling as pure, tested functions before touching UI." "All new strings go to `messages/en.json`; avoid user-facing hard-coded units/labels."

**Target pace**: 1-2 weekends (PM sizing below). Weekend 1 is pure units code, migration, tag and search backend, and the security checkpoint (no UI). Weekend 2 is UI, e2e, carried import fixes, docs and gate.

- Server-side scaling, persisting a scaled recipe, "save scaled copy", per-recipe persisted unit override (the toggle is local view state).
- Metric/US conversion of temperatures (`temp_c`/`temp_f` stay as stored; spec: unchanged).
- Non-metric/US units (cups of the Imperial variety, UK pints, Japanese cups), volume<->weight conversion for any ingredient outside the density table.

**Hard rules**
- Units and scaling are **pure functions with tests before any UI** (spec instruction). T1 and T2 land and are green before T7 and T11 start. No `Date`, `Math.random`, DOM, DB or `fetch` in `src/lib/units/`.
- Conversion never invents data: no density match -> no cross-dimension alternate; unknown unit text (`can`, `clove`, `pinch`, `to taste`) passes through unchanged; a user-entered or imported value is never overwritten by a derived one ("imported metric value wins if present").
- Search results respect visibility **in the SQL**, not by filtering afterwards: a recipe the actor may not read must never be selected, counted or ranked (acceptance: private recipe not found by another user). The same rule governs tag autocomplete and chip counts: tag names and counts are derived only from recipes the actor can read.
- User search text never reaches `MATCH` raw. Tokens are extracted, each quoted, and the prefix operator is appended by code; FTS5 operators (`AND`, `OR`, `NOT`, `NEAR`, `"`, `*`, `-`, `:`, `^`, parentheses, column filters) typed by a user are inert text. A test fuzzes this (T6, T8).
- FTS stays in sync through **database triggers** (spec wording), so every write path (create, replace, copy, import save, delete, cascade) is covered without remembering to call a sync function.
- The migration is data-preserving and idempotent, backfills the FTS index for existing recipes, and is tested on a v0.3.2-shaped database with rows (as `0004` was). No change to existing columns.
- No regex built from user input; bounded query length (100 characters) and token count (8); bounded result count.
- Fixed UI strings in `messages/en.json`; unit labels and `≈` handling via message keys or a units display map, not literals in components. One message per new error code.
- Conventional Commit after each numbered task, **no co-author trailers** (owner's global CLAUDE.md). No background processes or server start commands in task commands; the dev server and Playwright are run by the developer or CI.
- Out of scope held: no AI calls, no new runtime dependency, no weakening of the SSRF/sidecar controls.

## Security note (new read path)

Search adds a user-controlled string to a SQL `MATCH` and a new place where visibility must hold. Assets: private recipes (title, ingredient lists, tags can all leak through ranking or autocomplete), tag names of private recipes, query performance (a pathological `MATCH` or a huge result set). Attacker: any signed-in member, or an unauthenticated caller (401 first). Required controls: visibility predicate inside the SQL (T6), tokenize-and-quote query builder with no raw `MATCH` (T6), bounded query/tokens/results (T6), tag autocomplete and chip counts derived only from readable recipes (T4, T6), CSRF/auth unchanged (GET is authenticated, no state change), output rendered as React text (tag names, titles), no user data in SQL strings (parameter binding only; FTS `MATCH ?`). Residual: bm25 ranking could in principle reveal the existence of a private term through ordering, but ordering is computed only over readable rows, so nothing about unreadable rows is observable. Checked at T8.
