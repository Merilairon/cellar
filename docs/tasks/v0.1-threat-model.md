# v0.1 Threat Model and Security Review (Gate G-2)

Date: 2026-11-05. Scope: branch `release/v0.1` (T1-T11). Method: STRIDE per trust boundary, then a code review of the actual implementation against it. No code was changed.

**Verdict: PASS** (0 blockers, 3 major, 12 minor). Majors should be fixed or explicitly accepted before the v0.1 tag.

## 1. System and assets

Single Next.js 16 container (standalone, user `node`), SQLite (WAL) on the `app-data` volume, optional Caddy 2 reverse proxy with automatic HTTPS, an `admin:reset` CLI run through `docker compose exec`. Roles: admin and member. No recipe data exists yet.

Assets: account credentials (argon2id hashes), session tokens, invite and reset tokens, the admin role, SQLite file, `SESSION_SECRET`.

Attackers: anonymous internet client; invitee holding a valid invite; authenticated member; malicious website visiting a logged-in user (CSRF); someone with network access to the app port; someone with read access to a volume backup.

## 2. Trust boundaries

| # | Boundary | Controls |
|---|----------|----------|
| B1 | Browser to proxy/app | TLS (Caddy), HSTS when `BASE_URL` is https, SameSite=Lax HttpOnly cookie, Origin/Sec-Fetch-Site check on every mutating request, CSP with nonce |
| B2 | Caddy to app | Fixed IP `172.28.0.10`, `TRUSTED_PROXIES`, app port not published when `-f docker-compose.yml` is used |
| B3 | proxy.ts gate to handlers | Cookie-presence gate plus allow-list; authoritative checks in `getCurrentUser`, `requireAdmin` |
| B4 | App to SQLite | drizzle parameterized queries, BEGIN IMMEDIATE transactions for first-admin, register, reset, last-admin guards |
| B5 | Host operator to CLI | `docker compose exec` only; no HTTP surface; issues a single-use reset link |
| B6 | Build supply chain | `npm ci` with lockfile, native modules (argon2, better-sqlite3) per arch, multi-arch CI build |

## 3. STRIDE

| Threat | Component | Scenario | Existing control | Residual |
|--------|-----------|----------|------------------|----------|
| S | `/setup` | Anyone reaching a fresh instance claims admin | Closes after first user (race-safe) | **M1** open window, no secret |
| S | Login | Credential stuffing | Per-IP and per-email limits, argon2id, generic error, dummy verify | M2, m7 |
| S | Session | Token theft or guess | 256-bit random, SHA-256 at rest, HttpOnly, Secure iff https, SameSite=Lax | m4 |

## 4. Review results

### 4.1 Session handling (src/lib/auth/session.ts, cookies.ts)
Good: 32 random bytes, only the SHA-256 stored, expiry checked and expired row deleted, deactivated users rejected, sessions deleted on deactivate, delete and password reset, logout deletes the row and clears the cookie, hourly sweep. A fresh token is minted on login, so classic fixation is not possible (an attacker cannot plant a known token that becomes valid). Gaps: no `__Host-` prefix (m4), fixed 30-day lifetime without idle timeout (m9).

### 4.2 CSRF coverage
Mutating entry points found: `/api/auth/login` (login/route.ts:17), `/logout` (logout/route.ts:10), `/register` (register/route.ts:14), `/reset` (reset/route.ts:14), `/api/setup` (setup/route.ts:18), server actions `createInviteAction`, `createResetAction`, `deactivateAction`, `deleteUserAction` through `guard()` (admin/users/actions.ts:18), and `updateProfileAction` (profile/actions.ts:15). Every one calls `isCsrfSafe` before any state change. No GET handler mutates state; route files export only POST (and GET for health). Complete.

### 4.3 Invite and reset tokens
Hash at rest, 256-bit, expiry, single use, atomic consume inside BEGIN IMMEDIATE (db/invites.ts:48, db/password-resets.ts:48). Invalid, expired and used tokens render the same 404. Tokens travel in URL paths; `Referrer-Policy: same-origin` and no third-party resources keep them out of logs elsewhere. Argon2 is computed before the atomic check, so concurrent submits cost CPU but yield one user.

### 4.4 Enumeration
Login: same redirect and same argon2 work for unknown email, wrong password and deactivated user (login/route.ts:32-36). Residual: `email_taken` on register (m6).

### 4.5 Rate limiting and TRUSTED_PROXIES
Spike result in proxy-trust.ts is correct: Next does not expose the TCP peer, so trust is operator-asserted. Behind Caddy the right-most hop is the real client and cannot be forged. Problems are the default and the override footgun (M2, M3).

### 4.6 CSP and headers (security/headers.ts)
Nonce plus `strict-dynamic`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `unsafe-eval` only when not production (proxy.ts:23), HSTS when https, headers applied to redirects and 401s. `style-src 'unsafe-inline'` is a documented, accepted trade-off.

### 4.7 Container and secrets
Non-root `node`, multi-stage, no toolchain at runtime, `.dockerignore` excludes `.env*`, `.git`, `docs`. `SESSION_SECRET` is required by compose and rejected if a placeholder in production. Hardening options in compose are absent (m2).

## 5. Findings

### Blockers
None.

### Major

**M1. `/setup` takeover window.** `src/app/api/setup/route.ts:17-36`, `src/app/setup/page.tsx:14`. Anyone who can reach a freshly deployed instance, especially one on a public Caddy host, can create the admin. Fix: add `SETUP_TOKEN` (env, or random value logged once at startup when no users exist), require it in `setupSchema` and compare with `timingSafeEqual`; at minimum state in README that the operator must complete `/setup` before exposing the host, and bind first start to localhost.

**M2. Shared `unknown` bucket allows trivial lockout of all logins.** `src/lib/security/request-client.ts:22`, `src/lib/security/auth-limits.ts:15-19`, `proxy-trust.ts:91`. With the default empty `TRUSTED_PROXIES` every client shares one bucket, so 21 POSTs in 15 minutes to `/api/auth/login` block every user, admin included, and the same for register/reset/setup (10 per hour). Fix: for `UNKNOWN_CLIENT` skip the per-IP limiter and rely on the per-email limiter plus a high global ceiling (for example 10x), or make the unknown-bucket limit separately configurable; document it in README.

**M3. Override file auto-loads and defeats Caddy trust model.** `docker-compose.override.yml:4-6`, `docker-compose.yml:15`. `docker compose --profile caddy up` (without `-f`) publishes the app on `0.0.0.0:3000` while `TRUSTED_PROXIES=172.28.0.10`; clients can then send arbitrary `X-Forwarded-For` and, because the right-most hop is untrusted, get a fresh rate-limit bucket per request, and use plain http. Per-email limits still cap password guessing, so impact is limited. Fix: remove the override and use an explicit file or profile for direct mode (for example `docker-compose.direct.yml`), or at least publish as `127.0.0.1:${APP_PORT:-3000}:3000`.

### Minor

- **m1.** `SESSION_SECRET` is validated (`src/lib/env.ts:29-35`) and required by compose but used nowhere in `src`; sessions are random DB tokens. It implies a signing control that does not exist. Fix: remove it from required config, or use it (HMAC of cookie value / pepper) and say so in docs.
- **m2.** No container hardening in `docker-compose.yml:5-31`. Fix: add `read_only: true` with `tmpfs: [/tmp]`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `pids_limit`, `mem_limit`. Pin `node:24-bookworm-slim` (`Dockerfile:2`) and `caddy:2` (`docker-compose.yml:36`) by digest.
- **m3.** Direct mode listens on all interfaces over http (`docker-compose.override.yml:6`), so session cookies (not Secure) cross the LAN in clear. Fix: bind to 127.0.0.1 by default, document LAN use as http-only risk.
- **m4.** Cookie `Secure` depends only on `BASE_URL` (`src/lib/auth/cookies.ts:13`); a proxy deployment with an http `BASE_URL` silently yields non-Secure cookies. Fix: log a startup warning when `TRUSTED_PROXIES` is set and `BASE_URL` is http; consider the `__Host-` cookie prefix when https.
- **m5.** No body size limit on public POSTs (`formData()` at login/route.ts:23, register/route.ts:19, reset/route.ts:19). Fix: `request_body { max_size 64KB }` in `Caddyfile:7`; check `Content-Length` in handlers for direct mode.
- **m6.** `email_taken` reveals whether an email has an account to any invite holder (`src/lib/db/invites.ts:64-66`, `src/app/register/[token]/page.tsx:13`). Rate limited to 10/h per IP. Fix: return the generic invalid-input message, or accept as low risk for a family/friends app.
- **m7.** Per-email limiter increments before verification, so an attacker can keep a known account locked (`login/route.ts:27`), and the 10,000-key cap evicts oldest keys, letting a distributed attacker flush counters (`rate-limit.ts:51-53`). Fix: document as accepted; admin recovers via `admin:reset` (note that reset has its own bucket).
- **m8.** Auth for `(app)` pages relies on the layout (`src/app/(app)/layout.tsx:10`); layouts are not re-run on client navigation, so each future page and loader must call `getCurrentUser` itself. Today only profile and admin pages exist and both check. Fix: add a `requireUser()` data-access helper and use it in every page, route and action from milestone 2 onward.
- **m9.** Fixed 30-day session with no idle timeout or "sign out everywhere" (`session.ts:12`). Acceptable for v0.1; track for v0.2.
- **m10.** Supply chain: `npm ci` runs install scripts and native prebuilds are fetched at install time (`Dockerfile:12`); CI actions are pinned by tag, not SHA, and there is no `npm audit` or Dependabot (`.github/workflows/ci.yml`). Fix: add `npm audit --omit=dev --audit-level=high` and `npm audit signatures`, enable Dependabot, pin actions by SHA. The multi-arch native-module load check already in CI is good.
- **m11.** Any admin can issue a reset link for any other admin (`admin/users/actions.ts:44`, `resets.ts:17`), which is account takeover between admins, and there is no audit log. By design for a small trusted group. Fix: write a structured log line (actor, action, target) for invite, reset, deactivate and delete.
- **m12.** `next.config.ts:11` reads `BASE_URL` at build time; the Docker build has none, so `allowedOrigins` is never applied. Not exploitable because `isCsrfSafe` is authoritative and Caddy sets `X-Forwarded-Host`, but the config is dead. Fix: remove it, or pass `BASE_URL` as a build arg.

### Informational
- `/r/` is allow-listed as public (`src/lib/auth/routes.ts:15`) with no route yet (planned share links); recheck when share links (milestone 5) land.
- Behind Docker's userland proxy the client address Caddy sees may be the bridge gateway, collapsing all users into one bucket; verify on the target host.
- `admin:reset` abuse requires container exec on the host, which already implies full control of the volume; no extra control needed. It never reactivates deactivated users and always yields a single-use 1-hour link.
- Admin lockout: the last-admin guard is enforced inside the DB transaction for deactivate and delete (`db/users.ts:60-67`, `100-108`), so the system cannot lose its final admin through the app.

## 6. Test suggestions
Add e2e or unit tests for: POST without Origin/Sec-Fetch-Site returns 403 on each of the 5 routes; direct request with forged `X-Forwarded-For` when `TRUSTED_PROXIES` is empty stays in the shared bucket; `/setup` returns 404 after the first user; reset invalidates existing sessions (unit test exists).
