## Verdict: PASS WITH FIXES

No exploitable injection, no ReDoS in the mapper's own patterns, no prototype pollution, and the operation budget does stop the structural blowups. Open items: one budget undercount that allows ~300 ms synchronous CPU per call, a flaky wall-clock test, warning truncation that can hide codes, and a quadratic regex in `ingredient-parser.ts` that becomes reachable from the mapper's helper `ingredientsFromLines` (and already from paste). Nothing here blocks weekend 2 work, but F1, F2 and F3 must be fixed before T7 wires `mapGrid` into the pipeline.

## Checked and clean

- **ReDoS in mapper modules.** The only registered regexes are `^[\p{L}\p{N}\p{M}]$` and `^[\p{L}\p{N}]$`, both single-character anchored and run once per code point. No other regex literal exists in `map-*.ts`, `text-tokens.ts`, `ingredient-match.ts`, `step-verbs.ts`. No `new RegExp` anywhere in these files; ingredient names and step text are never interpolated into a pattern (Map/Set token matching).
- **Deep parentheses.** `parentheticalMask` is a stack plus difference array, linear. PoC with 1900-deep nesting x 100 steps, unbalanced `(` and `)` runs: 1 to 5 ms.
- **Unicode and offsets (v0.3.0 F2 class).** `tokenizeDetailed` normalizes (`NFKC` then `toLowerCase`) once, and all later offsets (`Token.start`, `markerBefore`, `qtyBefore`) index into `Tokenized.text`, the same normalized string. Temperature and duration extraction work on the original text but never use token offsets. PoC with `İİİ ﬃ stir 100 g sugar ...` (length changes from `İ` -> 2 code units and `ﬃ` -> 3) produced correct portions (`100 g` then `remaining` = 200). U+FDFA (NFKC expands 1 -> 18 code units) x 30 steps of 4000: 12 ms; normalization expansion is bounded by the 120k total-char cap (at most about 2.1M code units).
- **Prototype pollution.** Output objects are built from literals and spreads of fixed keys (`coerceIngredient`); input keys are never used as property names. `VERB_CLASS`, `PREP_OBJECTS`, `UNIT_ALIASES`, `SYNONYM_OF`, `byFirst` are `Map`s. Names/steps `__proto__` (tokenizes to `proto`, underscores are not word chars) and `For the __proto__:` (section title is data in an array) did not pollute. The single plain-object lookup is F5.
- **Unbounded output.** Ingredients capped 200, steps 100, step 4000 chars, total 120k, tokens per step 800, sections 6, warnings 60 (see F4), `portion_label` and `split_group_id` sliced. Warning payloads embed at most 200 chars of input (`ingredient_unmentioned:`, `ambiguous_name:` uses a token that must equal a name token).
- **Pattern/imports/clock guard.** Source scan forbids `Date`, `Math.random`, `eval`, `process`, `fetch`; mapper has no clock, so the budget is deterministic (determinism assertion `a == b` holds in all PoCs).
- **Stack/recursion.** No recursion over input depth. Largest spread is `push(...g.steps)` with at most 100 elements.
- **Shared-prefix blowup (many ingredients x many steps).** 200 names with 7-token common prefix x 100 steps of 790 tokens: budget trips at about 14 ms (default) and 24 ms even at a 10M budget. Good.

## Findings

### F1 (Medium) Budget undercounts per-mention work; about 300 ms per call at maximum input

`findMentions` (`ingredient-match.ts`) charges `spend(budget)` once per matched mention, but then does `[...best.v.byLevel[...]].sort(...)` and `ids.every(...)`, which cost O(k log k) where k is the number of ingredients sharing the matched variant (up to 200). `mapSection` Phase B adds `m.ids.filter(...)` per ambiguous mention (also O(k)). None of that is charged. With 200 ingredients named `w<i> s` (all level-4 candidates for the word `s`) and 75 steps of `"s " x 799`, there are about 60k mentions x 200 ids.

Evidence (`poc3.ts`, `poc4.ts`), result `mapped: true`, so the budget never fired:

```
F2 ambiguous 200 ings, 1-char mention     312 ms  (repeat: 254, 247, 257 ms)
F3 200 identical names, 1-char            363 ms
6 grouped sections, ambiguous             306 ms
```

The same shape appears in the repo's own bounds test (`200 identical ingredient names`, 132 ms alone, over half the 250 ms limit). The mapper runs synchronously on the request thread; a few concurrent imports of such a recipe stall the Node event loop. Not a hang, but it defeats the stated "budget is the guard" design.

Fix: charge the real cost.

```ts
// findMentions, after choosing `best`
const set = best.v.byLevel[best.level - 1]!;
spend(budget, set.size);                 // sort/every cost
const ids = [...set].sort((a, b) => a - b);
```

and in `mapSection` Phase B: `spend(budget, m.ids.length)` before `find`/`filter`. Also add a cheap cap: when `set.size > 8`, treat as `ambiguous` without sorting everything (the downstream only needs "open" candidates), or keep the sorted id list precomputed per Variant at the end of `buildIndex` (one sort per variant instead of one per mention). Add a bounds test for this exact input asserting `reason: 'budget'` or a time-independent operation count.

### F2 (Medium) Quadratic regex in `ingredient-parser.ts` `clean()`, reachable from `ingredientsFromLines` and paste

`const clean = (s) => s.replace(/\s+/g, ' ').replace(/^[\s,;:.-]+|[\s,;:]+$/g, '')` (line 161). The second alternative `[\s,;:]+$` is retried at every start position inside a long run of `,;:` or spaces that is not at the end of the string, giving O(n^2). `map-sections.ts` `ingredientsFromLines` passes lines to `parseIngredientLine` with no per-line length cap (it only caps the number of lines: 400). The parser is outside the file list and the source scan does not cover it, so the "every regex is linear" hard rule is unverified there.

Evidence (`poc6.ts`), `parseIngredientLine('1 cup flour' + ';'.repeat(n) + 'x')`:

```
n=10000   51 ms
n=20000  197 ms
n=40000  785 ms
n=80000 3145 ms     (4x per doubling: quadratic)
```

Paste allows `MAX_PASTE_CHARS = 500_000` characters (`paste.ts`), so one line of that length costs roughly two minutes of event-loop time. This is a v0.3.0 issue made reachable by the mapper helper; confirm whether the paste ingredient path in `normalize`/`paste` already hits it today (likely yes).

Fix: replace the trailing-trim alternative with a linear scan (strip leading chars from a set, strip trailing chars from a set with two index loops), or cap each ingredient line (for example 500 chars, matching `raw_text`) before parsing. Do both: cap in `ingredientsFromLines` (`line.slice(0, 500)`) and in `parseIngredientLine`. Add the 80k PoC as a regression test with an operation-free assertion (length cap) plus a generous time tripwire.

### F3 (Medium) Wall-clock assertions are flaky

`map-bounds.test.ts` asserts `a.ms < 250` for ten max-size cases and `ms < 20` for each registered pattern. The header comment calls these "regression tripwires", but they fail the suite. Reproduced with 16 busy loops running alongside the suite:

```
FAIL ... 200 identical ingredient names, steps naming them
  expected 4467.35 to be less than 250
FAIL ... 100 steps of 800 distinct tokens with 200 ingredients of 8-token names
  expected 1722.87 to be less than 250
```

Two of three loaded runs passed; unloaded the heaviest case takes 132 ms (see F1), so the margin is only about 2x on an idle machine. CI shared runners will hit this. The 20 ms pattern checks on 4000-char inputs of single-character-anchored regexes are also pointless (they cannot backtrack) and subject to GC pauses.

Fix: make the budget the assertion. Expose a deterministic counter (for example `mapGrid(input, { budget })` plus an optional `onStats` or return `used` in the failure and success results in a test-only way) and assert `used <= MAP_LIMITS.budget` and, for pathological inputs, `reason === 'budget'`. Keep one coarse wall-clock guard at 2 to 5 s, or gate wall-clock checks behind an env flag (`PERF_STRICT=1`) and retry-once. Drop the per-pattern 20 ms tests or raise to 200 ms.

### F4 (Low) Warning cap silently drops warning codes

`Warnings.list()` returns the first 60 of an insertion-ordered Set. `ingredient_unmentioned:<name>` is added for every unmatched ingredient (up to 200), so later, more important codes are cut. Evidence (`poc1.ts`): 1 matched + 200 unmatched ingredients and a step with two different durations gives `warnings.length === 60` and `time_ambiguous` absent (`false`). On the failure path, `mapping_invalid` is added last and can be cut the same way. Confidence and gating use `warn.has()` before truncation, so scoring is unaffected; the UI just under-reports.

Fix: collapse the data-carrying codes: keep at most N (for example 10) of each prefix family and add one summary code (`ingredient_unmentioned_more`), or reserve slots: output fixed (non-prefixed) codes first, then prefixed ones up to the cap. Add a test with 200 unmentioned ingredients that still includes `time_ambiguous` and, in a failing case, `mapping_invalid` / `mapping_budget`.

### F5 (Low) Plain-object lookup `IRREGULAR[w]` in `singularize`

`text-tokens.ts` declares `const IRREGULAR: Record<string, string> = {...}` and does `IRREGULAR[w]`. For the word `constructor` (length > 3, lowercased token) the lookup returns `Object` (inherited), so `singularize` returns a function. Evidence (`poc1.ts`): `typeof singularize('constructor') === 'function'`; `nameTokens('constructor')` is `[ [Function: Object] ]`; an ingredient named `constructor` yields `split_group_id` = `split:function Object() { [native code] }:0`. It does not pollute and matching still works by reference equality, but it breaks the `string[]` type invariant, and a name with that token will join as `function Object() { [native code] }` in `rowKey`, so two different ingredients that both normalize to a function would compare equal keys. `__proto__` cannot occur because `_` is not a word character, and other inherited names are camelCase (lowercased tokens miss them).

Fix: `const IRREGULAR: ReadonlyMap<string, string> = new Map([...])` and `IRREGULAR.get(w)`. Strengthen the existing "hostile names" test to assert correct mapping of an ingredient called `constructor` (it currently only asserts no throw).

### F6 (Low) Caller-controlled budget is not clamped

`run()` accepts any finite positive `opts.budget`. With `budget: 1e12` the shared-prefix input that normally fails at 14 ms runs to completion in 199 ms (still bounded by the input caps, so not an unbounded hang). Today only tests pass `opts`; T7 must not expose it to request data.

Fix: `limit = Math.min(MAP_LIMITS.budget, Math.floor(opts.budget))`; test-only larger budgets can use a separate internal parameter.

### F7 (Low) Lone surrogates from slicing

`fallbackLabel` (`.slice(0, 24)`), `coerce`/`str` (`.slice(max)`), and the 4000-char step cut can split a surrogate pair. Evidence (`poc7.ts`): label `xxxxxxxxxxxxxxxxxxxxxxx\ud83d` (`isWellFormed() === false`), ingredient name and truncated step `detail` also ill-formed, and `mapped: true` (zod accepts them). Downstream effects are mostly cosmetic (SQLite or JSON encoders replace with U+FFFD) but "detail is verbatim" can silently break and ill-formed strings can break TextEncoder or some renderers.

Fix: reuse the `capCodePoints` approach from `sanitize.ts` (drop a trailing high surrogate) in `str()`, `fallbackLabel`, the step-length cut and the 40/60-char slices, or call `s.toWellFormed()` after slicing.

### F8 (Info) Test and scan gaps

- The source scan's "regex-taking string method" rule only matches `.replace(/` style literals directly in a call. A new bare regex literal (`const R = /(a+)+$/; R.test(x)`) would pass unless registered with `pattern()`. Add a rule that flags any regex literal outside `map-patterns.ts` / `pattern(` calls, for example by scanning for `/[^/\n*]+/[dgimsuvy]*\s*[.,)]` after stripping comments and strings, or use an ESLint `no-restricted-syntax` rule on `Literal[regex]` in these files.
- `ingredient-parser.ts` is imported by `map-sections.ts` but is only checked for forbidden imports, not for regex safety (see F2). Add it to the ReDoS fuzz scope: run `parseIngredientLine` and `toIngredientFields` against the adversarial strings used in `map-bounds.test.ts` plus long runs of `;`, `:`, `,`, spaces and digits.
- No test pins the İ / NFKC offset behaviour (v0.3.0 F2 class). The code is correct today; add a golden case: `'İİİ ﬃ stir 100 g sugar'` with total 300 g and a later `remaining` step must give portions 100 and 200, and a `half` marker after `İ` must resolve.
- The `registers at least the known patterns` test only requires 2 entries; it will not notice a regex added without `pattern()`.
