## Summary

The core is in good shape. The span arithmetic is correct for move, delete, insert and split
(I walked the boundary cases: delete of the first, last and only row of a span, insert at
`start`, `end` and `end + 1`, split at both edges) and every function returns the same reference
when nothing changes, which the identity-based dirty check depends on. History is small and
right: coalescing is gated on an explicit key, `markSaved` clears the group, undo and redo clear
it, the cap trims `past` only. Client keys are monotonic (`nextKey` never decremented), so undo
cannot hand out a key twice. The server side is tight: the stamp compare and the write share one
`BEGIN IMMEDIATE` transaction, the visibility guard is re-run inside it, `GridConflictError`
rolls back, and the schema is strict so recipe fields, tags and ids are rejected, not ignored.
`stampAfter` is used by all three updating writers of the recipe stamp. The Delete-with-Undo
toast is scoped to the exact document the delete produced, which is a nice way to make a stale
Undo impossible.

The weak spots are all in the save and leave plumbing: 422 errors are mapped onto a document
that may have changed while the request was in flight, the "is this still the sent document"
check reads a ref that is updated in an effect, and the leave guard has a few unverified
assumptions about Next's popstate handling. None is a blocker.

Verdict: **APPROVE WITH CHANGES.** Fix M1 and M2 (both a few lines in `useSaveFlow.ts`) before
tagging; the rest can ride into the carryover.

Counts: 0 blockers, 2 major, 12 minor, 9 nits.

## Major

### M1. 422 errors are mapped onto the current document, not the document that was sent
`src/components/recipe/grid-editor/useSaveFlow.ts:127-129`.

The request body is built from `sent` (line 101). On a 422 the paths in `errors[]` index into
`sent`, but they are resolved with `mapServerErrors(doc(latest.current), ...)`, and
`rejected.doc` is set to that same current document, so the "only while the document is the one
they were mapped against" guard at line 195 passes.

Failure scenario: save with a (server-only) rejection, for instance a limit the client mirror
does not catch; while the request is in flight the user deletes row 1 of section 0. The 422
says `sections.0.ingredients.3.name`; it is resolved against the new document where index 3 is
the old row 4. The error is shown on, and focus goes to, the wrong row, and it stays until the
next edit. The reverse (index out of range) silently drops the target, leaving a count in the
toolbar with nothing to go to.

Suggested fix: map against `doc(sent)` and store `{ doc: doc(sent), errors }`. The existing
`rejected.doc === doc(editor)` guard then hides them automatically when the user has moved on,
which is the intended behavior. Add a unit or component test that edits during a mocked 422.

### M2. "Still the sent document" is decided from a ref that is updated in an effect
`useSaveFlow.ts:77-80` (`latest.current` set in `useEffect`), `:119`
(`if (doc(latest.current) === doc(sent)) dispatch({ type: 'markSaved' })`).

`markSaved` in the reducer marks whatever `history.present` is at reduce time, while the guard
compares a ref that lags the state until passive effects have run. If an edit is dispatched and
the response is processed before that edit's render and passive effects have flushed, the guard
passes and the reducer marks the NEW document as saved. The result is a clean indicator, a
disabled Save and a Done button that closes without asking, over an edit the server never saw.
For discrete events React flushes effects synchronously, so the window is small, but the
consequence is silent data loss and the fix is cheap. The same lag affects `save()` reading
`latest.current` (line 101) if Save is triggered in the same tick as an edit.

Suggested fix: make the check atomic in the reducer. `{ type: 'markSaved', doc: sentDoc }` that
only applies when `history.present === action.doc` (the history module already compares by
identity). Then `latest` is only needed for `save()`'s read, which can also come from a
`useReducer` state ref updated during render (`latest.current = editor` in the render body is
acceptable here) or from passing the editor into `save`.

## Minor

### m1. Discard (and Done after Cancel) while a save is in flight still saves
`GridEditor.tsx:359` (`onClose` on Discard), `:366-370`; `useSaveFlow.ts:111-123`.
The toolbar stays enabled while `flow.saving`. Cancel, Discard changes: the editor unmounts but
the PUT completes and `RecipeView.onRecipe` stores the result, so the user's explicitly
discarded edits are persisted. Fix: disable Cancel/Done while `saving` (cheap), or ignore the
outcome with a mounted flag and say so. At minimum drop the Discard path from the in-flight
window.

### m2. Leave guard: unverified assumptions and a counter that is not balanced in cleanup
`useLeaveGuard.ts:28-38`, `:61-68`.
(a) The unmount cleanup calls `history.back()` without bumping `skip`. Today the listener is
already removed, so the late popstate is harmless in production. In dev, Fast Refresh re-runs
all effects: cleanup pops the entry (`back()`), effect 1 pushes it again, and the popstate for
the earlier `back()` arrives at the freshly re-attached listener with `skip === 0` and an entry
set, so it is treated as a user Back and opens the leave confirm spuriously. Same shape with
React strict mode if the editor ever mounts dirty. Fix: increment `skip` in the cleanup path or
keep the guard's state in one place that is not re-created.
(b) If a `history.back()` we issued produces no popstate (the user already traversed away from
the entry, or the browser refuses), `skip` stays at 1 forever: the guard is silently off for the
rest of the editor's life and swallows one real popstate. Suggest a timeout reset or comparing
`history.state` with a marker object (`pushState({ geGuard: true }, '')`) instead of counting.
(c) Next's App Router also listens to popstate. `pushState(null, '')` replaces the state Next
keeps on that entry; the code relies on Next ignoring a null state and on a pop back to the real
entry being a no-op for the router. I could not verify that there is no router restore, scroll
reset or refetch when the guard entry is popped (it happens on every Back attempt and when a
save makes the document clean, right after `router.refresh()`). The e2e leave-guard test covers
the happy path of that, so this is a question for the author, not a defect. Please state the
Next version/behavior this was checked against in the file comment.
(d) Not covered by the e2e test: two quick Backs, and Back while a save is in flight.

### m3. `issuesFor` re-validates the whole document on every document change
`GridEditor.tsx:59`, `issues.ts:72-115`.
`issuesFor(d)` rebuilds the full payload, runs `validateRecipeGrid`, then runs
`sectionInputSchema.safeParse` per section. It runs for every commit, and text edits commit per
change. At the schema ceiling (20 sections x 200 rows) that is thousands of Zod object parses
per keystroke on the main thread. Sections are structurally shared, so untouched sections have
the same reference: memoise per section with a `WeakMap<EditorSection, Issue[]>` (the grid-level
cross-section check is cheap). I did not measure it; `perf-sanity.ts` measures the server.

### m4. `useMediaQuery` is called once per row
`RowControls.tsx:50`. Each row creates its own `matchMedia` and listener through
`useSyncExternalStore`. With 200 rows per section that is hundreds of subscriptions. Read it once
(`useStepWiring` already does) and pass `isPhone` down, or use one module-level store keyed by
query.

### m5. Row delete and split change quantities in ways the user does not see
`reducer.ts:291-299` (delete), `:323-333` (split).
Deleting one portion of a split pair strips the group and label from the survivor but keeps its
HALVED quantity, so the recipe silently loses half the ingredient (the Undo toast is the only
safety net). Consider restoring the pre-split total when the last sibling goes, or announcing it.
Split rounds each half to 4 decimals (`half`), so 1/3 + 1/3 does not equal the original. The
labels `'half'` and `'remaining'` (lines 324, 337) are English literals stored in the database,
not i18n keys; fine while only `en.json` exists, a data migration problem the day a second
locale is added.

### m6. Moving a row can stretch a step over unrelated rows
`spans.ts:32-46` (hull). A step covering rows 2 to 4, with the row at index 3 moved to index 0,
gets the span 0 to 4 and now covers two rows it never covered. This is the documented Q1
behavior ("hull of the new positions"), and the announcement only reports newly uncovered rows,
never newly covered ones. Please confirm the owner accepted the silent growth, or announce
"Step X now covers rows a to b".

### m7. Undo coalescing has no time or focus boundary
`history.ts:21-25`, `useStepEditing.ts:273` (`groupKey: step.key:field`).
Any later edit of the same field of the same step merges into the same undo entry, however much
time and other interaction (focus elsewhere, selection changes, saves excepted) happened in
between. Undo then removes minutes of typing at once. Cheap fix: reset the group on `select` or
blur (a `closeGroup` action), or add an injected timestamp with a gap. Also note that
`sectionRename` accepts a `groupKey` but no caller passes one, so renames are one entry per
commit; that is consistent but the parameter is dead.

### m8. Span drag details
`useSpanDrag.ts:28`, `:63-68`, `:56-60`.
(a) `TOOLBAR_INSET = 56` is a constant, but the toolbar is `flex-wrap` and takes two rows on
narrow widths, so the top auto-scroll zone can sit under the toolbar. Measure the toolbar.
(b) `rects()` runs `querySelectorAll` plus `getBoundingClientRect` on every pointermove and
every animation frame while auto-scrolling, forcing layout each time. Cache rects at drag start
and offset by scroll delta.
(c) If `setPointerCapture` throws, the code continues with listeners on the handle only, so a
real drag leaves the handle's bounds and silently stops getting events until pointer-up fires
elsewhere (never). Treat a failed capture as a failed drag start for real pointers.
(d) Cleanup itself looks right: `finish` is idempotent, removes all five listeners, cancels the
frame, releases capture, and the unmount effect plus `teardown` cover the unmount-mid-drag case.

### m9. Reducer is run twice and keys are predicted from a possibly stale closure
`useStepEditing.ts:88-98` (`apply` pre-reduces `editor`, then dispatches), `useRowActions.tsx`
(`setEditing({ key: newKey(editor.nextKey), ... })` after `rowAdd`, also in `finishEdit`
`addBelow`). The announcements and the "new row" key are computed from the render-time `editor`,
while the dispatch is applied to the latest reducer state. Two actions in one render (key repeat,
`rowEditText` then `rowAdd` in `finishEdit`, which does rely on the second seeing the first)
can produce a wrong announcement or a wrong predicted key. It is correct today because
`nextKey` is only bumped by `rowAdd`/`rowSplit`/`stepAdd`/`sectionAdd`, but the coupling to
`newKey(nextKey)` is implicit. Suggest having the reducer expose the created key (selection
already carries it: `selection.rowKey` after `rowAdd`) and reading that on the next render.

### m10. e2e source-check specs can pass vacuously
`tests/e2e/grid-editor-keyboard.spec.ts:36-37`, `grid-editor-mouse.spec.ts:37-40`.
`src.slice(src.lastIndexOf('// ----' + ' body'))`: if the marker comment is edited or removed,
`lastIndexOf` returns -1 and `slice(-1)` is the last character of the file, so the banned-word
check scans nothing and passes. Assert `idx >= 0`. The check also only reads its own file: the
shared helpers (`grid-editor-support.ts`, `helpers.ts`, `registerViaInvite`) and
`evaluate(() => el.click())`, `dispatchEvent('click')` and `keyboard.insertText` are not in the
banned list either. A plain string scan is a guard against
accidents, not a proof; the test name overstates it. Consider an ESLint `no-restricted-syntax`
override per file instead, which sees the AST and covers imports.

### m11. Serial groups, CI retries and `beforeAll` side effects
All ten `grid-editor-*` specs use `describe.configure({ mode: 'serial' })` with a
`beforeAll` that registers a user and creates one shared recipe, and `playwright.config.ts:12`
sets `retries: 2` on CI. In serial mode a retry reruns the whole group including `beforeAll`:
`registerViaInvite` for the same identity a second time may fail or collide (I did not check the
helper's idempotence), and one failure skips every later test in the file so a single flake hides
the rest of the file's results. Tests in the recreation specs also depend on state left by the
previous test. Use per-spec unique emails/titles (a run id), make registration idempotent, and
prefer one fresh recipe per test where the cost is acceptable. Also `grid-editor-save.spec.ts:220`
asserts the Tailwind class `/bg-emerald/` for "primary button"; a role/aria or `data-` hook would
survive a restyle.

### m12. A successful save with an unreadable body is reported as a network failure
`useSaveFlow.ts:111-123`, `:143-146`. A 200 whose body fails `res.json()` or lacks
`updated_at` falls through to `phase = 'network'` with a Retry. The write already happened, so
Retry sends the old `base` and gets a 409 against the user's own save. Rare (a proxy that
rewrites the body), but the recovery path is confusing. Treat a 200 with a bad body as "saved,
reload to continue" or fetch `GET /api/recipes/:id` to get the stamp.

## Nits

  the server prop wins on equal or newer, so a later visibility change from `OwnerActions` is not
  masked). It is only correct while `stampAfter` keeps producing `toISOString()` output; a one-line
  comment at the comparison stating that assumption would protect it.
- `GridEditor.tsx:52`, `:429`, `:449`: the header comment and two `SEAM T7/T8` markers describe
  work that is done or cut ("Move up / down" for sections has a reducer action `sectionMove` and
  no UI). Remove the markers; either wire section reorder or drop the action and its tests.
- `GridEditor.tsx:92`: the `setTimeout` in `announce` is never cleared on unmount.
- Dead or test-only code in `src`: `hasErrors` (`issues.ts:117`, unused), `coverageNames`
  (`spans.ts:132`, unused outside tests), `rowsCovered` and `mapMovedRow` are exported but used
  only inside `spans.ts`, `run` (`reducer.ts:631`), `sample-recreation.ts` (114 lines, imported
  only by `payload.test.ts`) and `fixtures.ts` (tests only). Move the last two next to their tests
  or under `tests/`; drop the unused exports.
- `useFocusLater.ts:17-26`: the effect has no dependency list, so it runs after every commit of
  the editor even when nothing is pending (one ref read, so cheap, but it is the hot path while
  typing). Guard with a `pending` state bump or run it from the commit that set it.
- `useStepWiring.tsx` and `useUndoToast.tsx` exist to keep `GridEditor.tsx` short and have one
  caller each. They are fine as organization, but the real size problem is the six hooks that all
  take the same `{ editor, dispatch, announce, root, focusLater, showToast, t }` bag; a small
  `EditorContext` would remove the prop plumbing and the stale-closure risk in m9.
- `service.ts` `updateGridFor`: `validateRecipeGrid` runs once for the 422 check and again inside
  `defaultViewMode` (`:293-296`). Also `defaultViewMode` always recomputes, so a PUT to `/grid`
  turns a stored `list` into `grid` when the spans are valid, unlike `updateRecipeFor`, which
  keeps a stored list. The editor is only offered on grid recipes, so this is reachable only by
  API; state it in the endpoint's comment or keep the stored value.
- `globals.css`: the dark palette is written twice (`:root[data-theme='dark']` and the
  `prefers-color-scheme` block, lines 38-59 of the addition). It matches the existing pattern, but
  twelve tokens in two places will drift; define them once with `color-scheme`/`light-dark()` or
  a shared selector list. `--ge-page` hard-codes the body background so the sticky toolbar can
  hide what scrolls under it; if `bg-white`/`bg-neutral-950` changes, the toolbar shows a stripe.

  allocates keys correctly (`grouped ? nextKey : nextKey + 1`).
