# v0.4.1 grid editor: persona usability walkthrough (T11)

Status: expert walkthrough by an agent, branch `release/v0.4.1`, after T9 (editor, phone sheets, save flow).

## 1. Read this first: what this is and is not

- **This is an agent walkthrough of the code, the UX spec and the message catalog. It is NOT user testing.** No real person used the editor. Marie, Tom and Jan below are the personas from `docs/user-journeys.md`, played by the agent.
- **It is NOT real touch.** Nothing was run on a phone or tablet. "Phone", "tablet" and "desktop" mean the layout the CSS and media queries select (phone < 640 px, tablet 640 to 899 px, desktop >= 900 px), reasoned from `src/components/recipe/grid-editor/*`, `globals.css` and `messages/en.json` (`gridEditor.*`). Nothing was built, served, or driven with Playwright (the port is in use by another agent).
- Findings are **likely problems**, each with the file or string key that supports it. Items marked "verify" depend on rendering or focus behaviour I could not observe. Step counts are counted from the code paths, not timed.
- Not covered: real fingers (drag accuracy, handle reach, scroll vs drag conflicts), on-screen keyboards, iOS Safari / Android Chrome quirks, screen readers (T12), real family members, time on task, visual density measured in pixels. The owner's 15-minute real phone and tablet try (Q11) remains the only evidence for those.
- The tasklist names the output file `v0.4.1-usability.md`; this file is `v0.4.1-usability-check.md` as requested. Reconcile the name when the tasklist is ticked.

Severity follows the tasklist: **S1** blocks a task, **S2** serious friction or data-loss risk, **S3** polish. **No S1 was found.** Every persona task can be completed by the paths in the code.

## 3. Task walkthroughs

### 3.1 Marie, phone: fix one wrong span (imported recipe)

Entry: a low-confidence import was saved as a list ("Could not map reliably"), so Marie (or Jan for her) first used **Convert to grid**, then "Saved as a grid." + **Fine-tune in the editor** (`gridEditor.entry.savedAsGrid`, `fineTune`; transient, lost on reload) or later the **Edit grid** button (`gridEditor.entry.edit`).

| # | Action | What she sees | Concern |
| --- | --- | --- | --- |
| 1 | Tap **Edit grid** | Editor: heading, two muted lines (`scope`, `asWritten`), two-row sticky toolbar, then the section header with Rename / Delete section / Add row / Add step / Add top banner / Add bottom banner | F9: lots of chrome before the table |
| 2 | Scroll to the wrong step, scroll sideways (ingredient column is sticky) | Step cells with the label | Long imported labels may truncate (verify) |
| 3 | Tap the step cell | Step selected, bottom sheet at 55 dvh: Start row / End row steppers, "Covers N rows", list of covered names, "Step details" closed | Good: no keyboard, live highlight behind |
| 4 | Press `-` / `+` on Start and End | Value text "Row 3 of 9, eggs" | **F1**: `-` means "grow" on Start but "shrink" on End |
| 5 | **Close** | Focus returns to the step cell | Fine |
| 6 | **Save changes** | Toolbar says "All changes saved" (`toolbar.clean`); editor stays open | F8: needs a second tap on Done |
| 7 | **Done** | Back to the read view | |

Estimated taps: 5 fixed + one per row moved. **Task success: likely, completed in about 7 to 9 taps.** Risks: F1 (wrong direction), F2 (Android back or a header link loses edits), F9 (chrome pushes the table down), F10 (tapping an ingredient opens a text editor + keyboard).

Mistake recovery: she overshoots a row. The sheet steppers are individually undoable; after Close, the toolbar shows **Undo** with the action in its name (`toolbar.undoWith`, "Undo: changed the rows of a step"). Discoverability is good (always visible, text label, not only an icon). She can also just press the opposite stepper. Verdict: strong.

### 3.2 Tom, tablet: build a two-part recipe (Cake / Frosting)

Precondition (spec F1/Q5): a grid recipe must already have at least one column step. A recipe Tom built in the form with ingredients and steps is a list until he uses **Convert to grid**; then **Edit grid**.

| # | Action | What he sees | Concern |
| --- | --- | --- | --- |
| 1 | Edit grid; section header says **Section 1** (fallback for an untitled section) | | F5/F6: the single section is called "Section 1", not the recipe name |
| 2 | **Rename**, type "Cake", Enter | Inline field in the heading, focus returns to Rename | Good (Escape cancels, Enter commits) |
| 3 | **Add section** (bottom of page) | New section titled **"Section 2"**, empty, focus on its **Add row** which immediately opens a text field | F5: title is stored as the literal "Section 2" (`useSectionActions.add` passes `t('recipe.section')`); Rename is not offered |
| 4 | Scroll up to its heading, **Rename**, "Frosting" | | One more hop than needed |
| 5 | Type ingredients: "200 g butter", Enter, then **Add row** again for each | Parsed preview "Parsed as: ..." after 200 ms | F7: Ctrl+Enter (add next) is invisible to touch and unhinted; each row costs a tap on Add row |
| 6 | **Add step** | New step "New step" covering only the first uncovered row (`defaultSpan`), selected, label field focused | F4/F3 below |
| 7 | Resize: tap the step, drag the green bars or **Adjust rows** | Handles are `opacity: 0` until the step is selected (`.ge-handle`); the hint under the panel says "Alt+Up or Down..." | **F6**: no touch hint, keyboard jargon |
| 8 | Name the step (label field in the panel below the table) | Panel is under the whole table | F3: panel can be off-screen after a tap-select (verify) |
| 9 | Repeat for each step, add banners, **Save changes** | | |

Estimated effort: about 12 to 15 interactions per step-with-rows pair. **Task success: likely, with at least two moments of "where do I tap now"** (F6 handles undiscovered; F3 label off-screen). Tom reorders nothing between sections: **there is no section reorder UI** (`useSectionActions` comment "Reorder is a stretch and has no UI"). If he builds Frosting first he must delete and redo (delete section has a confirm and Undo, so it is recoverable). Row moves at 768 px need the Row actions menu (Move buttons are hidden under 900 px), two taps per move.

Good: "Add step" in an empty section is aria-disabled with a visible reason (`step.noRows`: "Add an ingredient before adding a step."), so he is told why. The empty second section shows a non-blocking warning ("Frosting has no ingredients.", `issue.empty_section`).

### 3.3 Jan, desktop: reorder and split with the keyboard

| # | Action | Keys | Concern |
| --- | --- | --- | --- |
| 1 | Open editor | Click Edit grid; focus lands on the heading | Fine |
| 2 | Reach the table | Tab through toolbar and section buttons | There is no "Keyboard help" disclosure (spec 14.1 item 3 is not implemented; no `keyboard` key in `en.json`) |
| 3 | Roving table: arrows to a row | Arrow keys, Home/End, PageUp/PageDown between sections | Good |
| 4 | Reorder | Alt+Up / Alt+Down on a row (`useRowActions.onRowKey`) | Only discoverable from the spec; the on-screen hint (`hint.resize`) covers step resize only |
| 5 | Split | Not a chord. He must Tab to that row's `...` Row actions button and choose **Split into portions** | F11 |
| 6 | Rename portion | Focus goes to the new portion's label field ("half", "remaining") | Good defaults (reducer `rowSplit` sets `half`) |
| 7 | Edit text | F2 or Enter, Ctrl+Enter adds below, Escape cancels | Hidden |
| 8 | Delete | Delete / Backspace on a row removes it at once, toast Undo for 10 s, toolbar Undo stays | Backspace habit is risky but recoverable |
| 9 | Save | Ctrl+S works inside and outside text fields (`GridEditor.onKeyDown`) | Good |

**Task success: likely, but only if Jan knows the chords.** Alt+Left/Right is swallowed so the browser Back shortcut cannot fire over a target (`step-chords.ts`, O4), which is a good catch. Tab-order cost: the per-row Move up, Move down and `...` buttons are ordinary tab stops (only menu items have `tabIndex={-1}`; `RowControls.tsx`), so a 9-row section adds about 27 stops. The spec promised "one tab stop for the table" (14.1 item 4); the table is roving but the row controls are not.

### 3.4 Rename a section (all personas)

Strengths: inline field, Enter commits, Escape cancels, focus returns to Rename, announcement `section.renamed`. Weak points:

- Blur with an empty name in a multi-section recipe silently reverts and discards the field (`SectionHeader.commit`, `viaBlur` path): no message. Enter shows `section.renameEmpty` ("Give each section a name.") correctly.
- The rename button is the literal word "Rename" (`section.rename`), identical in every section; the group `aria-label` carries the title for screen readers only. Sighted users rely on position.
- Tom/Marie on a phone: the section toolbar is six buttons wide; Rename is the first.

### 3.5 Recover from a mistake (all personas)

| Mistake | Recovery path | Verdict |
| --- | --- | --- |
| Wrong span edge | Undo (toolbar, named) or opposite control | Strong |
| Deleted row that also removed a step | Toast: "Removed X and the step Y that only used it." (`row.deletedWithStep`) with Undo, 10 s, paused on hover or focus; toolbar Undo afterwards | Strong. The warning about removed steps is exactly what a cook needs |
| Deleted section | Inline confirm that counts rows and steps, then Undo toast (`section.deleteConfirm` ends "You can undo this.") | Strong, slightly redundant (confirm and undo) |
| Typed a bad ingredient | Escape cancels; preview "Parsed as" or "Could not read a quantity; saved as a name." | Strong |
| Wants to throw everything away | Cancel (dirty) then "Discard your unsaved changes?" Keep editing / Discard changes | Strong; **Keep editing** is the first and focused option |
| Leaves via a header link, Android back swipe, or iOS edge swipe | Nothing: only `beforeunload` is registered | **F2** |

### 3.6 Handle a conflict (all personas)

Flow (`useSaveFlow`, `ConflictPanel`): Save returns 409, the panel replaces the Problems panel, focus and scroll go to its heading, three choices: **Keep editing** (primary), **Load the latest version** (confirm "This throws away your changes in the editor."), **Save mine anyway** (danger style, confirm "This replaces what the other person saved with your version.").

- Marie: she edits on the phone while Jan fixes the same recipe on his desktop. She gets "This recipe changed while you were editing." She cannot see what changed, by whom, or when. Her likely choice is "Load the latest" (safest sounding) and she redoes one span: cheap for her.
- Tom: loses 15 minutes of Cake / Frosting work if he picks Load latest, and has no way to copy anything out first. Likely picks **Keep editing**, presses Save again, gets the same 409 (the stale `base_updated_at` is unchanged), and loops. Nothing tells him why.
- Jan: most likely conflicted with himself (second tab, or the recipe form saved in another tab). "Someone saved it" is misleading for a one-person case.

Safe defaults are right (primary = non-destructive, both destructive paths confirmed). The gap is information and a dead-end loop. See F3.

### What works well (keep)

- Every destructive action has Undo with a named target (`toolbar.undoWith`), and the dirty marker is text plus a dot, not colour alone.
- Non-drag alternatives exist everywhere: steppers on phone, "Adjust rows" on tablet and desktop, chords for keyboard.
- Disabled buttons stay focusable and say why (`step.noRows`, `toolbar.saveDisabledErrors`, `section.last`).
- Row delete that also removes steps says so (`row.deletedWithStep`).
- Sensible split defaults ("half", "remaining" labels, halved quantities) and a visible "Portion 1 of 2" chip.
- Alt+Left/Right is swallowed so browser history cannot fire mid-edit.
