## Findings

### H1 (High): restore apply peaks at about 2 GB and blocks the event loop for about 19 s

Why High: the criteria list "unbounded resource use by an authenticated member"; this is bounded by the format caps, but the bound is far above a small host and a single 0.6 MB request reaches it. The documented target includes a Raspberry Pi.

Reproduction (any member; `RATE_LIMIT_RESTORE_MAX` is 10 per hour per user):
1. Build a zip with a stored or deflated `backup.json` of 26 recipes, each 20 sections x 200 ingredients (104 000 ingredient rows, 29.1 MiB of JSON, 627 KB zipped; under every cap: `MAX_MANIFEST_BYTES` 32 MiB, `MAX_TOTAL_ROWS` 250 000, per-recipe limits, ratio about 48).
2. `POST /api/import/backup` (`application/zip`): 201 in 1.4 s, server RSS 489 to 807 MiB.
3. `POST /api/import/backup/<id>/apply` `{"strategy":"skip"}`: 200 after 19.2 s; server RSS 2086 MiB (`VmHWM`, `RssAnon` 1.96 GB). `GET /api/health` sent every 20 ms during the apply: first answer after 19.4 s, every other user is frozen.
4. Same result with `NODE_OPTIONS=--max-old-space-size=640` (RSS 2008 MiB): the growth is outside the V8 heap.
5. A restore of 4000 tiny recipes (2.9 MB zip) alone blocks the loop for 8.2 s (health answered after 8.05 s).

Impact: on a 1 to 2 GB host the container is OOM-killed (every user logged out of an in-flight request, the staged file lost); on any host one member freezes the instance for up to 20 s, ten times an hour. The apply loop in `restore.ts` never yields (the `await` inside it only runs when the archive has photos), and every ingredient is its own `insert(...).values(...).run()` (`src/lib/db/recipes.ts:90`), which prepares one native statement per row.

Smallest fix (two small edits, both measured in a copy of the clone, same archive, same machine):
- `src/lib/db/recipes.ts:90-101`: insert ingredients in chunks of 100 rows (`tx.insert(ingredient).values(chunk.map(...)).run()`).
- `src/lib/backup/restore.ts`, in the `for (let k...)` loop (line 295), after each recipe commit: `await new Promise((r) => setImmediate(r));`

| Build | Apply time | Peak RSS (HWM) | Longest `/api/health` answer during stage + apply |
| --- | --- | --- | --- |
| `884aa09` | 19.2 s | 2086 MiB | 19.4 s |
| chunked insert only | 8.2 s | 871 MiB | 8.2 s |
| chunked insert + yield per recipe | 8.2 s | 726 MiB | 1.9 s (the 1.3 s stage-time parse remains) |

Reviewer note (architect): yield every N rows rather than per recipe (one 4000-ingredient recipe still blocks about 0.7 s), set a `mem_limit` on `app` in compose so an OOM restarts only the app, add a global restore limiter, and treat the in-memory apply lock as a hard single-process constraint; a worker thread is the durable fix (post-1.0). The remaining 1.3 s block is the stage-time JSON parse plus zod; accepted. Optional hardening (not needed for the tag): refuse a restore whose manifest exceeds a fraction of the container memory limit.

### M1 (Medium): a member can make the admin export impossible

Reproduction: after the member restored 52 recipes of the shape above (or created them with `POST /api/recipes`, 4000 ingredients each, no quota), `GET /api/export?all=1&photos=1` as admin answers `413 export_too_large` ("larger than this Cellar can restore later"), as does the member's own export. The cap is deliberate (`exportCaps.manifestBytes` = `MAX_MANIFEST_BYTES`, so every export can be restored); there is no per-user quota (v0.4.2 Q13, accepted). Impact: loss of the JSON backup path until the data is removed; the volume copy (documented as the primary backup) is unaffected. Smallest fix: none needed in code if the owner accepts; otherwise a per-user row quota at recipe write time. Recommendation: **owner-accept in writing**, and state in the README backup section that the JSON backup has a 32 MiB manifest ceiling and the volume copy has none.

### M2 (Medium, weak test): controls whose removal fails no test

Found by mutation (section "Negative controls"):
- Login timing equalizer: `: (await verifyDummy(...), false)` replaced by `: false` (`src/app/api/auth/login/route.ts:43`): 73 tests pass. (Live: known 23.7 ms vs unknown 24.0 ms median over 150 pairs; the control works, nothing guards it.)
- `PASSWORD_MAX = 128` set to 1 000 000 (`src/lib/auth/password.ts:15`): 70 tests pass (the bound on hashing cost of attacker input). Live: a 10 000 character password is rejected in 4 ms.
- The `isCsrfSafe` call in `src/app/api/auth/login/route.ts:23` replaced by `if (false)` (Y2): 2917 tests pass (live: cross-site login POST is 403; login CSRF would let an attacker sign the victim into the attacker's account). The same call in `authenticate()` (`http.ts:30`, Y1) fails 19 tests. Register, reset, logout and setup have the same per-route call and were not mutated.
- `found.deactivatedAt` removed from the login condition (`login/route.ts:44`): 2917 tests pass. Low impact: `validateSession` still rejects the session (checked live: a login that "succeeds" for a deactivated user gives a cookie that is 401), so this is a redundant layer; the unit test of the sessions covers the effective control.
- `meta.width * meta.height > MAX_UPLOAD_PIXELS` (`process.ts`) and `limitInputPixels` each removed alone: 2911 tests pass, because each covers the other. Redundant pair, acceptable; one test that disables both would make it a control.
Smallest fix: five short tests (add: a login POST with a cross-site Origin is 403 and sets no cookie) (route test with a spied `verifyDummy` for an unknown email; `registerSchema.safeParse` with a 129-character password; a login for a deactivated user sets no cookie; the 17 Mpx PNG with the header guard stubbed). Recommendation: add the first two before the tag, owner-accept the rest.

### L1: no total deadline on a request body

A sender that sends 1 byte every 24 s on `POST /api/import/backup` held its per-user slot for the whole 420 s of the test (the connection was never closed; Next disables Node's `requestTimeout`); a second stage from the same user got 409, other users were unaffected. The same holds for any proxied route (stall after 1000 of 1 000 000 declared bytes: no answer in 100 s), unauthenticated. Cost per held connection is a socket. Accept for a family-scale deployment; the README reverse-proxy section can mention `servers { timeouts { read_body ... } }` (Caddy) or entrypoint `respondingTimeouts` (Traefik).

### L2: `source_url` accepts credentials

`PUT /api/recipes/:id` with `source_url: "http://user:pw@evil.example/"` is stored (200) and shown as a link on the public page (`rel="noopener noreferrer"` is present). The importer (`source-url.ts`, `safe-fetch.ts`) refuses userinfo; `recipeInputSchema.httpUrl` (`src/lib/recipes/schemas.ts:21`) does not. `javascript:`, `data:`, `vbscript:`, `ftp:`, `//host`, ` javascript:` and mixed-case schemes are all 422 (checked). Fix: in the `refine`, also require `!u.username && !u.password`.

### L3: `GET /api/export` is not cross-site gated

`GET` is "safe" to `isCsrfSafe`, and the export route takes no CSRF decision. A cross-site top-level navigation (SameSite=Lax sends the cookie) returned 200 (`Sec-Fetch-Site: cross-site`): the victim downloads their own backup and one of ten hourly exports is spent; the attacker cannot read it. Fix: in `src/app/api/export/route.ts`, answer 403 when `Sec-Fetch-Site` is `cross-site`.

### L4: `email_taken`

`POST /api/auth/register` with a valid invite and an existing address (also `B@T.TEST`) redirects with `error=email_taken`; reachable only by someone holding an admin-issued, unexpired invite (the invite is not consumed). Accept.

- Existing suites (`src/lib/import`) pass 1174; mutation checks in the control table.

### 3.2 Restore archives (live, hand-built zips; every rejected upload left `RESTORE_DIR` empty)
- Names refused (422 `backup_zip_invalid`): `../evil.webp`, `/etc/passwd`, `photos/../../x.webp`, `photos/<ULID>.webp/../../x`, backslash, NUL byte, `Photos/`, `.WEBP`, `./backup.json`, `backup.json/`, `photos/`, `x.txt`, a ULID with an invalid letter, trailing space, a full-width digit.
- Structure refused: overlapping entries (two central records on one local header), duplicate `backup.json`, stored entry with `csize != usize`, bad CRC, local header name differing from the central record, encrypted and strong-encryption flags, methods 9, 12, 14, a fake end record inside the zip comment, junk before and after, empty body, empty zip, central-directory count and offset lies, 60 001 entries.
- Bombs refused: deflate entry declaring 100 B with 50 MiB of output (cut off by the inflate limit), 17 MiB manifest, an honest 20 MiB photo of zeros (ratio over 200).
- Accepted by design: a symlink-attribute entry with an allowed name (never extracted: the bytes are the link text, `processImage` rejects them; `photos_failed` 1, no `/etc/passwd` content on disk), a zip inside a zip as a photo (re-encode fails, counted), the UTF-8 flag.
- Content: `__proto__` and `constructor.prototype` keys (`forbidden_key`), 5000-deep JSON (rejected, server alive), 5001 recipes, over-long strings, `javascript:` and `data:` `source_url` (422), photo `file` values with traversal (422 by `PHOTO_PATH_RE`), hostile photos inside a valid archive (SVG, GIF, 30 000 px bomb refused; polyglot re-encoded; 2 restored, 3 failed, only RIFF/WEBP on disk), a member file claiming `scope: all` (403), a member file with `owner_email` (422).
- Admin `all` file edited by hand (unknown owner `ghost@t.test` with role admin in `users`, a case-variant owner, a note attributed to another active user): no user created, no role changed (counts compared), unknown owner rerouted to the restoring admin (L4 of the v0.5.1 checkpoint), the unknown author's note dropped, the note attributed to an existing user kept (admin-only by design).
- 300 recipes with `visibility: users` in a member file: restored as the member's own recipes with that visibility (documented, the member can set it anyway).
- Concurrency: a second stage from the same user while the first trickles: 409; other users: unaffected. Two stage/apply by different users while an apply runs: serialized because the event loop is blocked (H1), the `409` lock is never the thing that answers.
- Restore loop: `RATE_LIMIT_RESTORE_MAX` is the only throttle on stages (10 per hour per user, refunded on early rejections); apply has none beyond one stage per user.
- Export while a restore applies: served (200 in 10 ms) once the loop yields; no shared state.
- Caddy gap (258 to 268 MB, now `270MB`): `270MB` = 270 000 000 B is above `RESTORE_BODY_MAX` 268 435 456 B, so Caddy never refuses a body the app would accept; bodies between the two reach the app and get the app's 413. Static analysis only; **not run by me**.
- `RESTORE_DIR` permissions: files `0600`; the directory is created `0700` only when missing (an existing volume keeps its mode, v0.5.1 I2); orphan files are pruned after an hour when any restore call arrives.

## 4. CSRF

`isCsrfSafe` (`src/lib/auth/csrf.ts`): `GET`/`HEAD`/`OPTIONS` pass; otherwise `Sec-Fetch-Site` must be absent or `same-origin`, `Origin` absent or equal to the `BASE_URL` origin, and at least one present. 26 mutating handlers (all `POST`/`PUT`/`DELETE` under `src/app/api/**`; `/api/health` and `/api/photos` GET excluded): login, logout, register, reset, setup, recipes POST, recipe PUT/DELETE, grid, visibility, share-link POST/DELETE, copy, notes POST/PUT/DELETE, rating PUT/DELETE, photos POST, cover, photo DELETE, import, import save, backup stage, apply, discard.

Each of 25 handlers (setup excluded) was called with a valid session and each of 12 variants (300 requests; `/api/setup` calls `notFound()` before the CSRF check, so it was tested before the first admin existed only: 403 cross-origin); the grid route also exports 405 stubs for other methods: no `Origin` and no `Sec-Fetch-Site`; `Origin: http://evil.example`; `Origin: null`; `Sec-Fetch-Site: cross-site`, `same-site`, `none` (each without Origin); `Origin` right + `Sec-Fetch-Site: cross-site`; `Sec-Fetch-Site: same-origin` + `Origin` wrong; `Origin` on another port; `Origin` = base + `.evil.example`; upper-cased scheme and host; trailing slash. **All 300 answered 403**, and the recipe, note and photo were unchanged afterwards (setup answers 404 first once an admin exists). Positive controls: `Origin` = `BASE_URL`, and `Sec-Fetch-Site: same-origin` alone, are accepted.
- The three restore routes bypass the proxy (matcher exclusion) and call `authenticate` themselves: without a cookie, cross-origin gives 403 and same-origin gives 401 on all three (403 before 401).
- Content-type confusion: `application/x-www-form-urlencoded`, `text/plain`, `multipart/form-data` to the seven JSON routes and to photo upload: 415 even with a correct Origin.
- CORS preflight (`OPTIONS` with `Origin: evil`): 401, no `access-control-*` header.
- Matcher path variants for the restore routes: `/api/import/backup/`, `//api/import/backup`, `/api/import//backup`, `/api/import/./backup`, `?x=1`: redirect to the canonical path or reach the route (own auth, 401/409); `%62ackup`, `backup%2F`, `backupx`, `/API/import/backup`, `/api/import/Backup`, `/api/%69mport/backup`: other routes (405/404/proxy 401), never the upload handler; no variant skips both the proxy and the route's own session check.

## 9. Residuals Q4, Q7, Q16: recommendation

| Residual | Evidence | Recommendation |
| --- | --- | --- |
| Q4 limiter trusts `X-Forwarded-For` | Confirmed live: with `TRUSTED_PROXIES` set and the port reachable, rotating the header defeats the public and the per-IP login limiters; with it empty the public limiter does not run and the header is ignored. Nothing else depends on the client address (no authorization decision), the per-email login limit and the 128-bit token do not use it. With the shipped Caddy profile and the Traefik example the peer is the proxy, which replaces the header (the docs agent's Traefik run showed it) | **ACCEPT.** The README and `docs/deployment.md` already say "do not publish the app port". | Q7 admin export contains others' private data | Admin-only (member `?all=1` 403, also in `buildBackup`, role re-read in the transaction), logged, no hash, token, session, invite or import job (grep of the 5 KB to 20 KB exports); the admin can already read any private recipe by id (matrix) and holds the volume | **ACCEPT.** Keep the log line; the backup page should keep saying the file contains everyone's private recipes |

Residual wording (architect): Q4 is a mode trap, the same `TRUSTED_PROXIES` value is safe or unsafe depending on topology the app cannot verify; with it empty the per-IP login limiter and the `/r/*` limiter are inert (only the lockable per-email limit remains), so direct mode has no public-link throttle; optional startup warning. L1 should be a README MUST for internet exposure (proxy read timeouts), not a mention. Also add a unit test that every `route.ts` under `api/import/backup/**` calls `authenticate` (the matcher exclusion is default-open for new routes).

Further residuals I recommend recording in the carryover: no general write rate limit for members (a member can issue back-to-back maximum-size recipe `PUT`s, about 0.7 s of event loop each; family-scale, accepted); L1; the 1.3 s stage-time block after H1; JSON backup ceiling of 32 MiB (M1); a restore of an admin `all` file by an admin remains fully trusted input.
