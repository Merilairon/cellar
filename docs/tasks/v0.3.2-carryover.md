# Cellar — Open Topics Carried Past v0.3.2 (T18 part; T19 and the gate extend this file)

## 1. arm64 (threat-model condition 9): PENDING CI, NOT VERIFIED

The `arm64` job in `.github/workflows/ci.yml` builds the app and sidecar images for `linux/arm64` under QEMU, runs a `sharp` jpeg-to-webp re-encode plus `argon2`/`better-sqlite3` loads in the app image, and runs the three real-Chromium Docker test files (`render`, `render-abuse`, `syscalls`, including the sandbox self-check and EPERM syscall checks) in the sidecar image. It has **not been run yet**: this host has no arm64 binfmt and no GitHub runner was available. Until that job is green on `release/v0.3.2`, arm64 stays "not verified" in the docs and condition 9 stays open. A green run proves "works under QEMU emulation", not real hardware (Raspberry Pi); QEMU cannot show that the Chromium sandbox works on a real arm64 kernel. If the sandbox fails under QEMU, the sidecar is documented unsupported on arm64 (never `--no-sandbox`).

- F3: the `headless-tests` CI job runs the 39 real-Chromium tests at `--memory 2g` via `docker/browser/scripts/docker-tests.sh`, with `kernel.apparmor_restrict_unprivileged_userns=0` on the runner. Locally on amd64: 39/39 pass (16 + 10 + 13). The job itself has not run on a GitHub runner yet; the sysctl step is unverified there.
- F4: server `headersTimeout` 5 s, `requestTimeout` 15 s, `keepAliveTimeout` 1 s, `maxHeaderSize` 8 KiB (431 on oversize), tested in `server.test.ts`. `BIND_ADDR` must now be an IP literal (tested). The default stays `0.0.0.0`: compose cannot know the container's `headless-link` address without static addressing, and the mandatory bearer token plus the internal-only link network are the controls. Accepted, not changed.

## 3. Sidecar memory evidence (amd64, Docker 29.9.3, `docker stats` MemUsage, image 1.21 GB)

| Measurement | Result |
| --- | --- |
| Idle after healthy, `--memory 1g` | 106 MiB |
| `render.docker.test.ts` (16 cases, includes a 6 MB DOM) at 1 GiB | passes, peak 903 MiB sampled (includes the node test runner and fixture servers in the same container) |
| `render-abuse.docker.test.ts` (10 cases) at 1 GiB | **OOM-killed** (exit 1, `OOMKilled=true`, sampled peak 865 MiB before the kill) |
| All 39 at `--memory 2g` | 39/39 pass |

Reading: the production service sits near 106 MiB idle (spike: 178 MB after a small render, 195 MB peak); the 1 GiB limit is a deliberate cap that an adversarial page or the abuse suite can hit, in which case the container is killed and restarted (`restart: unless-stopped`). That is the limit doing its job, but it means abuse/heavy pages can end in OOM instead of a clean error code. A heavy real public page was not measured (no outbound target on this host). arm64 numbers: none (pending CI, see 1).
