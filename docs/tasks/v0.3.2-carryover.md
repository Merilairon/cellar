# Cellar — Open Topics Carried Past v0.3.2 (T18 and T19; the gate extends this file)

## 1. arm64 (threat-model condition 9): VERIFIED ON A NATIVE GITHUB ARM64 RUNNER

The first design ran the `arm64` job under QEMU user-mode and failed: QEMU does not emulate `clone/unshare(CLONE_NEWUSER)`, so `syscall(unshare)` returned an error (`userns unavailable`) and the Chromium sandbox could not start (14 of 16 render tests and the namespace tests failed). The sandbox was not weakened and nothing was skipped. The repository is public, so the job now runs on the native `ubuntu-24.04-arm` runner (real aarch64 kernel, no emulation). It builds the app and sidecar images for `linux/arm64`, runs a `sharp` jpeg-to-webp re-encode plus `argon2`/`better-sqlite3` loads in the app image, and runs the three real-Chromium Docker test files (`render`, `render-abuse`, `syscalls`, including the sandbox self-check and EPERM syscall checks) in the sidecar image. Result: green in CI run 42357515708 on `release/v0.3.2` (an earlier green run, 42354517591, was followed by a red headless-tests run 42355861404, see 3a). Still unverified: Raspberry Pi / Home Assistant hardware specifically (a different kernel and distro from a GitHub arm64 VM; kernels with user namespaces disabled remain unsupported). The separate `docker` job still builds amd64+arm64 under QEMU, build and native-module load only.

## 3a. CI correction: C18 oom_kill assertion (post-release)

The first CI runs on a GitHub runner exposed a wrongly specified assertion, not a product defect. `render-abuse` test C18 (gzip bombs) asserted that the cgroup counter `oom_kill` in `/sys/fs/cgroup/memory.events` did not change. That counter counts every process the cgroup OOM-kills, including a runaway Chromium renderer, which is the intended containment (the preceding C5e memory-bomb test already logs `oom_kill 0 -> 1` by design). On the slower runner one more renderer kill landed during C18 (`2 !== 1`), run 42355861404 red; run 42354517591 on the same code was green, so the count is timing-dependent. Locally on amd64 three repeat runs at `--memory 2g --memory-swap 2g` always gave C5e `0 -> 1`, C18 unchanged. C18 now asserts the real property: every vector ends within the kill window, each next job renders, PID 1 and the test process are alive, and no contexts leak; the counter is only logged. Negative control: with the supervisor made to poison all jobs after a failed one, C5e and C18 both fail. CI run 42357515708 (all five jobs) is green with the fix. The v0.3.2 tag was re-created on the final main commit after that.
