# v0.1 (M1 Foundation) Development Tasks

## Specification Summary

**Source**: [milestones/01-foundation.md](../../milestones/01-foundation.md), [PROJECT.md](../PROJECT.md), [RELEASE_PLAN.md](../RELEASE_PLAN.md) (Definition of Done), [TASK_ASSIGNMENTS.md](../TASK_ASSIGNMENTS.md) (v0.1 table), [data-model.md](../data-model.md) (`user`, `session`, `invite`, `password_reset` only).

**Objective (quoted)**: "A deployable skeleton: Next.js app, SQLite database with migrations, invite-based auth, i18n plumbing, and Docker packaging."

**Technical stack**: TypeScript strict, Next.js App Router, Tailwind, Drizzle + better-sqlite3, argon2id, next-intl, Vitest, Playwright, Docker multi-stage and multi-arch, Caddy example.

**Env vars**: `DATABASE_PATH` (default `/data/app.db`), `SESSION_SECRET`, `BASE_URL`. Data in `/data` (`app.db`, `uploads/`).

**Target pace**: M1 gets two weekends (RELEASE_PLAN). Re-split if it cannot finish in two.

**Order**: Tasks follow the spec order exactly. Note that the spec lists 10e, 10a, 10b, 10d, 10c after 10, in that order. Commit after each numbered item with Conventional Commit messages.

**Hard rules from the spec ("Instructions for LLM")**
- Data access only in `src/lib/db/`, auth only in `src/lib/auth/`; no raw SQL in route handlers.
- No features outside this list (no recipes yet).
- No hard-coded UI strings; keys go in `messages/en.json`.
- Validate all inputs with zod.

**Agent name shorthand**: lead/support names come from the v0.1 table in TASK_ASSIGNMENTS.md. Where the table has no row for a spec item (route middleware, app shell, CI), the closest row is used and marked "(nearest row)".

### [ ] T4: Login/logout, DB-backed sessions, cookies, CSRF (spec item 4)

**Requirement (quoted)**: "Login/logout with email + password (argon2id), DB-backed sessions, HTTP-only, SameSite=Lax, Secure when HTTPS cookies; CSRF protection on mutating routes."

**Lead / Support**: engineering-identity-access-engineer / security-appsec-engineer. CSRF piece: security-appsec-engineer / engineering-backend-architect (per the "Rate limiting, security headers, CSRF" row).

**Depends on**: T2, T3.

**Files to touch**
- `src/lib/auth/session.ts` (create, validate, delete; session id is a random high-entropy value; if only a hash is stored, say so in the schema; expiry check; cleanup of expired rows)
- `src/lib/auth/csrf.ts` (e.g. double-submit token or Origin/Host check on all POST/PUT/PATCH/DELETE; choose one and document)
- `src/app/login/page.tsx`, `src/app/api/auth/login/route.ts`, `src/app/api/auth/logout/route.ts`
- `src/lib/auth/cookies.ts` (HttpOnly, SameSite=Lax, Secure iff `BASE_URL` is https, see G3)
- `src/lib/auth/current-user.ts` (resolve the user from the cookie; reject deactivated users per G1)
- `messages/en.json` keys

**Acceptance checks**
- Valid credentials create a `session` row and set a cookie with HttpOnly and SameSite=Lax; Secure present when `BASE_URL=https://...`, absent for `http://`.
- Logout deletes the session row and clears the cookie; the old cookie no longer authenticates.
- Expired session is rejected.
- Wrong password and unknown email give the same generic error (no user enumeration); login timing does not trivially differ (verify against a dummy hash for unknown emails).
- Any mutating request without a valid CSRF proof returns 403 and has no effect.
- Deactivated user (G1) cannot log in.
- All inputs validated with zod.

**Test expectations**: unit tests for session expiry, cookie flag logic for http/https `BASE_URL`, CSRF accept/reject. Login rate limiting is added in T10a.
