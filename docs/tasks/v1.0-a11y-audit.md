### 2.1 Fix proposals (High and Medium)

**F1.** In `layout.tsx` use a template and let each route set its own part (all strings through the catalog, R10):

```ts
export async function generateMetadata(): Promise<Metadata> {
  const t = await getTranslations();
  return { title: { template: `%s | ${t('common.home')}`, default: t('common.home') } };
}
```
Then `export const metadata`/`generateMetadata` with a catalog title per page: Sign in, Recipes, New recipe, Edit recipe, Import, Backup, Profile, Users; `/recipes/:id` the recipe title. The public page already returns the recipe title; its not-found branch must keep returning no title so the 404 stays uniform (give the shared 404 one fixed title such as "Page not found | Cellar" in `not-found.tsx`). Verify: a unit test per page for `metadata.title`, and the axe specs already assert a non-empty title.

**F2.** Add one rule next to the global styles:
```css
@media (forced-colors: active) {
  [aria-pressed='true'] { background: Highlight; color: HighlightText; forced-color-adjust: none; }
}
```
(or `outline: 2px solid` plus a leading check mark glyph with `aria-hidden`). Verify with `forcedColors: 'active'` screenshot and `getComputedStyle` of pressed vs unpressed differing.

**F3.** Give the track a border and the knob a system colour:
```css
@media (forced-colors: active) {
  [role='switch'] > span { forced-color-adjust: none; border: 2px solid CanvasText; background: Canvas; }
  [role='switch'][aria-checked='true'] > span { background: Highlight; }
  [role='switch'] > span > span { background: CanvasText; }
}
```

**F4.** `btnPrimary`: add `border border-transparent` (a transparent border becomes visible in forced colors). Same for any other filled button without a border.

**F5.** Either accept the exemption (below) or make the disabled look pass: drop `opacity-60` on aria-disabled primaries and use explicit tokens, for example a light surface with dark text (`#1f2a1f` on `#cfe3d6`, 9.9:1) plus a dashed border so it still reads as unavailable. Verify: pixel sample of the button.

**F6.** Let the group wrap or scroll: replace `overflow-hidden` with `flex-wrap` on the group (borders move to each button), or `max-w-full overflow-x-auto`. Verify: 375 px at 200 % text, scrollWidth <= clientWidth.

## 3. Table semantics: what a screen reader receives (cake, public and owner pages identical)

`page.locator('main').ariaSnapshot()` and the Chromium accessibility tree (CDP `Accessibility.getFullAXTree`), cake section "Cake" (5 step columns, 8 ingredient rows, a banner row on top):

```
region "Cake: ingredient grid, scrollable"                 (tabindex 0, labelled; aria-describedby the scroll hint when columns are off-screen)
  table "Cake: ingredients and the steps that use them"
    caption: "Cake: ingredients and the steps that use them"   (sr-only, same text as the table name)
    rowgroup (thead, visually zero height, still in the tree)
      row: columnheader "Ingredient", "Step 1: cream", "Step 2: beat in", "Step 3: mix", "Step 4: fold in", "Step 5: bake"
    rowgroup
      row: cell "Heat the oven to 350F (170C) and line a 9 inch round pan."        <- banner row, colSpan = 6, no row header
      row: rowheader "115 g (1/2 cup) unsalted butter, softened"
           cell "cream Uses unsalted butter to sugar."          button (rowSpan 2)
           cell "beat in Uses unsalted butter to vanilla extract."  button (rowSpan 4)
           cell "mix Uses unsalted butter to milk."             button (rowSpan 7)
           cell "fold in Uses unsalted butter to sugar."        button (rowSpan 8)
           cell "bake 350F (170C) 28 to 32 min Uses unsalted butter to sugar."  button (rowSpan 8)
      row: rowheader "100 g (1/2 cup) sugar (half)"             <- no cells: all five are covered by the spans above
      row: rowheader "2 large eggs"   cell ""                   <- empty cell, no name, no content
      ...
```

What this means for a user, and what is verified:

- `<table>`, `<caption>`, `<th scope="col">` (hidden header row) and `<th scope="row">` are exposed as table, caption, columnheader and rowheader. Verified in the tree.
- Row and column **spans are native `rowspan`/`colspan` attributes** on the cells (markup: `rowSpan={c.rowSpan}` and the banner `colSpan={columns + 1}` in `RecipeGrid.tsx`; the spans of the cake, 2, 4, 7, 8 and 8 rows, read from the rendered layout, not from the DOM). Neither the CDP tree nor `ariaSnapshot` exposes span values, so **what NVDA or VoiceOver announces for the spanned cell (for example "row 2, column 3, rows 2 through 5") is NOT TESTED**; section 7 lists it for the owner. The span is also given in words by the sr-only text "Uses X to Y." inside the cell's button, which is what the tree does show.
- A covered row (here "sugar (half)") has a row header and **zero cells**. Table navigation in column 2 from row 1 down to row 2 depends on the screen reader's span handling; it will either repeat the spanning cell or report a blank. NOT TESTED.
- The **banner row** is one `cell` spanning every column, in the body, with **no row header**. Its column header is ambiguous (colspan across all headers). Reading order is correct (top banner first, bottom banner last). Acceptable, listed in the owner checklist.
- Empty cells have no name and no text (silent or "blank").
- Each step cell is a `cell` containing a `button` whose name is "label params Uses X to Y." with `aria-expanded` and `aria-controls` (inline) or `aria-haspopup="dialog"` (phone sheet). The click handler on the `<td>` is a pointer convenience; the button is the keyboard and AT target.
- The step detail panel is a polite live region (`aria-live="polite"`, id `rg-detail-...`) placed after the **table**, not after the cell. Expanding with Enter announces the whole panel text including "Close" (live log: "creamBeat the butter with half of the sugar until pale and fluffy.Close"); focus stays on the step button.
- Print (`emulateMedia print`): both tables, captions (display block), header group (`table-header-group`) and the source URL (`::after`) remain; buttons are visible as step labels only. The structure survives printing.
- The list view has no table: `h2` Ingredients with a `list`, `h2` Steps with a `list` (ordered steps), then Notes.
- Headings: h1 recipe title, h2 per section, h2 Notes; no skipped level on the recipe, list, public and backup pages. The edit form has an `h4` after an `h2` ("How each line is read"), outside this audit's grid scope (recorded under NOT TESTED / follow-up in section 8).

## 5. Decisions asked for

**Dark disabled primary buttons (1.4.3).** The criterion reads: "Text or images of text that are part of an inactive user interface component, that are pure decoration, that are not visible to anyone, or that are part of a picture that contains significant other visual content, have no contrast requirement." (WCAG 2.2, SC 1.4.3 Contrast (Minimum), exception "Incidental"). WCAG 2.2 has **no glossary entry** for "inactive user interface component" (checked: the glossary goes from "image of text" straight to "informative"), so the text does not say that `disabled` is the test, and it does not name `aria-disabled` either. The Understanding document applies the exception to controls that are not available for interaction, but these buttons are kept focusable and announced as unavailable by design (v0.5.1), so a strict reader can argue either way. Decision: **treat as in scope, Medium (F5)**, not High, because the reason is shown next to the button as full-contrast text ("Choose a file first", "Nothing new to restore"), the control is announced as disabled, and the tags `disabled`/`aria-disabled` make it non-operable. Measured: light 2.61:1, dark 3.65:1 (text vs fill from pixels), fill vs page 1.97:1 in dark. Real `disabled` controls (Reset, Grid on a list-only recipe): computed 3.41:1 light, 4.98:1 dark; exempt under the same exception and not counted.
