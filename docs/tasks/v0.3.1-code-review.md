# v0.3.1 code review (slice 03b, auto-mapper)

Scope: `git diff main...release/v0.3.1` (70 non-fixture files, about 9.5k added lines) against
`milestones/03-url-import.md` (reqs 5 and 12), `docs/data-model.md` §3, `v0.3.1-tasklist.md`
and `v0.3.1-ux-spec.md`. Read-only review; nothing was edited or committed.

Evidence base: I read the mapper modules, the save/pipeline/service changes, `ReviewForm`,
`MappingPanel`, `MappingPreview`, `RecipeForm`/`form-model` changes and the corpus runner. I ran
`vitest run src/lib/import tests/unit src/components/import src/lib/recipes` (46 files, 1159
tests, all pass) and `npm run test:mapper` (all gates PASS, confident-wrong 0). I also ran
ad-hoc probes through `mapGrid` (scratchpad, not in the repo) to look for wrong-but-confident
cases. I did not run Playwright e2e or the full lint/typecheck sweep.

## Summary

The branch is well built and unusually careful: the mapper is pure and total, regexes are
registered and constant, nothing is built from input, the budget is a deterministic operation
counter (not a clock), the save path re-validates everything through `recipeInputSchema` and the
grid validator, `split:*` temp ids are remapped to ULIDs on write, the preview renders only
React text nodes, and the source-URL / duplicate-lookup change is correct for the cases that
matter. Hydration is handled properly (index-derived keys, no counter at render).

The main weakness is calibration honesty. The corpus is 100 percent on author-written fixtures
(26/26 clean, 5/5 reference), which proves the code matches its author's mental model, not that
"Good match" is trustworthy. I found one genuinely confident-wrong class (ingredient that is also
a leading verb) that the corpus does not cover, and two places where a warning on screen
contradicts the "Good match" badge (unresolved split, banner-only ingredient). None is a
security or data-loss issue; the user always sees the preview and can fall back to List.

Counts: 0 blockers, 3 major, 6 minor, 5 nits.

## Major

### M1. [FIXED] Ingredient that is also a leading verb is matched as a mention: confident wrong grid
`src/lib/import/ingredient-match.ts:221-262` (`findMentions`), consumed at
`src/lib/import/map-grid.ts:240-262`.

Evidence (probe through `mapGrid`, ingredients `1 cup cream, 1 cup butter, 1/2 cup sugar, 2 eggs`;
steps `Cream the butter and sugar. / Beat in eggs. / Whip the cream. / Chill 1 hour.`):

```
confidence 1, level high
rows:  cream | butter | sugar | eggs
steps: column:cream[0,2] column:beat in[0,3] column:whip[0,3] banner_bottom:chill
```

`cream` (the verb, step 1) is counted as a mention of the `cream` ingredient, so the cream row
is placed first and step 1 spans it, while the cream is really used in step 3. Same pattern for
any ingredient that is also an imperative: `oil`, `butter`, `flour`, `season`, `zest`, `juice`,
`salt`, `sugar` ("Sugar the rim"), `cream`, `mash`. `step-verbs.ts` already knows `cream` is a
verb (`CREAM_NOUN_PREV`) and the label even says "cream", so the two halves of the mapper
disagree about the same token. Score is 1.00 because no signal looks at it, so the review
opens in Grid with "Good match". The spec requirement "no confident wrong answer" is met on the
corpus only because no fixture contains this shape.

Fix: in Phase A, when a mention starts at the first content token of a sentence/clause and that
token is in `VERB_CLASS` (and is not followed by a comma or end of clause), do not count it as an
ingredient mention; or count it as half-ambiguous (`ambWeight += 0.5`) so the score drops below
0.70 whenever it is the only evidence. Add fixtures `hard-verb-is-ingredient-cream` and
`hard-verb-is-ingredient-oil` with `confidence.max: 0.69`.

### M2. [FIXED] Unresolved split still scores "high" (0.90)
`src/lib/import/map-confidence.ts:35` (`0.10 * splitOk`), fixtures
`tests/fixtures/mapper/hard-split-unresolvable-some-of-the.json:54` and
`hard-split-three-way.json:56` (`"confidence": {"max": 0.95}`).

Evidence: probe E (`some sugar` ... `the rest of sugar`) and the two fixtures all end at 0.90,
level high, with `split_unresolved:sugar` in the warnings. The review opens as Grid, "Good
match", with one sugar row that a person would draw as two rows. data-model §3 5b says
"otherwise keep one row and lower the confidence"; the tasklist fixture list says "confidence
reduced". The fixture bound `max 0.95` is loose enough that any value passes, so it asserts
nothing about the behaviour it describes (this is a tuned-to-pass expectation).

Fix: treat any unresolved split candidate as a hard demotion, for example cap at 0.69
(`if (splitCandidates > 0 && splitResolved < splitCandidates) raw = min(raw, 0.69)`), expose the
count in `signals`, and tighten both fixtures to `max: 0.69`. Cheaper alternative: raise the
`splitOk` weight to 0.30 and rebalance the base to 0.35.

### M3. [FIXED] The corpus gate is self-referential; "confident-wrong = 0" is weaker than it reads
`scripts/mapper-corpus.ts:197-206`, `tests/unit/mapper-corpus.test.ts`, `tests/fixtures/mapper/*`.

Evidence: 53 fixtures plus 5 derived references, all written by the same author as the mapper,
all English, all with tidy punctuation. Clean 26/26 and 110/110 steps. Calibration table: the
0.70-1.00 bucket is 43/43 exact, the other buckets hold 3 fixtures in total, so the table cannot
say whether 0.7 is the right threshold. Two of the 15 `hard` fixtures with an expected
structure miss or are PARTIAL (`hard-spelling-variant-yoghurt`, `hard-steps-no-verbs`), and the
test deliberately exempts `hard` from "meets its expectations" (`mapper-corpus.test.ts`, "except
the reported hard misses"), which is where a regression would hide. M1 shows the gate misses a
whole class.

Fix (cheap, no new dependency): (1) add 10-15 adversarial "plausible real recipe" fixtures not
written while looking at the code (homonyms, parallel components in one section, "meanwhile"
steps, ingredient used before it is listed, steps that reuse a noun as verb); (2) make the guard
fail when any `hard` fixture's stated expectation fails unless it carries an explicit
`"known_miss": true`, so new misses are visible; (3) in the README for the corpus and the
tasklist evidence, state that the table is a regression net on self-authored text, not an
accuracy estimate (the report header already says this once; repeat it in the gate evidence).

## Minor

### m1. [FIXED] Banner-only ingredient counts as "matched"; "Good match" with an "unmentioned" warning
`src/lib/import/map-grid.ts:252-262` (Phase B loop runs to `n`, not `bottom`, and calls
`matched.add(id)` for banner steps) versus `:343-346` (such an ingredient is then appended and
warned `ingredient_unmentioned`). Fixture `hard-banner-mentions-ingredient` shows
`1.00 high ... ingredient_unmentioned:honey`. Calibration change 5 introduced this. Fix: only add
to `matched` when `i < bottom`; the ingredient is then correctly unmatched (cov 0.8 on a 5-row
list is still 0.64 x ..., so decide whether that is the wanted effect and re-baseline) or keep
cov as is and drop the warning from the high-confidence reasons.

### m2. [FIXED] Calibration documentation does not match the brief (5 documented, 7 expected) and one rule is fitted to a boundary
`docs/tasks/v0.3.1-tasklist.md:143-148` lists five departures. The two I can add from the code
are (6) cov also counts banner-only and `ref === 'all'` placements as matched
(`map-grid.ts:262,328`), and (7) `distinctSpans` is computed over bare `row_end` numbers across
sections (`map-grid.ts:494`), so two sections that both end at row 1 count as one distinct span
(probe J: a sensible two-section recipe is capped at 0.55). Please list the real seven.

Assessment of the documented ones:
1. `sections_from_ingredients_only` 0.65 instead of 0.85: the stated reason is "the fixture
   requires it", i.e. fixture-fitting by construction. The product reasoning is sound (steps are
   flat, so the section split is a guess) but it means such a recipe can never be `high`.
   Acceptable; record it as a product decision, not a calibration.
2. No-verb cap 0.39: justified by G18, but the value is chosen to land just under the 0.40
   boundary (`negative-non-english-steps` scores exactly 0.39) and the trigger is `verbs <= 0`,
   so a Dutch or French recipe with one cognate verb ("serve", "mix") escapes the cap. Name matching
   is language independent, so such a recipe may still map correctly, but the claim "non-English
   gets low confidence" is not enforced. Prefer `verbs < 0.5` or a proportional factor.
3. Prep window 8 tokens, stop at another verb: justified, guarded against the over-reach.
4. Split rule (a') qty then remaining: justified, common in real recipes.
5. Leading serve verb forces a bottom banner: justified, but see m1.

### m3. [FIXED] `readMapping` validates sections but not warnings content, signals shape, or level/confidence consistency
`src/lib/import/mapping.ts:62-83`. A row is server-written, so this is defence in depth only:
`warnings` is unbounded, `signals` is any object, and `level` can disagree with `confidence`
(the badge uses `level`, the details show `confidence`). Fix: derive `level` from `confidence`
with `levelOf` on read, cap `warnings` at, say, 100 strings of at most 300 chars, and check that
`signals` values are finite numbers. `mapping_level` in `toJobResponse` (`service.ts:88`) then
cannot disagree with the number next to it.

### m4. [OPEN, carried] Heading-like first steps are silently dropped from the proposal
`map-sections.ts` (`stepHeadingTitle`), probe G/H: a first step `Make the dough` (no period,
under 60 chars) becomes a section title "Dough" and the sentence is removed from `steps`. The 3a
list keeps it, the grid proposal does not. Score stays medium here only because every step spans all rows; with distinct spans it
can reach high. Fix: only treat `Make the X` / `Prepare the X` / `To make the X` as headings when
the line ends with `:` or the recipe already has another heading, or keep the text as the section
note. The risk is highest for `Make the` / `Prepare the`, which are also the most common ordinary
first steps.

### m5. [OPEN, carried] Duplicate lookup misses a stored non-default port on the entered scheme
`src/lib/db/recipes.ts:125` plus `source-url.ts`. `http://host:443/x` is stored with port
(`storedSourceUrl` keeps non-default ports of the entered scheme), but the key drops 443 and 80
for either scheme (`normalizeSourceUrl`), so lookup candidates are `https://host/x` and
`http://host/x`, never `http://host:443/x`. Practically unreachable (the SSRF policy allows only
80/443) but the two functions disagree. Fix: derive the `http:` candidate from `canonical()`
(same port rule as the stored form), or document the edge. Add a test with `:443` on `http`.

### m6. [OPEN, carried] Wall-clock backstop tests assert almost nothing; ReDoS registry is thin
`src/lib/import/map-bounds.test.ts:57,105`: `BACKSTOP_MS = 10_000` for patterns that are either
anchored single-character classes (`/^[\p{L}\p{N}]$/u`, `map-patterns.ts` consumers at
`text-tokens.ts:7`, `step-verbs.ts:122`). They cannot backtrack, so 15 adversarial strings x 2
patterns is ceremony, and a 10 s bound would not catch a real regression anyway. Not flaky (good),
but low value. The meaningful assertions are the operation-count ones (`:401-402`), which are
deterministic and good.

## Checks that came out clean (so they need not be repeated)

- Save path: `view_mode` is optional, validated by `recipeInputSchema`; explicit `grid` with any
  invalid span gives 422 (`service.ts:126-128`); a client cannot save an invalid grid. `mapping`
  is never read from the request. Free text is re-sanitized (`sanitizeTree`). `split:*` ids are
  remapped to ULIDs (`db/recipes.ts:36,80`) and cross-section split groups are rejected by the
  validator.
- `source_url`: the form always sends the key, so "explicit empty clears" works; omitted key
  falls back to draft URL then job URL; scheme is kept (Q3); http and https both match in the
  duplicate lookup.
- XSS: warning suffixes and titles are only rendered as React text nodes or ICU values; no
  `dangerouslySetInnerHTML`; `href="#field"` targets come from validator paths.
- Budget and size: input caps at entry, deterministic operation budget clamped to the default
  (`mapGrid` cannot be raised by a caller), 512 KB proposal and 1 MB draft guards, mapper never
  throws, failure leaves `mapping: null`. Tests use operation counts, not timing, except the
  10 s backstop noted in m6.
- React: `key={mapState.version}` remount keeps title/description and other fields via
  `withSections(current, ...)`; `includeCover` and the duplicate banner live above the keyed
  component so they survive; focus is restored explicitly through `pendingFocus`; `edited`
  detection ignores row keys; keys are index-derived so SSR and client markup match; the
  `details` open state is controlled and synced.
- No `.skip`, `.todo`, `fixme` or `only` in the added tests; no test relies on a sleep.

## Resolution (post-review pass)

M1, M2, M3, m1, m2 and m3 are fixed; m4 to m6 and the nits are carried. Evidence is the
commit series after this review (`git log --oneline -6`), summarized here.

- **M1**: `imperativeLeadIndexes` (`step-verbs.ts`) marks the listed verb that opens a sentence
  (after "-ly" adverbs and "then"/"next", followed by more words in the same clause, not a list
  noun); `findMentions` ignores a single-word match there. No new word list: it reuses the verb
  list and its `cream`/`brown` guards. Unit tests in `step-verbs`, `ingredient-match` and
  `map-grid`; fixtures `hard-verb-is-ingredient-cream` and `-unmentioned`. Limits: only the
  sentence-initial verb (`Mix well and cream the butter` is still a mention), and `Zest the
  lemon` with a `zest` ingredient leaves `zest` unmentioned (lower score, no guess). The review's
  suggested fixture bound (`max 0.69` for the cream case) applies when cream is only the verb
  (`-unmentioned`); when cream is also used as a noun later the grid is now exact and high.
- **M2**: `splitOk < 1` caps at 0.69 (`map-confidence.ts`); both split fixtures are now
  `list`, `max 0.69`. Test table updated.
- **M3**: 12 fixtures added (11 hard, 1 clean) from the reviewer's shapes and general prose, expectations
  written before running. First run: 2 confident-wrong. One was my row-name typo, one was a real mapper
  bug (trailing "Finish with the remaining butter" was a bottom banner and lost the split portion at
  confidence 1.00), fixed in the mapper. One miss remains (`basil leaves` vs "the basil", 0.69). The guard now fails on
  any hard fixture missing its stated expectation unless it carries `known_miss` with a reason, and
  on a stale marker. Three known misses: yoghurt, no-verbs, basil leaves. Numbers: fixtures 53 -> 65,
  clean 26/26 -> 27/27 (110/110 -> 114/114 spans), hard exact 13/15 -> 23/25, confident-wrong 0 -> 0,
  calibration 0.70-1.00 bucket 43/43 -> 50/50, 0.40-0.69 bucket 2 -> 6 fixtures (5 exact). The README for
  the corpus and the report header now say the table is a regression net on self-authored text,
  not an accuracy estimate.
- **m1**: banner-only ingredients no longer count as matched (`hard-banner-mentions-ingredient` is
  now a list at 0.44). Product trade-off documented in the tasklist.
- **m2**: all calibration deviations are listed in the tasklist "Calibration changes" block (the two extra
  ones as items 6 and 7, plus the post-review changes 8 to 11). `distinctSpans` now counts
  (section, `row_end`) pairs; fixture `clean-two-sections-uniform-spans`. The no-verb cap trigger
  (`verbs <= 0`) was left as is and is carried.
- **m3**: `readMapping` derives `level` from `confidence`, caps warnings at 100 strings of at most 300
  characters, and requires `signals` to be an object of at most 20 finite numbers.
