## Summary

The format and the restore core are careful. Redaction by construction, strict zod objects with caps, one
`BEGIN IMMEDIATE` transaction per recipe, fresh ids, `withDeferredFts` called inside that transaction (a rolled-back
recipe leaves no FTS row; tested), photo files written only after the recipe commit and removed if the row insert
fails, conflict decided against the pre-run titles, one apply per process, and every staged file is removed on every
route path I traced (stage: `finally` with `keep`; apply: `finally` `discardStage`; delete; TTL and orphan prune).
Leases (`beginUpload`, `beginApply`, `acquireExport`) are released in `finally` or by the stream close hook; no early
return between acquire and `try` leaks one. The proxy matcher guard `(?:/|$)` is exact, and all three routes call
`authenticate` (CSRF, then session) and set `no-store` and `nosniff` themselves.

Verdict: **APPROVE WITH CONDITIONS.** 0 blockers, 1 major, 6 minor, 5 nits. Condition: decide and document M1.

## Findings

### Major

M1. `src/lib/backup/unzip.ts:84-86` (`isAllowedEntryName`) and `:168`. Any entry other than `backup.json` or
`photos/<ULID>.webp` refuses the whole archive, including harmless ones. The test table refuses `photos/` as a
"directory entry" on purpose. Failure scenario: a user unzips the backup to inspect it and zips it again. `zip -r
b.zip backup.json photos` writes a `photos/` entry; Python `shutil.make_archive` does too; Finder "Compress" of the
folder prefixes every name with the folder (`cellar-backup/backup.json`) and adds `__MACOSX/` and `.DS_Store`.
Each gives 422 `zip_invalid`, and the message ("must be a backup downloaded from Cellar") does not say why. Data
descriptors, extra fields (0x5455, Unix attrs), `version made by` and stored or deflated methods are handled
correctly (extra length is skipped, central sizes trusted), so the allowlist is the only obstacle. Fix: skip (do not
read, do not count as photos) entries that are directories (name ends in `/`, size 0) and the well-known
`__MACOSX/` and `.DS_Store` names, or at least add the reason words to the 422 body and to the README. Keeping
the strict stance is defensible, but then document "re-zipped archives are not accepted".

### Minor

m1. `src/lib/backup/unzip.ts:19-20` vs `schema.ts:11` (`MAX_RECIPES = 5000`). `scripts/export-sizes.ts` measured
1000 fixture recipes at 4.6 MiB of JSON, so 5000 would be about 23 MiB, over the 16 MiB manifest cap. The comment
"a 5 000 recipe export is a few MiB" is wrong for that fixture. Scenario: export succeeds, restore of the same file
is 413 (JSON) or `entry_too_large` (zip). The break-even is near 3 400 recipes of that size. Fix: make export
return 413 `export_too_large` when the manifest exceeds the cap, or raise the cap together with its memory
measurement (the checkpoint left the 16 MiB path unmeasured); correct the comment.

m2. `src/components/backup/RestoreView.tsx:~224` (`stoppedAt`, `index: state.result.failed_at`). `failed_at` is a
0-based index (`restore.ts` loop `k`), shown as "Stopped at recipe 0 of 12" when the first recipe fails. Fix: pass
`failed_at + 1`, or document 0-based in the message. Check the unit test does not pin the wrong value.

m3. `src/components/backup/backup-logic.ts:97-113` (`stageError`) and `:132-138` (`applyError`). Status 5xx, 408, 429
and 400 all map to the key `network` ("Could not reach the server") and discard the server message. A rate-limited
user (429, which has `Retry-After`) or a server 500 sees a connection hint. In apply, a 422 (staged file no longer
valid) or 500 returns to `preview` with that text and the stage is already discarded server-side (`finally`), so
the retry is a 404 "expired". Fix: map 429, 408 and 5xx to a generic "failed" or the server `message`; on apply
500 treat the stage as gone.

m4. `src/lib/backup/restore.ts:305-340` (photo phase). Photos run after the recipe commit; a photo that fails
(decode busy after 3 retries, unreadable, budget) or a process death between commit and photos leaves a recipe
without photos, and re-running with `skip` skips that recipe, so the photo is unrecoverable except by `rename`
(duplicate recipe). Docs say "run the same file again with Skip to continue", which holds only for recipes. Also a
crash between `writeFile` and the row insert (`storePhoto`) leaves orphan files in `UPLOADS_DIR`, with no sweeper.
Fix: document it in the result text (`photosFailed`), and consider a "photos only for recipes already restored"
rerun or a note in `docs/deployment.md` about orphan files.

m5. `src/lib/backup/schema.ts:127,146` (`MAX_SECTIONS 200`, `MAX_INGREDIENTS_PER_SECTION 400`, steps 400) against
`recipes/schemas.ts:129-148` (20 sections, 200 ingredients, 100 steps). A hand-edited file passes preview and
restores a recipe the edit form then rejects on every save. Likewise a tag that `normalizeTagName` rejects
(zero-width, control) passes the schema (`min(1).max(40)`), then throws in `setRecipeTags` and stops the whole run
at that recipe (`failed_at`). Fix: reuse the app limits and `normalizeTagName` in the backup schema so preview
catches it.

m6. `src/lib/backup/restore.ts:174-181` (`notesSkipped` UI text). In a member restore, skipped notes are other
users' shared notes, but `backup.result.notesSkipped` says "written by a user who does not exist here". The docs
describe the real reason. Fix: neutral wording ("notes by other users were left out").

### Nits

n1. `restore.ts:62` `normalizeTitle` lowercases after NFC and does not re-normalize (the tag code comment says
lowercasing can change composition); inner whitespace is not collapsed, so "Apple  Pie" and "Apple Pie" are not
conflicts. Either follow the tag rule or state "trim only" in G16 docs.

n2. `restore.ts:72-79` `renamedTitle`: slicing the raw title can leave a trailing space before the suffix; a later
file recipe literally titled "X (restored)" is not a conflict (only pre-run titles) and duplicates the renamed copy.
Rename is not idempotent on a second run by design; fine, worth one sentence in the docs.

n3. Restored recipes all get `updated_at = now` in one burst; `ulid()` within a millisecond is not monotonic, so the
original relative order in the recently-updated list is arbitrary. Documented as "stamps not applied". Using one
`monotonicFactory` for recipe ids would keep file order at no cost.

n4. `useRestore.ts:12-15` `live` ref is synced in an effect, so two clicks inside one render could both pass the
`phase` guard; the reducer guards (`uploadStart`, `applyStart`) make the second dispatch a no-op but the request
itself would still start. Update the ref in the reducer wrapper or set `abortRef` before the first await.

n5. `restore-api.ts:41` `xhr.ontimeout = xhr.onerror` while no `xhr.timeout` is set (dead line); an early 413 from
Caddy that closes the socket mid-upload surfaces as `onerror` ("network") rather than "too large" (the client
precheck covers the common case). Test gap: no test asserts a restored recipe is found by ingredient and note
search (`restore.test.ts:360` only checks the rollback case).
