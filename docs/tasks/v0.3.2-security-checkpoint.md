## Condition 3 gap: syscall and capability evidence (closed)

Run (image rebuilt from the current tree, `cellar-browser:t11`):

```
docker/browser/run.sh --memory 2g --memory-swap 2g -v "$PWD/docker/browser/test:/srv/test:ro" \
  -e BROWSER_DOCKER_TESTS=1 -e HEADLESS_ALLOW_NO_TOKEN=1 --entrypoint node cellar-browser:t11 \
  --test test/syscalls.docker.test.ts          # 13 tests, 13 pass
```

The test calls `mount`, `bpf`, `keyctl`, `ptrace` and `open_by_handle_at` through perl `syscall()` (x86_64 and aarch64 numbers), both from the plain process and from inside a freshly unshared user + mount namespace (the state a compromised renderer can reach, because `unshare` is allowed). All return `-1 EPERM`. It also asserts inside the container: `CapBnd = 0000000000040000` (CAP_SYS_CHROOT only), `CapEff/CapAmb = 0`, `NoNewPrivs 1`, `Seccomp 2`, uid 10001.

Honest limits, measured with `--security-opt seccomp=unconfined` as a control:

| Call | With profile | Unconfined (same caps) | Who denies |
| --- | --- | --- | --- |
| `mount` in plain process | EPERM | EPERM | caps and seccomp (not distinguishable) |
| `mount` in new userns | EPERM | **0 (success)** | seccomp only |
| `keyctl(-1)` | EPERM | 95 EOPNOTSUPP | seccomp only |
| `bpf`, `ptrace`, `open_by_handle_at` | EPERM | EPERM | kernel checks (no caps / sysctl) as well; seccomp is a second layer |

So the in-namespace `mount` and `keyctl` cases would fail if the profile gained those syscalls; for `bpf`, `ptrace` and `open_by_handle_at` the test proves the observable behaviour, and `seccomp.test.ts` plus `check-seccomp.mjs` prove statically that they are not unconditionally allowed. Compose-level proof (`docker compose -p t11check --profile headless up -d browser`, then `docker inspect` and `/proc/1/status`): `CapAdd=[CAP_SYS_CHROOT] CapDrop=[ALL]`, `no-new-privileges`, seccomp profile inlined, `ReadonlyRootfs=true`, no mounts, no port bindings, `Privileged=false`, networks `headless-link` and `headless-egress` only, sandbox self-check ok, container healthy. A static test (`test/compose.test.ts`, runs in `npm run test:browser`) now pins these compose properties so a later edit cannot add `SYS_ADMIN`, a volume, a port or the default network without failing CI.

## Findings

### F1 (Medium) Zombie Chromium children exhaust `pids_limit`

`killChromium` SIGKILLs the process group after the 30 s deadline, but PID 1 in the container is `node`, which never reaps adopted orphans. Each kill leaves the zygote, renderer and utility processes as zombies, and zombies count against the cgroup `pids_limit: 256`. Evidence: a script that launches Chromium, opens a page and calls `killChromium()` three times left 4, 8, then 12 zombies without an init and 0 with `docker run --init`. Roughly 60 timeouts (an A2 user can cause them with a slow page) leave the sidecar unable to spawn Chromium until the container is restarted; the restart policy does not trigger because the container stays up.

Fix (applied): `init: true` on the compose service, `--init` in `run.sh`, and an assertion in `test/compose.test.ts`. Re-checked: container starts through `docker-init`, self-check passes, caps/seccomp unchanged, 39/39 Docker tests green with `--init`.

### F3 (Medium) Real-Chromium tests are not in CI

`npm run test:browser` reports 39 skipped (everything gated by `BROWSER_DOCKER_TESTS=1`): the T9 proxy-bypass matrix, the sandbox/sandbox-escape cases and the new syscall test. CI only builds the image. A regression in the guards would pass CI. Not fixed here because I cannot validate a GitHub-hosted runner (Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor, which may need a `sysctl` toggle) from this host, and a red unverified job is worse than a documented gap.

Ticket (T18, owner devops-automator): in the `docker` job load the amd64 image and run `docker/browser/run.sh --memory 2g --memory-swap 2g ... --test test/*.docker.test.ts`, adding `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` if the runner needs it. Until then the Gate must run the three docker test files by hand (command in each file header; use `--memory 2g`).

### F4 (Low) Server timeouts and bind address

`createServer` in `server.ts` leaves `headersTimeout`/`requestTimeout` at Node defaults, so a client on `headless-link` can hold sockets for up to 300 s (it cannot take a render slot; auth is checked before the body is read). It also binds `0.0.0.0`, so the port is reachable from the egress bridge gateway, but the bearer token is mandatory. Suggest `headersTimeout: 5000`, `requestTimeout: 15000`, `maxHeaderSize: 8192` with a test, in T18.

### F5 (Info, accepted) Token handling

R7 asked for `${HEADLESS_TOKEN:?set a token}`. Compose interpolates the whole file for every profile, so `:?` would break `docker compose up` with the profile off (the app service reads the same variable). The sidecar itself exits 1 without a token, so the property R7 wants (no tokenless sidecar) holds; with `restart: unless-stopped` a missing token shows as a restart loop with a clear FATAL line. The token is visible in `docker inspect` of the browser container and in its own `/proc/1/environ`; Chromium does not receive it, and it only grants `/render`. Accepted.

## Changes outside the headless feature (review m7)

Two changes in this slice do not belong to headless; they are listed here so they are not missed in a large diff.

- `src/lib/import/safe-fetch.ts`: when a host resolves to several addresses, the fetch tries the next address after a connect failure, and the abort and listener handling was reworked. The property that makes the fallback safe is that every candidate address is validated against the SSRF policy before the first connect; the connection is then pinned to a validated address, so a fallback can never reach an address the policy would refuse. Tests: `safe-fetch.test.ts`.
- `src/app/api/photos/[id]/route.ts`: `Cache-Control` change (v0.3.0 review m5, commit `db5de1b`). Tests: `photos-route.test.ts`.
