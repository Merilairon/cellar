# v0.5.0 Security Checkpoint (T8)

Scope: slice A of v1.0 on `release/v0.5.0` (HEAD `0dc92a8`): `src/lib/recipes/access.ts` (`canView`, `canEdit`, `isImportedUnedited`), `share.ts`, `public.ts`, `service.ts` (`toApiShare`, `createOrRotateLinkFor`, `revokeLinkFor`), `src/lib/db/recipes.ts` (`setShareToken`, `getRecipeRowByShareToken`), `src/app/api/recipes/[id]/share-link/route.ts`, `src/app/r/[token]/page.tsx`, `src/app/robots.ts`, `src/proxy.ts`, `src/lib/security/public-limit.ts` (with `request-client.ts`, `proxy-trust.ts`, `rate-limit.ts`), `src/lib/auth/routes.ts`, `src/components/recipe/public/*`, `src/components/recipe/share/*`, the print CSS and `RecipeMeta.tsx`. Reviewed against the Security note, T8, G1, G3 to G7, G24, R4, R5 and R8 in `v1.0-tasklist.md` and UX spec sections 2 and 3. Code read, unit negative controls, and a live probe against a production build (`next build` plus `next start` on port 3777, temp SQLite, `TRUSTED_PROXIES=127.0.0.1`, `RATE_LIMIT_PUBLIC_MAX=30`). Both the build and the server were run in a throwaway git worktree; the server was stopped and the worktree removed. Playwright was not run (needs the pinned image); e2e specs are cited as evidence by reading only.

## Verdict: PASS

No Critical, High or Medium finding. Five negative controls fail the expected tests; six extra controls were run and all fail a test, except one that is covered by a second layer (X2). Two Low findings and several Info items are listed; none blocks the tag.

## Findings

| ID | Severity | Title | Status |
| --- | --- | --- | --- |
| L1 | Low | The public limiter trusts the right-most non-trusted `X-Forwarded-For` hop. Next 16 does not expose the TCP peer (`proxy-trust.ts` spike note), so if the app port is reachable directly, a client can send a fresh `X-Forwarded-For` per request and never be limited. Live: 40 requests with 40 different spoofed addresses gave 0 x 429 (limit 30). The same property already holds for login and registration | Accepted by design (documented: with `TRUSTED_PROXIES` set the operator asserts the app port is not published). Keep the "Traefik/Caddy example must not publish the app port" check in T15/T14. The 128-bit token means the limiter protects CPU, not secrecy |
| L2 | Low | The fail-open branch of `publicRateLimit` (`public-limit.ts:55`, bad env throws, request proceeds) has no test. `proxy.test.ts` covers the unknown-client branch (no `TRUSTED_PROXIES`), not the `catch`. Removing the `try/catch` was not exercised (no test names it) | Open, carryover: one unit test that makes the mocked `getEnv` throw and expects a non-429 response |
| I1 | Info | `/r/<token>/`, `//r/<token>`, `/r//<token>` answer a Next-level 308 to `/r/<token>` before the proxy runs. The 308 carries no security headers and `Location` contains the token (the token the visitor already sent). It is not counted by the limiter. Not a leak: same origin, same token, the target carries `no-referrer` | Accepted |
| I2 | Info | `POST /r/<token>` renders the page (200, counted by the limiter, no state change). `HEAD` 200, `OPTIONS` 400 (Next). `GET` semantics only matter for caching, and the response is `no-store` | Accepted |
| I3 | Info | The public page's RSC payload carries the whole i18n catalog (owner-side strings such as "Shared by {name}"). No data, only labels | Accepted |
| I4 | Info | `limiterKey` does not canonicalize IPv6 notation (`2001:0db8:...` and `2001:db8:...` give different keys) and lumps unusual `::`-first forms into `0:0:0:0::/64`. A trusted proxy writes canonical addresses, so this only matters with a spoofed header (L1). Over-grouping can only over-limit, never under-limit | Accepted |
| I5 | Info | Residual DB-lookup timing: `getRecipeRowByShareToken` is an indexed equality lookup on a `UNIQUE` column. B-tree comparison time can depend on a shared prefix, so a hit and a miss are not byte-for-byte constant. Not exploitable: 128 random bits, network jitter dwarfs the signal, the limiter caps probes, and the later `timingSafeEqual` runs only after a row was found | Accepted |
| I6 | Info | The token is in the URL, so it is in browser history, in reverse-proxy access logs and on a printed page when the browser prints its URL footer. The app logs no request URLs (only `console.warn`/`error` in import, photos, instrumentation; none take a path) | Accepted, operator note for the deployment docs |

### 2. Uniform 404

Live (production build): unknown, revoked, malformed-short and trailing-garbage tokens all answered `404`, headers identical after normalization (`Referrer-Policy: no-referrer`, `X-Content-Type-Options`, `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`, same CSP shape), body byte count 45,691 for unknown and revoked, and byte-identical after replacing the nonce and the echoed token. `/r/abc` is 404 with the same headers (body differs only by the echoed path segment, as the router state embeds it). `getPublicRecipe` returns the single value `null` for every branch (malformed, unknown, revoked, deleted, disabled); `page.tsx:32` turns it into the one `notFound()`, and `generateMetadata` adds no title on a miss (`page.tsx:23`). Evidence: `public.test.ts` "every failure is the same value"; e2e `public-page.spec.ts` "every miss is the same 404" (status, all headers, body byte for byte, 7 probes including deleted-recipe and revoked), "a link turned off a moment ago and a rotated token both fall into the same 404". Revoke is a single `UPDATE ... share_token = NULL` (`recipes.ts:335`) and the page is `force-dynamic` with `no-store`, so the next request misses (live: DELETE 204, next GET 404).

Header scoping: `sharePath` only overrides `Referrer-Policy`; the 429 path also carries the full security header set, `Retry-After` and `Cache-Control: no-store`. `isPublicPath` rejects `..`, `//`, `\` and requires something after `/r/`. The limiter key is `limiterKey(getClientIp(headers))`; the client is the right-most hop that is not a trusted proxy, left-side hops are ignored (live: `10.0.0.$i, 192.0.2.77` limited as one client, 10 x 429 of 40). IPv6 keyed on /64 (live: 40 addresses in one /64 gave 10 x 429; `proxy.test.ts` "keys IPv6 clients on their /64"). Unknown client is not limited by design (`proxy.test.ts` "skips the limit when the client is unknown"; live without `TRUSTED_PROXIES` was not run). Live with no `X-Forwarded-For`: 10 x 429 of 40, because `next start` fills the header from the socket and `localhost` resolved to `::1`, which is not in `TRUSTED_PROXIES=127.0.0.1`, so the peer became the client. Fail-open on a broken env: `public-limit.ts:55`, L2. Live 429: exactly 30 allowed then 429 `Retry-After: 60`, body "Too many attempts. Try again later.", `no-store`, `no-referrer`.

### 4. `canView` matrix and `readableBy`

`access.test.ts` enumerates 4 actors x 2 visibilities x 4 link states ("has the full 4 x 2 x 4 matrix"); signed-in actors get the same answer with or without a context. `readable.test.ts` keeps the SQL twin `readableBy` in step for signed-in actors; the admin-reads-private-by-id asymmetry is documented in both files and in data-model §1. Anonymous: `canView(null, ...)` is true only with a stored, matching token and `publicLinksEnabled === true`; a token is independent of `visibility` (G24 test "anonymous with no token never views anything, including a `users` recipe"). `canEdit(null, ...)` is false.

### 6. `share-link` CSRF and authorization

`authenticate` runs first: no CSRF proof or cross-site 403 (even when anonymous), then 401. Then `PUBLIC_LINKS_ENABLED` false is `403 public_links_disabled`, then `createOrRotateLinkFor` / `revokeLinkFor`: missing or private-foreign 404, readable-but-not-writable 403 (member on a `users` recipe), owner and admin 201/204. The write itself re-checks in the transaction (`writeGuard`, `setShareToken`). Every response is wrapped in `noStore`. Matrix live-tested only for anonymous (401); full matrix by `share-link.test.ts` "authorization matrix" (reader 403 on `users`, 404 on private and missing, admin 201/204, anonymous 401 with `no-store`), "missing or cross-origin CSRF proof is 403 before any work", and "owner creates (201) and revokes (204); both no-store". `updated_at` is unchanged by share actions (R5), "updated_at is byte-identical across create, rotate and revoke".

### 7. `PUBLIC_LINKS_ENABLED=false`

Enforced in three server-side layers: `canView` (`access.ts:45`, strict `=== true`), `getPublicRecipe` (`public.ts:41`), the share-link route (`route.ts:17,32`), plus `toApiShare` hides the token. Tests: `access.test.ts` "PUBLIC_LINKS_ENABLED=false keeps a matching token inert", "publicLinksEnabled must be the boolean true"; `public.test.ts` "PUBLIC_LINKS_ENABLED=false makes a stored token inert, and re-enabling restores it"; `share-link.test.ts` "PUBLIC_LINKS_ENABLED=false: 403 public_links_disabled on both, tokens untouched".

### 8. User-controlled text, copyright notice

No `dangerouslySetInnerHTML` or `innerHTML` in `src` (grep; only tests asserting their absence). ## Residuals

- L1 (spoofable `X-Forwarded-For` when the app port is published), I5 (DB lookup timing), I6 (token in URLs, proxy logs, history).
- Anyone holding a link can read that recipe (title, ingredients, steps, source, tags) until it is revoked or rotated; there is no expiry and no per-link view count (Q-level decision, accepted for v1.0).
- Admins see another owner's token through `GET /api/recipes/:id` (`canEdit` true for admin); consistent with admin-writes-any.
- Link text copied from the share dialog goes to the clipboard; nothing is stored client side (public page keeps no localStorage or cookies, e2e "store nothing").
- Not tested: Playwright suite, a real reverse proxy with real client addresses, real CDN behaviour (headers reviewed only), timing measurement of hit versus miss, browsers other than the unit/jsdom path.

## Try in v1.0 T15 (pentester list)

1. Port-published deployment: spoof `X-Forwarded-For` to bypass the limiter (L1); confirm the Traefik/Caddy examples do not publish the app port.
2. Multi-hop `X-Forwarded-For` with trusted-looking left hops; IPv6 with zone ids, leading-zero forms (I4).
3. Hit-versus-miss timing over many samples at the lookup (I5), with and without the limiter.
4. Cache poisoning/deception: `Accept: text/x-component`, `RSC: 1`, `_rsc=` query on `/r/<T>` (the RSC response of a valid token, cacheability and `Vary`).
5. Rotation race: two POSTs, revoke during an in-flight render; confirm the old token 404s on the next request only.
6. Token-bearing `Referer` when navigating from the page to the source link and from print/preview; open redirect via `//r/<T>` forms (I1).
7. Enumerate through other surfaces: search/FTS, export (slice B), photos by id, `copied_from_id` lineage, the notes and ratings endpoints for a link visitor.
8. `PUBLIC_LINKS_ENABLED` flip while links exist: token stays inert and hidden, returns on re-enable.
9. Stored XSS in every public field (title, description, ingredient name, step label, tags, source name) under the CSP.
