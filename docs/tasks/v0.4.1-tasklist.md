**Objective (quoted, milestone 04)**: "Make the recipe collection usable day to day: search and tags, unit conversion and scaling, a visual grid editor, and photos/notes/ratings." Slice rule: "**4b (v0.4.1)** grid editor (5). ... The grid editor is the riskiest slice, so it ships on its own." "Components from M2 (`RecipeGrid`, validation) are reused by the editor."

**Requirement 5 (quoted, in full)**: "**Grid editor** (prototype: grid-prototype.html, 'Edit spans') `GridEditor` component. Interaction by device: **tablet/desktop** use drag handles on the top and bottom edge of each step cell plus the keyboard equivalents; **phone** (< 640 px) must not rely on drag or on four buttons inside each cell (too bulky at 375 px): selecting a step opens a bottom sheet with Start row and End row steppers (- / +) showing the covered ingredient names, and the grid highlights the span live. Buttons must be at least 36 px (44 px on touch) with aria-labels. Editor features: reorder ingredients (drag or buttons), edit text inline; add/rename/delete sections; split an ingredient into portion rows; add top/bottom banner steps; for each step column, drag top/bottom handles to set `row_start`/`row_end` (also keyboard operable); add/delete/reorder steps; convert step to banner; live validation warnings (uncovered ingredients); undo/redo; atomic save via `PUT /api/recipes/:id/grid`."

**Acceptance (quoted, 04b subset)**:
- "Editor can recreate the sample grid from scratch using only the mouse and also only the keyboard."
- Instructions: "Reuse `validateGrid` from M2 in both editor and API." (the function is `validateRecipeGrid` / `validateSection` in `src/lib/grid/validate.ts`, see G2.) "Keep the editor state in a reducer so undo/redo is straightforward." "All new strings go to `messages/en.json`; avoid user-facing hard-coded units/labels."
- Release plan: "Accessibility pass on grid (keyboard, screen reader table semantics)" is a v1.0 checklist item; this slice carries the keyboard acceptance for the editor (v0.4.0 T12 deferred "the editor keyboard acceptance is 04b").

**Data-model §2 validation rules (quoted, governs editor and API)**: 1 positions contiguous from 0; 2 `row_start <= row_end`, both within range; 3 a column step includes at least one row; 4 order `banner_top`, `column` by position, `banner_bottom`; 5 "Every row must be covered by at least one column step (warn, don't block)"; 6 rows sharing a `split_group_id` must be in the same section. Data-model §5: "`PUT /api/recipes/:id/grid` | Replace ingredient order + step spans atomically".

**Target pace**: 2 weekends maximum (PM sizing below; the Release Plan rule "Re-split any slice that cannot finish in two weekends" applies, the pre-agreed split is in Sizing). Weekend 1 is design, pure logic and the API, no editor UI. Weekend 2 is the UI, tests, checks and gate.

**Hard rules**
- The reducer and all span arithmetic are **pure and tested before any editor UI** (spec instruction; mirrors v0.4.0 units rule). T2 and T3 land and are green before T4 starts. No `Date`, `Math.random`, DOM, `fetch` or React import in the pure module.
- **One validator**: `validateRecipeGrid` (and `validateSection`) from `src/lib/grid/validate.ts` is the only rule source on the client and in the API. No second copy of rules 1 to 6 in the editor. Errors block save (editor shows them, API returns 422); `row_uncovered` is a warning only and never blocks (rule 5).
- **Atomic save**: one `PUT` replaces sections, ingredients and steps in one `BEGIN IMMEDIATE` transaction; any failure leaves the stored recipe untouched; the FTS row is rebuilt once (`withDeferredFts`). The endpoint never touches recipe fields, tags, visibility, photos.
- **Authorization identical to `PUT /api/recipes/:id`**: CSRF first (403), session (401), `canRead` else 404, `canWrite` else 403, and the guard is re-run on the stored row inside the write transaction (no check-then-act gap). A recipe the actor cannot read is indistinguishable from a missing one.
- **No server trust in client state**: the server re-parses the body with the same zod schemas, recomputes `view_mode`, rewrites `split_group_id` to fresh ULIDs, runs `completeMeasures`, enforces the 20 / 200 / 100 limits and the body cap. The client never sends ids as authority (existing child ids change on every replace).
- **Derived measures never go stale**: when the editor changes an ingredient's quantity or unit text, the non-primary side is cleared and re-derived by the server (`completeMeasures`), exactly as the recipe form does (G11, carryover C7). Unchanged ingredients keep their stored sides untouched.
- Every control has a text alternative and an `aria-label` where the text is not visible; targets at least 36 px (44 px on touch, `pointer: coarse`) per the spec; nothing depends on colour alone; nothing is operable only by drag.
- All strings in `messages/en.json`; one message per new error code; no hard-coded labels. User text (ingredient names, step labels, section titles) is rendered as React text only; no `dangerouslySetInnerHTML`.
- Conventional Commit after each numbered task, **no co-author trailers** (owner's global CLAUDE.md). No background processes or server start commands in task commands; the dev server, Playwright and docker runs are done by the developer or CI.
- The editor chunk is loaded only on the recipe page and only when editing starts (dynamic import; read the Next 16 docs for the current syntax), so view-only pages do not pay for it.

## Security note (new write path)

Assets: recipe integrity (the whole structure is replaced in one call), other users' recipes (authorization), the single-threaded server (a maximal payload fans out into thousands of inserts and FTS work), stored text rendered later to other users (stored XSS), client-chosen identifiers (`split_group_id`). Attacker: any signed-in member trying to edit a recipe they only read (`users` visibility) or cannot see (`private`), an unauthenticated caller, or a CSRF page. Required controls: CSRF and session checks before any work (reuse `authenticate`), `canRead` then `canWrite` then in-transaction guard (reuse `writeGuard`), `Content-Type: application/json` (415), body-size cap before parsing, zod schema with the existing limits, server-side `validateRecipeGrid`, `base_updated_at` compare inside the transaction, all text stored as data and rendered as React text, `split_group_id` rewritten server-side, no SQL string building, `Cache-Control: private, no-store` on every response, error bodies carry paths and codes only (no SQL, no stack). Residual to decide in the checkpoint (T14): no rate limit on write endpoints (parity with `PUT /api/recipes/:id`, which is also unthrottled); one maximal replace cost (measured in T3); an admin can write any recipe (existing `canWrite`, parity); a read-only `users`-visible recipe must return 403 not 200; a private foreign recipe must return 404 not 403.
